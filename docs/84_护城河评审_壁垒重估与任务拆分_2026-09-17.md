## 一、评审范围与结论摘要

### 1.1 评审对象

PRD §14.3 提出的护城河主张（原始 5 维度）归并为**三大支柱 + 一个总纲**：

| 支柱 | §14.3 对应维度 | 供血层 |
|---|---|---|
| 支柱一：刻意训练机制（闪测） | 维度一 机制 | — |
| 支柱二：个人资产沉淀（语料库三元组） | 维度二 沉淀 | 维度三 内容源 |
| 支柱三：真人实战出口（话题建议） | 维度五 实战出口 | 维度四 反馈层级 |

总纲：**结构化的用户行为数据飞轮**（§14.3 末节）。

### 1.2 结论摘要

1. **战略主张成立，但今天它是蓝图不是防御**。不跟豆包比 AI 能力、比"训练系统"的定位准确（发动机 vs 赛车赛道的比喻成立）；但 5 维度中 3 维刚被 P0-1 解锁、1 维（实战出口）仍被 P1-2 削弱，**目前 0 维在产出数据**。
2. **PRD 对各维度的星级自评存在系统性高估**，需要重估（见 §四）。核心误判是"调度算法不可复制"——SM-2 是公开算法，真正的壁垒是算法跑出来的行为数据。
3. **敌人排序：90 天流失 > 炼化质量 > 豆包**。数据飞轮的前提是留存，不是反过来；留存 → 数据 → 壁垒，顺序不可颠倒。

### 1.3 与 83_ 文档的关系

`83_` 给出了三大机制的风险清单与实验设计（方向正确，予以采纳），本文档补上两件它没做的事：

- **壁垒强度的诚实重估**（PRD 自评 vs 评审重估）；
- **执行顺序重排**（按"激活飞轮"而非"完成功能"排序，P1-2 从 W7 提前至本次执行）。

同时修正 `83_` 中的一处事实偏差：**PRD §5.3.2 已定义 +24h 入库冷却**（V1.7 修订口径：入库 → `next_due_at = +24h`），并非"未定义冷却期"；真正的缺口是**首次闪测引导**与**过期任务的衰减策略**（到期队列只增不减 → 闪测债务）。

## 二、核心出发点回顾

**一句话定位**（PRD §2-3）：把你的工作日常变成英语练习——以真实工作场景为料、以口语演练为核心的个性化职场英语训练引擎。

**核心闭环**（PRD §5.1）：

```
说（实战演练）→ 读（自我输出镜像）→ 炼化（话术块萃取）→
提取训练（内化）→ 语料库（资产沉淀）→ 话题建议（走向真人实战）
```

**北极星指标**：周完成"说 → 回顾 → 入库"完整流水线至少 1 次的用户占比（含迷你会话）。

**护城河的本质是一条数据链**：

```
炼化质量 → 语料库资产 → 闪测数据（遗忘曲线）→ 绿灯 → 话题建议 → 实战命中 → 正反馈
```

这条链上**每一环都必须真实产出数据**，任何一环空转，后面的环拿不到输入，飞轮不转。因此任务拆分的第一原则是：**每个任务必须回答"它让哪条数据流开始产出数据"**，而不是"它完成了哪个功能"。

## 三、三大护城河逐条评审

### 3.1 支柱一：闪测（间隔重复 + 主动召回）

**PRD 主张**：⭐⭐⭐⭐⭐，"调度算法不可复制"。

**评审结论**：机制科学（间隔重复 + 主动召回是被认知科学反复验证的），但**壁垒归因错误**。

- SM-2 是公开算法，Anki 用了十几年；竞品抄一个调度器只需一个周末——PRD 自己的结论也承认"竞品一个周末就能抄走 UI"。**算法是货架商品**。
- 真正不可复制的是**算法跑出来的数据**：每个用户哪些块第几次才自动化、哪些概念反复卡壳（"卡壳地图"）。这部分应并入总纲的数据飞轮，而非单独计五星。

**两个 PM 级风险**：

1. **闪测是负向体验型功能**。它的天然属性是考试，焦虑是副作用。5 秒限时 + 无文本提示考的是"脱口而出"（设计正确），但首次体验若被吓退，机制再科学也产不出数据。PRD 已有 +24h 冷却，缺的是：首次引导（"明天系统会抽查你练过的表达"）、绿灯达成的仪式感（"已自动化"是护城河关键里程碑，不能当普通状态变更）、以及**过期任务衰减**（避免"闪测债务"压垮低频用户）。
2. **上游依赖**：闪测考的内容来自炼化。炼化质量差 → 用户在"考一句没价值的话" → 对整个机制失去信任。**支柱一的生死握在支柱二手里**。

**当前实现**：调度器就绪（`internal/drill/scheduler.go`），状态机/`next_due_at`/`success_streak` 全部实现；闪测 UI 与判定（E1-E5）待 W6。

### 3.2 支柱二：语料库三元组（话术块沉淀）

**PRD 主张**：⭐⭐⭐⭐⭐，"数据飞轮不可复制"。

**评审结论**：**三支柱中唯一无争议的壁垒**，但存在两个被忽视的时滞。

- **壁垒有时滞**：50 个话术块的切换成本并不高，手动复制一个周末就能带走。壁垒要到数百块 + 使用历史 + 调度状态才真正咬合。在那之前，语料库是**功能，不是壁垒**。
- **飞轮的前提是留存**：PRD 自己引用"90% 用户 3 个月流失"。留存不成立，数据飞轮永远转不起来。正确的因果是 **留存 → 数据 → 壁垒**，而不是先有壁垒再谈留存。这意味着早期执行纪律是**速度优先于打磨**——PRD 末尾"炼化/闪测/语料库/话题建议 > UI 美观"的工程优先级提醒方向完全正确。

**质量风险（最需要补的洞）**：PRD §5.2 对"地道版"只有三个字，没有可操作标准——而三元组质量就是产品全部价值。需要：改写标准的操作化定义（更简洁/更地道/保留原意/可迁移）、用户负反馈通道（"不够地道"按钮）、Prompt A/B。

**供血层现状**：维度三（内容源 ⭐⭐⭐⭐）实际 A1/A2 素材输入仍属"后续波次"未启动——**语料库的供血层还没接上**，当前炼化原料只来自 App 内对话与救援事件（后者见 P1-1）。

**当前实现**：表结构/CRUD/状态灯/标签就绪；真实 LLM 炼化已验证（82_ 报告：2 个高质量三元组，锚点校验通过）；P1-1（救援事件 → 炼化）未打通。

### 3.3 支柱三：真人实战出口（话题建议）

**PRD 主张**：⭐⭐⭐⭐⭐，"闭环终点是真实沟通"。

**评审结论**：**最有产品灵魂、也最脆弱的一环**。三个断点：

1. **供给断裂**：用户可能根本没有真人对话对象。`83_` 的三级出口（系统内模拟 → 平台集成 → 真实场景）是正确兜底，但 Level 2 需商务谈判、Level 3 不可控——MVP 事实上只有 Level 1。
2. **数据诚实性断裂（最需警惕）**：B7 命中检测只工作在 **App 内对话**。真实会议/Slack 中的使用，系统无法被动检测；按 PRD §7.8，H3 是"打卡 + 可选自评顺畅度"——**实战转化率本质上是自报数据 + App 内练习代理数据**。这不丢人（健身 App 同理），但埋点口径必须诚实，否则数字骗自己。`83_` 中"Level 3 被动检测命中"的表述比 PRD 实际口径更乐观，应以本文档口径为准。
3. **门槛断裂**：≥20 个话术块才触发话题建议（§7.8 H1，服务端可配）。按调度规则（+24h 起步、连对 3 次转正），20 块最快也要数周，**而流失悬崖在 90 天**——出口开得太晚，用户来不及体验完整闭环。建议降低首次触发门槛（如 10 块）或设计一次"首周闭环体验"。

**当前实现**：H1-H3 全部待开发；**P1-2 命中回写缺失 → 该维度实际为 0%**。

### 3.4 总纲：数据飞轮（终极护城河）

PRD 主张"竞品可复制功能，无法复制数据厚度"。论点成立与否取决于三个条件：

| 条件 | 评估 |
|---|---|
| 数据不可移植、不可再创 | ✅ 成立（行为数据 + 个人语料确实抄不走） |
| 数据能反哺产品（卡壳地图 → 垂直小模型/内容调优） | ⚠️ 逻辑成立，未验证 |
| 先到规模（"几万程序员用户"） | ⚠️ 未达成 |

**推论**：在规模达成之前，飞轮是**战略叙事，不是防御工事**；豆包抄不走数据，但用户流失掉，数据也就不存在了。

## 六、本次执行：P1-2 命中回写详设

### 6.1 现状（代码事实）

- `internal/corpus/mysql_store.go` `RecordHits`：同一事务 UPSERT `phrase_block_uses` 账本，**仅在首次插入时** `total_uses + 1, last_used_at = ?`；
- `real_use_count` 列存在（0006）但**从未被写入**，只有读取与拷贝；
- 命中**不回写** `success_streak` / `next_due_at` —— PRD §5.3.2 "实战命中（B7）视同一次成功"未落地；
- `internal/corpus/memory_store.go` `RecordHits` 同形状（内存实现，测试与本地用）。

### 6.2 目标口径（PRD §5.2.3 回写行 + §5.3.2）

> 命中：`real_use_count +1`，且视同一次成功（`streak +1`、按 §5.3 重排）；未命中：不回写，不惩罚。

重排阶梯（§5.3.2）：成功且累计 <3 → `training`，+24h；累计 ≥3 → `automated`，+7d；已 `automated` 再命中 → 保持 `automated`，+30d。

### 6.3 实现设计

**关键约束**：调度阶梯目前实现在 `drill` 包（`ApplyJudge`），而 `drill` 依赖 `corpus`（`drill → corpus`），命中回写发生在 `corpus` 存储层事务内 —— **corpus 不能反向 import drill**（循环依赖）。

方案：**把调度阶梯下沉到 corpus，drill 保留同名薄委托**。

1. 新增 `internal/corpus/schedule.go`：`ApplyJudge(block, pass, now)`（实现自 `drill/scheduler.go` 平移，语义零变更）+ 阶梯常量；
2. `internal/drill/scheduler.go`：`ApplyJudge` 改为一行委托 `corpus.ApplyJudge`，drill 现有 API 与测试不受影响；
3. `internal/corpus/mysql_store.go` `RecordHits`：首次插入分支内，`SELECT state, success_streak, next_due_at ... FOR UPDATE`（按 `block_id` 排序处理，固定加锁顺序避免死锁）→ `ApplyJudge(block, true, usedAt)` → 单条 UPDATE 同时写 `total_uses+1, real_use_count+1, last_used_at, state, success_streak, next_due_at, updated_at`；
4. `internal/corpus/memory_store.go` `RecordHits`：同语义对齐（测试与本地环境一致）。

**时间锚点**：重排以命中检测时间 `DetectedAtMs`（`usedAt`）为基准，而非服务端 now —— 语义更真实，且重复上报幂等（同一 (session, turn, block) 只回写一次，由账本唯一键保证）。

### 6.4 已知取舍

- **`real_use_count` 与 `total_uses` 双写**：`total_uses` 是 48_ §2.6 REST 契约冻结的聚合列（0009 迁移新增），`real_use_count` 是 PRD §5.2.3 与 F2 UI（"用上过 N 次"）引用的列。本次在同一事务内双写，两列不会漂移；未来可评估合并（V1.1 清理项）。
- **历史数据**：本次改动前产生的命中行，`real_use_count` 保持 0（`total_uses` 已有值）。当前无生产用户，不做回填。

### 6.5 实施记录（2026-09-17 完成）

| 落点 | 变更 |
|---|---|
| `internal/corpus/schedule.go`（新增） | 调度阶梯 `ApplyJudge` 下沉至 corpus（drill 与命中回写共用） |
| `internal/drill/scheduler.go` | `ApplyJudge` 改为委托 `corpus.ApplyJudge`，drill API 不变 |
| `internal/corpus/mysql_store.go` | `RecordHits` 首次插入分支：`SELECT ... FOR UPDATE` → 阶梯重排 → 单条 UPDATE 写 `real_use_count/total_uses/last_used_at/state/success_streak/next_due_at/updated_at` |
| `internal/corpus/memory_store.go` | 同语义对齐 |
| `internal/corpus/hits_service.go` | 新增 `sortedHits`（固定加锁顺序，防并发死锁） |
| 测试 | `schedule_test.go`（阶梯）、mysql sqlmock 三例（常规/绿灯/块缺失）、memory 三例（首发/累计/幂等）+ 绿灯转正用例 |

验证：`go build ./...`、`go test ./...` 全绿；改动包 `gofumpt`/`goimports`/`golangci-lint` 干净。

### 6.6 验收标准

1. 命中首次上报后：`real_use_count +1`、`success_streak +1`、`next_due_at` 按成功规则推迟、`state` 按状态机流转（`new` → `training`）；
2. 同一 (session, turn, block) 重复上报：不回写第二次（幂等）；
3. 软删除块命中：不回写、不报错；
4. `automated` 块命中：保持 `automated`，`next_due_at = usedAt + 30d`；
5. 单元测试：`corpus` 新增/更新 sqlmock 用例 + memory store 用例；`drill` 既有测试全绿。

| `internal/reviewgen/failure.go`（新增） | `FailureKind` 八分类（invalid_request / empty_session / transport / empty_content / truncated_json / invalid_json / missing_fields / schema_violation）+ `GenerateError`（携带模型原文、HTTP body、finish_reason、全部未过规则） |
| 截断判定 | `finish_reason=length` 优先；其次 encoding/json 的 `unexpected end of JSON input`（载荷停在 token 中间） |

| `orchestrator.CompletionResponse` | 透出 `FinishReason` |
| `internal/session/review.go` | 空会话 INFO 且**不重试**；其余 WARN；两条路径都带 `failure_kind` / `raw_response` / `finish_reason` / `validation_rules` |

### 7.2 T4：救援事件作为炼化第二路输入（P1-1）

**问题**：炼化只吃转录，PRD §5.4.4 要求的救援事件序列缺失——沉默路径的卡壳点（用户一句话没说就被救援）在转录里没有任何用户文本可供锚定，全部丢失。

**链路（网关 → 落库 → 炼化）**：

| 落点 | 变更 |
|---|---|
| `migrations/0017_create_rescue_events.sql`（新增） | rescue_events 表：seq / turn_id / level / path / ladder_text / user_opened / anchor_text |
| `internal/voicegateway/rescue_log.go`（新增） | **卡壳事件按"一次卡壳"聚合**：同一梯子的 1→2→3 层是一个 episode（PRD §5.4.4 的"层数"），不是三条记录 |
| 网关锚点解析（PRD §5.2.2） | 未完成句路径：锚点＝那半句原文；沉默路径：锚点＝救援后用户开口第一句；始终未开口：锚点为空 → 不产话术块。文本取自客户端或服务端 ASR（复用 badge 的 `resolvedUserText`） |
| `internal/voicegateway/session_client.go` | `EndSessionRequest.RescueEvents` 随转录一并上报 |
| `internal/session` | 规范化（丢弃畸形事件但不影响会话收尾）→ 与转录同一事务落库 → `ListRescueEvents` |
| `internal/reviewgen` | `Request.StuckEvents` + userPrompt 渲染 + 系统提示写明两条路径的锚点规则与"不得伪造锚点" |

**已知边界**：关卡口（B13）开启且服务端 ASR 也为空时，沉默路径的锚点解析不到文本，该事件以"未开口"形态上报——不产块，但层数/路径仍进数据。这是锚点不可伪造原则的必然结果（§5.2.2）。

### 7.3 T5（后端部分）：E2 一键申诉闭环

**问题**：PRD §7.5 的 E2 是 P0，且被点名为"对主动召回训练的打击是毁灭性的"——闪测作答只有几秒，ASR 错误率天然高于长句，"说对了却被判失败"必须有出口。此前申诉完全未实现。

**口径（PRD §7.5 V1.7 定案，两件事分开）**：

| 面 | 处理 |
|---|---|
| 本轮结算 | **照实算**：`drill_records.semantic_pass` 保持判定结果，申诉不修改（否则申诉按钮会变成自我安慰按钮） |
| 该块进度 | **不因申诉被判失败**：按 `prev_*` 快照回滚——streak 不清零、状态不回退、`next_due_at` 回到原到期时间（"未做判定"，等下次正常复验） |

| 落点 | 变更 |
|---|---|
| `migrations/0018` | drill_records 增 `prev_state` / `prev_success_streak` / `prev_next_due_at` / `appealed_at` |
| `internal/drill` | 判定时写快照；`POST /api/v1/drill/appeal`；`JudgeResponse` 增 `record_id` 与 `asr_text`（E2 要求判定前展示识别文本） |
| 回滚护栏 | 只对**判定失败**且**快照存在**且**该块无更新的一次判定**的申诉回滚；三种拒绝各带一行 `note`，不静默 |
| 数据回流 | `drill_appeal_total` 指标 + `appealed_at`；申诉率即 ASR 质量信号（§14.3 行为数据） |

**E4 结算页**：后端已具备所需数据（判定结果、状态流转、streak），无需新接口。
### 7.4 T5（后端部分）：E3 调度参数服务端可配

**问题**：PRD §5.3.2 列的"服务端可配参数"此前全是编译期常量——调整阶梯要改代码重新部署；`每日新块释放上限` 未实现。

| 落点 | 变更 |
|---|---|
| `corpus.Schedule` | 阶梯结构体（转正次数 + 三档间隔 + 失败间隔）+ `Normalize`（零值落默认，不会把块排到"立刻到期"） |
| 单一来源 | **一条阶梯同时驱动两个写者**：`cmd/app-server` 用 `corpus.ScheduleFromConfig(cfg)` 构建一次，同时交给 corpus store（B7 命中回写）与 drill service；避免"命中与判定按不同规则转正"这类结构性错误 |
| `internal/config` | `DRILL_*` 七个环境变量 + 校验（负值→启动即失败；零值→文档默认；不可解析→回落默认） |

| 账本读取失败 | 记 warn 并按**不限**放行——记账故障不该把用户的闪测清空 |

**默认值**：转正 3 次、24h / 7d / 30d、失败 1h、单轮 10 题、每日新块不限——即当前线上行为，E3 是"可调"而非"改了行为"。

### 7.5 三条链路的 mock 全链路验证（cmd/smoke-moat）

**为什么用 mock 而不是真机**：三条链路（救援→炼化、命中回写、申诉）此前都是"代码完成、未在真实请求里跑过"。真机联调的瓶颈在设备与网络，而这里要回答的问题是"后端的路通不通"——用 mock iOS + mock 网关载荷走**真实 HTTP 路由、鉴权、存储、worker 循环**，只有两次 LLM 调用被打桩（否则每次结果不同，断言必然 flaky）。

```bash
go run ./cmd/smoke-moat          # 内存存储；MYSQL_DSN 存在时走 MySQL
```

| 链路 | 断言 |
|---|---|
| 救援 → 炼化 | 生成器收到 2 条 stuck event（incomplete 带半句锚点 / silent 锚点为空）；refine 卡锚定在救援锚点上；batch-accept 入库 |
| 实战命中回写 | `real_use_count` +1、`success_streak` +1；同一 (session, turn, block) 重复上报不双计 |
| 闪测 → 申诉 | 到期块进 round；判定通过推进阶梯；失败清零 streak；申诉恢复到失败前的 streak 与**原到期时间** |
