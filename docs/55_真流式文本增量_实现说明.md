# 真流式：`ai.text.delta` 变成真增量

**日期**：2026-09-11
**状态**：**文本半边已实现**。音频半边未做，见 §7 —— 它是 P1-2 里更大的那一半。
**对应**：meta `77_` **P1-2** · 执行计划**步 8**

## 1. 问题

`collectTurn` 是**阻塞累积器**：供应商把文本和音频流进它，调用方要等**整轮结束**才拿到结果。

而 `turnToOutbound` 在 `collectTurn` 返回**之后**才跑，发出的顺序是：

```
client.asr.transcription
ai.turn.end          ← 先
ai.text.delta        ← 后，且携带**整段回复**
```

日志里的 `ai.turn.end` 早于 `ai.text.delta`，就是这个结构直接产生的。

## 2. 消费者契约：iOS 早就在追加

改生产者之前先查了消费者。`SpeakingRoomFeature` 的 reducer：

```swift
case let .aiTurnTextDelta(text, turnID):
    if var last = state.timeline.last,
       last.speaker == .ai, last.status != .finalized {
        last.text += delta            // ← 追加
    } else {
        state.timeline.append(TurnTimelineItem(..., status: .streaming))
    }
```

**iOS 侧一行都不用改。** 它本来就是按真增量写的，并且会为第一段建一个 `.streaming` 项、等 `ai.turn.end` 来 finalize —— 生产者却从没发过增量。

### 顺带发现：今天这条链路是自相矛盾的

按旧的顺序推一遍 iOS 的状态机：

1. `ai.turn.end` 到达 → `aiTurnFinalized` → 最后一项是**用户**的，不是 `.ai` → **空操作**
2. `ai.text.delta`（全文）到达 → 新建一个 AI 项，状态 `.streaming`
3. 不会再有第二个 `ai.turn.end` —— 它**永远停在 `.streaming`**

**当前 `.streaming` 没有被任何视图读取**（全仓确认只有 reducer 里的赋值和 `!= .finalized` 判断），所以这不是一个可见缺陷，是一条**潜伏的契约违背**。流式顺序（增量在前、`ai.turn.end` 在后）把它一并修好了。

## 3. 缝：两个接口各自加一层

流式的前提是**能中途推送**，而 `HandleClientControl` 的形状是"返回一个切片"。所以加了两处，都是**可选**的：

### `voicepoc.TurnSink`

```go
type TurnSink interface {
    AssistantTextDelta(delta string)
}

func (s *DuplexSession) SetTurnSink(sink TurnSink)
```

`collectTurn` 在 `response.output_text.delta` 分支里**既累积也转发**：

```go
text.WriteString(evt.Delta)          // TurnResult.AssistantText 仍是整段
if s.turnSink != nil {
    streamed.WriteString(evt.Delta)
    s.turnSink.AssistantTextDelta(evt.Delta)
}
```

**累积不能省**：`AssistantText` 是这一轮被记录下来、要持久化的东西，流式不能把它变成碎片。

### `voicegateway.StreamingVoiceProviderSession`

```go
type StreamingVoiceProviderSession interface {
    VoiceProviderSession
    SetOutboundEmitter(emit func(ProviderOutbound) error)
}
```

provider 实现它；handler 在**每一处 `rt.provider` 被赋值的地方**调用 `attachOutboundEmitter`（初次 Open 与透明 reopen 各一处）。

### 并发：没有引入新的写者

`collectTurn` 的读循环跑在**调用方 goroutine** 上（只有 `sendSilence` 是 spawn 出来的），emitter 又是同步调用。所以推送与 handler 写出仍在**同一个 goroutine** 上串行 —— 网关的写路径本来就是这么串行的。这条写进了接口注释：实现**不得**从自己 spawn 的 goroutine 里调用 emitter。

## 4. 核心不变量：抑制帧，不抑制记录

回复已经以增量发出后，轮末**不能再发一遍全文** —— iOS 是追加，重复会显示两遍。所以 `turnToOutbound` 里：

```go
if !s.streamedText {
    outbound = append(outbound, ProviderOutbound{Control: voiceproto.NewAITextDelta(reply, ...)})
}
s.utterances = append(s.utterances, EndUtterance{Speaker: "ai", Text: reply})   // ← 照记
```

**`streamedText` 的清除点放在轮次*开始*（`user.speech.start`），不只是轮末。** 原因是有一个漏法：中途 `abort` 的轮次**永远不会走到 `turnToOutbound`**，标志会留到下一轮，把那一轮的回复**整段吞掉**。放在轮首清除，这个漏法就不存在。（`abort` 分支也清一次，是冗余的防御。）

**没有 emitter 时绝不置位。** 判断在置位**之前**：

```go
if delta == "" || s.emit == nil { return }
s.streamedText = true
```

反过来的话，一个不支持流式的网关会得到"抑制了轮末全文、却无处可推"的会话 —— **客户端一个字都收不到**。这是本次改动最需要避免的失败模式，有专门的测试钉住。

## 5. 一个记录在案的取舍：`done` 文本与增量不一致

`response.output_text.done` 携带**权威全文**，厂商**没有义务**让它等于增量的拼接。若两者不同，客户端已经显示了增量，而服务端将记录 `done` 的文本 —— **屏幕上看到的和回顾里存下的会是两段不同的文字**。

**没有修正**：协议里没有"替换已流式文本"的帧，加一个属于协议变更，不在本票。

**但也没有让它无声通过**：不一致时打一条 warn（两边长度）。同时用一条测试把这个行为**钉成决定而不是意外**：客户端拿到的是增量，`AssistantText` 是 `done`。

## 6. 没做的一件事：ASR 转录仍然不流式

`client.asr.transcription` 留在 `HandleClientControl` 的返回切片里，**没有**挪去流式。

原因是硬的：handler 靠扫描**返回的切片**里的 `ServerASRText` 做 badge 检测（`extractServerASRText`）。把它挪走，badge 就断了。

代价是一个顺序变化：现在助手文本的增量会**先于** `client.asr.transcription` 到达 iOS。已核对 iOS 的 reducer —— `aiTurnTextDelta` 无条件追加、不依赖相位，`serverASRReceived` 负责推进相位机与 `liveTranscript`，两者不冲突。**但这属于真机验证项**。

## 7. 本票只做了文本：音频那半边更大

**这是本次排查最重要的发现，P1-2 原本没写。**

音频同样是**攒完整轮才发**的。`turnToOutbound` 里：

```go
if pcm := resampleToPlaybackRate(turn.AudioPCM); len(pcm) > 0 {
    for offset := 0; offset < len(pcm); offset += audioFrameBytes { ... }
}
```

整轮音频一次性重采样、切帧；注释还写着 "The assistant's voice, **last** so it follows ai.turn.end"。

**后果**：用户要等到整轮（ASR + LLM + **全部 TTS**）生成完毕，才听到**第一个音节**。对一个"说"的应用，这比文本顺序的延迟大得多 —— 文本先流式让字幕好看了，但 AI **并没有更早开口**。

### 为什么没顺手做掉

流式音频需要一个**带状态的重采样器**。现在的 `resampleToPlaybackRate` 是**无状态**的线性插值，输出位置由绝对下标算出（3:2）：

```go
pos := float64(i) * float64(inSamples) / float64(outSamples)
```

**逐块独立重采样是错的**：块边界不对齐到 3:2，每个边界都会引入相位漂移与爆音。正确做法是跨块保留相位、并扣住最后一个样本等下一块。

它有一个**可证明的正确性判据**，也就因此有测试：

> **分块重采样的输出，必须逐字节等于把同样数据整段重采样的输出。**

这条等式一旦钉住，流式音频就是可证非回归的。但它是一块独立的 DSP 记账工作，与文本的顺序修复不是一件事 —— 混在一起做，会让"文本增量"这个已经可验收的改动被一块新的数值代码拖住。

**记录，单独做。** 见 meta `77_` 的 P1-2 拆分。
