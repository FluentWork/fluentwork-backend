# 护城河机制：定义审计与重构建议

**文档版本**: V1.0
**创建日期**: 2026-09-18
**状态**: 审计完成，待产品决策后执行
**依据**: PRD §5.2/§5.3/§5.4/§14.3、`83_护城河核心机制产品审视`、`84_护城河评审_壁垒重估与任务拆分`、当前代码实现

---

## 一、为什么要重写定义

三根支柱（闪测 / 语料库 / 实战出口）**代码层面都已建成**：调度、状态机、申诉、参数化、债务衰减、三元组、命中回写、推荐、质量回流、话题卡、打卡、转化率统计——`84_` 的 T1–T11 后端全部落地。

但建成 ≠ 成立。当前的问题是：**支柱之间的因果链没有被定义成可测量、可证伪的东西**。

- 我们说"闪测让表达内化"，但**判定是否准确**没有任何基线，而判定是整条链路唯一的真值来源；
- 我们说"语料库越厚迁移成本越高"，但**没有任何指标度量"厚"**；
- 我们说"推出去和真人聊"，但系统**看不到真实会议**，于是把"自报打卡"和"App 内命中"两个性质不同的量并列成"转化率"；
- 我们说"数据飞轮"，但**没有一条从数据回到产品的回路定义**：谁读、读什么、多久读一次、产出什么、怎么知道它有效。

本文档把每条机制的**承诺 → 可测信号 → 当前实现 → 定义缺口**摊开，给出建议定义与任务拆分。缺口编号 M1–M12，任务编号 N1–N7。

---

## 二、支柱一：闪测（间隔重复 + 主动召回）

| 项 | 内容 |
|---|---|
| **给用户的承诺** | 你练过的表达，会在你快忘的时候被考；答对 3 次就是脱口而出 |
| **应有的可测信号** | 首次闪测完成率、灰→黄→绿转化率、绿灯块的实战命中率、判定准确率 |
| **当前实现** | 固定阶梯（24h/7d/30d/1h，E3 可配）、三态状态机、E2 申诉与快照回滚、债务衰减（`DRILL_OVERDUE_WINDOW`）、转正标记 |

### M1【判定标准不可执行】🔴 最高优先

`internal/drill/judge.go:22` 的 `JudgePrompt` 全文只有一句 "Decide if the learner's utterance is **semantically equivalent** to the target phrase"。没有 rubric、没有边界例、没有金标集。

**为什么这是最大的洞**：闪测的 pass/fail 是**整条链路唯一的真值来源**——它决定 streak、决定状态灯、决定"已自动化"、决定话题卡的块清单、决定实战转化率的分母。判定错 10%，后面所有指标就错 10%，而且是**静默**错。这也解释了为什么 E2 申诉很重要（它是唯一的人工纠偏通道），但申诉率本身不该是主要防线。

**建议定义**：
1. **rubric 三档**：`pass`（语义等价）/ `pass_with_note`（等价但更地道的说法存在）/ `fail`（语义偏移、信息缺失、或无法理解）。当前二值 `pass` 保留对外语义，`pass_with_note` 只用于数据回流（它标记"这个块还有更好的说法"）。
2. **边界例清单**：同义改写、时态差异、省略主语、filler 词（uh/you know）、部分失败（说对一半）、母语直译。
3. **金标集**：人工标注 ≥100 条边界样本，作为判定质量的回归基线（与 B15 的 schema 回归并列，但对象是**判定**而非格式）。
4. **上线门槛**：金标集准确率 ≥95% 才允许调 prompt/换模型；否则"改判定"就是无据可依。

### M2【学习与复习同形】

`drill_records` 只有 `semantic_pass` + `response_ms`。一次就过 vs 第三次才过，在数据里同形——但"这个词我第一次就会"和"我卡了三次才记住"是完全不同的资产。

**建议定义**：卡壳地图的最小单元是 **streak 重置次数**，而非失败次数。E2 已写入 `prev_success_streak` 快照，可直接复用为口径：一次"卡壳事件" = `semantic_pass=false AND prev_success_streak > 0`（练过又忘了）；`prev_success_streak = 0` 的失败属于"新块没学会"。两者对内容的含义完全不同（前者是复习间隔问题，后者是难度/素材问题）。

### M3【间隔不随表现调整】

固定阶梯是 MVP 的明确决定（PRD §5.5），`ease_factor` 预留未启用。定义缺口不是"要不要 SM-2"，而是**"什么时候该启用"的判据**。

**建议定义**（写下来，等数据）：若 `+24h` 首复验的 pass 率 > 85% 且 `response_ms` 中位数 < 1.5s，说明间隔过密（用户在背已经会了的东西）；若 `+7d` 复验失败率 > 40%，说明转正过早。两个判据都可用现有字段算出，无需新埋点。

### M4【卡壳地图没有 schema】

PRD §14.3 说数据飞轮的核心是"竞品抄不走的数据厚度"，具体指"哪些技术概念上反复卡壳"。但"卡壳"目前散落在三处：`drill_records(pass=false)`、`rescue_events(path, level, anchor)`、`phrase_blocks(function_tag)`，**没有统一口径**。

**建议定义**：一张只读聚合视图（内部运营用，不对外）：

```
卡壳视图(user, function_tag) = {
  失败次数, 其中"练过又忘"次数(M2 口径), 触发救援次数,
  平均转正所需判定次数, 最后一次卡壳时间
}
```

它的用途是**内容与难度的迭代依据**：哪类意图（function_tag）系统性难？哪些场景（scene_tag）的块永远练不绿？——这才是"垂直领域数据飞轮"的最小可用形态。

## 三、支柱二：语料库（话术块三元组）

| 项 | 内容 |
|---|---|
| **给用户的承诺** | 你说过的每句话，被提炼成可复用表达，按场景分类 |
| **应有的可测信号** | 一键入库率、语料库周活跃率、负反馈率、跨会话复用率 |
| **当前实现** | 三元组 CRUD、状态灯、标签、批量入库、命中回写、场景推荐、质量反馈（T10） |

### M5【跨会话不去重】

`migrations/0006` 的唯一键是 `(user_id, source_session_id, expression_en, anchor_user_said, scene_tag, function_tag)`——**含 `source_session_id`**。同一句表达在不同会话里会生成**不同的块**。

对"资产"叙事这是直接伤害：用户练了三周，"汇报进度"这个意图下可能躺着 5 个近似块，检索、闪测、话题卡的块清单都被稀释。

**建议定义**（需产品决策，见 §六）：入库时按 `expression_en` 归一化（小写、去标点、去尾句号）做**近义判定**：
- **方案 A（自动合并）**：命中已有块 → 不新建，追加锚点/场景标签，`real_use_count` 保留；
- **方案 B（用户确认）**：命中的卡在入库页提示"这句你已经有了，合并 / 仍然新建？"
- 建议 A 为默认 + 保留"仍然新建"入口；纯 B 会把决策负担推给用户。

### M6【块没有版本】

用户编辑 `expression_en` 之后，历史 `drill_records`、命中记录、反馈指向的语义已经变了，但数据里没有任何边界。

**建议定义**：块级 `version`（编辑即 +1）或至少记录 `edited_at` 事件；所有统计口径（转化率、命中率）**按版本分段**计算——否则"这个块命中过 3 次"可能是三个不同句子的成绩。

### M7【"地道度"没有验收标准】

PRD §5.2 对"地道版"只有三个字。T10 的负反馈是**事后**信号，生成侧没有任何可执行的验收。

**建议定义**：把 T10 的负反馈率定为炼化质量的**唯一硬指标**（目标 <10%，见 `83_`）：
- 可接受下限（任一成立即失败）：改变原意 / 语法错误 / 比原句更长 / 含生僻表达；
- 每个 prompt 变更必须附前后负反馈率对比，否则视为未验证。

### M8【迁移成本不可度量】

我们对外说"迁移成本是护城河"，但没有任何指标度量它。

**建议定义**：**资产厚度** = 块数 × 跨会话复用率 × 命中率。三个因子缺一不可——只有块数会奖励"堆垃圾"，只有命中率会忽略规模。放进 T8 的 stats，作为内部北极星辅助指标。

## 四、支柱三：实战出口（话题建议 → 真人）

| 项 | 内容 |
|---|---|
| **给用户的承诺** | 练够了，系统推荐真实场景话题，把练的用上 |
| **应有的可测信号** | 话题触发率、点击率、打卡率、实战转化率 |
| **当前实现** | H1 阈值门槛、H2 落地校验 + 来源标注、可调用话术块清单、H3 打卡 + streak、T8 转化率统计 |

### M9【"实战"是代理量，且没有标注】

系统能看到的只有两件事：**App 内命中**（B7 的 token 重叠检测）和**自报打卡**。真实会议里的使用，服务端看不见。但 T8 的 `conversion_rate`（绿灯块中命中过的比例）与 `checkin_rate`（打卡/卡数）被并列呈现，两者性质不同却看起来同级。

**建议定义**：三级可观测性，所有对外数字标注级别：
- **L1 事实**：App 内命中（检测器判定，可复核）；
- **L2 自报**：打卡、自评（用户陈述，不可验证）；
- **L3 不可观测**：真实会议中的使用——只能由用户在打卡时复述（见 M10）。

对外文案与内部看板都必须写清级别，**不把 L2 说成 L1**。

### M10【打卡不回连到块】★

`CheckinRequest` 只有 `reflection`（`internal/topic/model.go:105`）。打卡时说一句"我用上了哪几句"，转化率就**从代理变成用户确认的事实**，还能反哺 `real_use_count`（比 App 内命中更接近实战）。

**建议定义**：打卡 body 增加可选 `used_block_ids []string`（卡片已经带 `blocks` 清单，客户端勾选即可）。口径：
- 勾选的块 → `real_use_count + 1`（与 B7 命中同权，但来源标记不同：`source=checkin` vs `source=b7`）；
- 未勾选不惩罚（与 PRD §5.2.3 "未用不产生负反馈"一致）；
- 转化率分母仍是绿灯块数，分子变为"L1 命中 ∪ L2 用户确认"，**并在响应里分开返回两个数**。

### M11【没有"没聊成"的路径】

话题卡 → 无行动的原因完全未采集：找不到人？不敢说？没时间？这决定下一步该投入什么（系统内模拟 vs 帮用户找人 vs 降低门槛）。而 `83_` 的 Level 1（系统内模拟）正是为此准备的。

**建议定义**：卡片上的轻量选择："这次没聊成，因为…" → `no_partner` / `not_confident` / `no_time` / `not_relevant`。四选一即可，用于决定投入方向。

## 五、总纲：数据飞轮的回流定义

PRD §14.3 的终极护城河是"结构化的用户行为数据"。但当前**没有任何一条从数据回到产品的回路定义**——谁读、读什么、多久、产出什么、怎么知道有效。

**建议定义（月度回流节拍）**：

| 输入 | 产出 | 验证方式 |
|---|---|---|
| 卡壳视图（M4）按 function_tag 排序 | prompt / 内容补充清单：系统性难的意图优先补素材 | 下月该类意图的转正判定次数下降 |
| 炼化负反馈率（M7） | 改写规则修订 | 修订前后负反馈率对比 |
| 判定金标集准确率（M1） | 判定 prompt / 模型调整 | 金标集准确率不下降 |
| 实战转化率分来源（M10） | 决定实战出口的投入方向 | 打卡率与 L2 确认率变化 |

**关键纪律**：每次修订必须记录**前后指标**。没有前后对比的"优化"无法证明飞轮在转，只会积累不可验证的改动。

## 六、需要产品决策的四点

1. **M5 近义块合并**：自动合并（默认）+ 保留新建入口，还是每次询问？（影响入库体验与资产质量）
2. **M10 打卡带块**：多一步勾选换取"事实级"转化率，是否接受交互成本？
3. **M3 自适应间隔**：V1.1 是否启用；启用判据用 §M3 提出的两条阈值吗？
4. **M1 金标集**：谁标注（团队内部 / 外包）、100 条是否够、判定准确率门槛定在 95% 是否合适？

## 七、任务拆分（按最小可验证闭环排序）

| # | 任务 | 对应缺口 | 产出 | 依赖 |
|---|---|---|---|---|
| **N1** | 判定 rubric + 金标集 + 准确率基线 | M1 | rubric 文档、≥100 条标注样本、`judge_accuracy` 回归 | 产品决策 4 |
| **N2** | 打卡带块（`used_block_ids`） | M10 | 事实级转化率、来源分列 | 产品决策 2 |
| **N3** | 卡壳视图聚合查询 + 内部端点 | M4、M2 | 按 function_tag 的卡壳地图 | 无 |
| **N4** | 块版本 / 编辑事件 | M6 | 统计口径按版本分段 | 无 |
| **N5** | 近义块合并 | M5 | 入库去重 | 产品决策 1 |
| **N6** | "没聊成"原因采集 | M11 | 四选一埋点 | 无 |
| **N7** | 月度回流机制（脚本 + 修订记录表） | M12、M8 | 回流报表 + 修订前后指标 | N1/N3 |

**排序理由**：N1 最先——判定是唯一真值来源，它的准确率决定了后面所有指标是否可信；N2/N3 紧随——一个把代理变成事实，一个把散落数据变成地图，都是"小改动、大信息量"。

## 八、与既有文档的关系

- `83_` 给出的是**风险与实验设计**（哪些环节会失效）；
- `84_` 给出的是**壁垒强度重估与执行拆分**（哪些环节值得投入，已执行完 T1–T11）；
- 本文档给出的是**机制的定义审计**：承诺 ↔ 可测信号 ↔ 实现 三者对齐，缺口编号 M1–M12、任务 N1–N7。

三者不冲突：`83_` 说"闪测节奏可能压垮用户"（体验风险），`84_` 说"实战出口是 0% 的维度"（投资排序），本文说"判定的准确率没有基线"（定义缺失）。
