# 上游断开后的会话恢复

**对应**：真机火山日志回溯（session `b3436904`，2026-09-10 22:20）。复现用户报告「三次以上必挂，无法继续」。  
**代码**：`internal/voicepoc/volc_duplex.go`（`ErrDuplexClosed`）· `internal/voicegateway/provider_volc_duplex.go`（`resetAfterTurnReadFailure`）· `internal/voicegateway/handler.go`（reopen 预算按轮复位）  
**门禁**：`./scripts/dev-check.sh` → All checks passed；`go test ./...` 23 包全绿

## 原理与背景

**上游死掉时,要在「发现死亡的那一刻」修,而不是留给下一次写入去撞。** 并且**恢复预算按轮给,不按会话给**。

## 缺口根因

### 一、`collectTurn` 读到断连后把尸体留在原地

`collectTurn` 的读失败分支只标注 outcome 就返回,不通知任何人连接已死。于是：

```
turn-N  collect 读失败 → outcome=error，duplex 保持死状
        ↓（下一轮第一次音频写）
HandleClientAudio 失败 → 花掉唯一的 reopen 预算
        ↓（再下一轮）
reopen_attempted=true → 会话结束
```

真机时序（session `b3436904`）：

```
22:20:04.226  provider reopened after audio forward failure        ← reopen 用掉
22:20:08.456  collect_turn.done turn-2  outcome=partial, duration_ms=1096
22:20:16.972  user.speech.start                                     ← turn-3
22:20:17.068  provider audio forward failed; reopen_attempted=true  ← 致命
```

### 二、`reopenAttempted` 是会话级的一次性开关

```go
// 旧实现（handler.go）
if !rt.reopenAttempted {
    rt.reopenAttempted = true
    ... 重开 ...
}
```

置位后**整场会话再没有第二次**。而实测 volc-duplex 的 duplex **大约每轮掉一次**（两份真机日志里 turn-1/turn-2 的 `collect_turn.done` 都带着非 ok outcome）。一次预算对上每轮一次的故障率,结果就是**第三轮必死**——与用户报告完全一致。

## 方案

### A. 在发现点重置 duplex

`voicepoc` 新增 sentinel，把「传输断」与「供应商 error 事件」分开：

```go
var ErrDuplexClosed = errors.New("duplex connection closed")
```

`collectTurn` 的读失败分支改为 `fmt.Errorf("%w: %w", ErrDuplexClosed, err)`。

`provider_volc_duplex.go` 在 `user.speech.end` 拿到 turn 结果后：

```go
if errors.Is(err, voicepoc.ErrDuplexClosed) {
    s.resetAfterTurnReadFailure(ctx)   // 复用 abort 的 resetDuplex
}
```

**为什么必须区分**：供应商发 `{"type":"error"}` 事件时连接还活着,而 `resetDuplex` 会**开一条新的 Volc 会话**,服务端保存的对话上下文全部丢失（AI 会忘掉前几轮）。所以只对真正的 socket 死亡重置,不按 outcome 一刀切。

重置失败不算致命：下一次音频写仍会走 handler 的 reopen 路径,退化成今天的行为而不会更糟。

### B. reopen 预算按轮复位

`user.speech.start` 到达时清 `rt.reopenAttempted`：

```go
if frameType == voiceproto.TypeUserSpeechStart && rt.reopenAttempted {
    rt.reopenAttempted = false
    ...
}
```

语义从「这**条会话**只许透明重开一次」变成「这**一轮**只许透明重开一次」。仍有硬上界（每轮至多一次,不循环）,但不再因为一次抖动就永久失去恢复能力。

## 新方案理由

- **不把 reopen 改成计数器**：计数器要拍一个魔法数,而且同样解决不了「尸体没人收」。按轮复位有明确语义——新一轮是新的开始。
- **不在 `HandleClientAudio` 里顺手重置**：那里只知道「写失败」,不知道失败的是哪一轮;而且它正是要省下预算的那条路径。
- **不改 `client.turn.abort` 已有的 reset**：那条路径本来是对的,本票只是让读失败这条对齐它。
- **不加新的 WSS 帧、不改任何 schema**：纯网关内部行为。

## 影响面

- **协议**：零改动。
- **成本**：重置会新开一条 Volc 会话。按轮上限一次,轮数是自然上界。
- **上下文**：只有真正的 socket 死亡才重置——那种情况下 Volc 侧的上下文本来就已经没了,不构成额外损失。
- **观测**：新增 `duplex reset after turn read failure`（Info）与 `reopen budget refilled for the new turn`（Info）,便于统计真实的重置频率。

## 未证实：上游为什么会关

**本票没有回答这个问题。** 两份日志能证明的只是「关掉之后我们处理得不好」。

一条待验线索：turn-2 的事件序列里 `input_audio_buffer.committed`（**我们** commit 的回执）排在 10 个 `transcription.delta` **之后**,说明 Volc 在我们 commit 之前已经在自己转录了——因为客户端在持续 append PCM（iOS 侧 `docs/40` 修的 bug）。服务端与客户端各跑一套轮次边界。若 P0-1 修复后上游不再掉线,则本条成立；若仍掉,下一个嫌疑是 `collectTurn` 期间每 20ms 一次的 `sendSilence` 与供应商正在推送的 `response.output_audio` 相互干扰。
