## 一、结论先行

**不是"写得乱"，是"加出来的一堆补丁缺少一个主结构"。**

代码质量本身在线：208 个 handler 测试、v1 schema 冻结、时钟可注入、写锁有上界——这些都是
被真机问题一课一课教出来的，不是随手写的。问题在**结构**：

| 判断 | 依据 |
|---|---|
| ❌ **turn 的生命周期没有唯一所有者** | 它被拆在 3 个 goroutine、5 个文件、约 12 个状态字段里 |
| ❌ **同一件事存在两个实现/两份常量** | 二进制帧编码 ×2、帧大小常量 ×2、PCM 块常量 ×4、文本解析 ×2 |
| ❌ **调用点自己长出了一套策略** | `handleControl` 的 279 行里，同一件事（provider 调用失败怎么办）有 4 种不同处理 |
| ⚠️ **生产语音链路的传输层，包名叫 `poc`** | 3.4k 行，且里面混着 WER 测量、注入窗口 PoC 等与生产无关的东西 |
| ✅ **测试不是问题** | 208 测试、schema 冻结、真 handler 驱动的契约测试都在。测试是这次的**主要信息来源**，不是被审对象 |

**复杂度不在算法，在接缝**：每一处都是某个真机 bug 的最小修法，单独看都对；
合起来就成了"想知道一个 turn 现在处于什么状态，得读五个地方"。

按你说的从 tests 开始。它们比注释诚实：

## 三、主要发现

### F1【高】turn 的生命周期没有唯一所有者

一个 turn 从 `user.speech.end` 到 `ai.turn.end`，状态散在：

| 位置 | 承担什么 |
|---|---|
| `handler.go:635` `handleControl`（279 行） | 帧分发 + 会话生命周期 + provider 转发 + 4 种错误策略 |
| `handler.go:921` `startCollectTurn` | 另起 goroutine，重复 unmarshal，做 ASR 校验/badge/救援锚点 |
| `provider_volc_duplex.go` `turnStarted` / `activeTurnID` / `resetTurnStreamingState` | provider 自己也在记 turn |
| `voicepoc/volc_duplex.go:510` `collectTurn`（**252 行**） | 又一套 turn 收集 + outcome 判定 |
| `sessionRuntime`：**30 个字段**，其中 **12 个带 `B8:` 前缀** | 救援子系统把字段铺满了整个 runtime |

**为什么这是问题**：出现时序 bug 时，没有一处能回答"这个 turn 现在是什么状态"。
今天我自己就在梯子音频那次踩到同形的问题（梯子音频被喂回救援状态机 → rung 永远停在 level 1），
根因就是"谁在改 turn 状态"没有边界。

### F2【高】`startCollectTurn` 把同一份 JSON 解了 3 次，同一段逻辑写了 2 遍

`handler.go:921-992`，同一个 `data []byte`：

```go
// 1) clientASRRequired 分支：json.Unmarshal(data, &end)   ← 为了拿 Text
// 2) badgeEmitter 分支：   json.Unmarshal(data, &end)     ← 又为了拿 Text/TurnID
// 3) rt.noteUserUtteranceText(resolvedUserText(data, outbound))  ← 再解一次
```

而"先取客户端 text、为空则退回服务端 ASR"这条规则**写了两遍**：

- `handler.go:976-981`（badge 分支内联）
- `handler.go:1058` `resolvedUserText`

两者现在恰好一致，但**没有任何测试钉住它们一致**。改一处不改另一处 → badge 与救援锚点
用不同的文本，且症状是"锚点偶尔不对"，极难查。

### F3【高】turn id 有 3 套取值规则、2 处重复实现，没有单一权威

| 位置 | 取值 |
|---|---|
| `handler.go:975-981` | `end.TurnID`，空 → `session.SessionID`（badge 分支内联） |
| `handler_rescue.go:460-463` | `rt.rescueTurnID`，空 → `session.SessionID`（**再写一遍**） |
| `provider_volc_duplex.go:444` | `end.TurnID` → `s.activeTurnID` |
| `provider_volc_duplex.go:201 / 235 / 334 / 830` | `canonicalTurnID(activeTurnID, nextSeq)` ← **完全不同的回落**（按音频序号造一个） |
| `provider_volc_duplex.go:401` | 字面量 `"bootstrap"`（会话首帧） |

回落规则**共两处实现**（`= session.SessionID` 两遍），加上 provider 侧按序号造 id 的第三套规则
与一个 `"bootstrap"` 字面量。结果：同一会话里可能出现 `session_id`、`turn-N`、
序号造出来的 id 三种形态。
iOS 侧要按 turn id 区分来源（梯子 vs 对话），**而 turn id 本身在这里就不唯一**。

### F4【高】二进制帧编码有两个实现

| 实现 | 用在哪 | 错误处理 |
|---|---|---|
| `voiceproto.AITTSAudio.Encode()`（`frames.go:195`） | dev-echo、梯子音频 | 返回 error，空 payload 拒绝 |
| `voicegateway.encodeAudioFrame()`（`provider_volc_duplex.go:998`） | **真机 AI 语音**（唯一上生产的那条） | 无 error，直接拼 |

两者都是"4 字节大端 seq + payload"，**但没有任何测试或类型让它们保证一致**（`frames_test.go` 只测前者）。
`audioFrameHeaderBytes = 4` 与 `Encode` 里的魔数 `4` 也是两份。

### F5【中】帧大小常量有 4 个，语义不同却长得一样

| 常量 | 值 | 含义 |
|---|---|---|
| `provider_volc_duplex.go:990` `audioFrameBytes` | 3200 | **出**：100ms @16k 单声道 |
| `rescue_orchestrator.go:117` `RescueAudioFrameBytes` | 3200 | **出**：同上，另起一个名字 |
| `voicepoc/volc_duplex.go:27` `pcm16kChunkBytes` | 640 | **入**：20ms 上行 |
| `provider_dev_echo.go:106` `devEchoChunkBytes` | 640 | 同 640，另起一个名字 |

3200 与 640 都**没有注释说明它们与采样率的关系**。`handler_rescue.go:204` 甚至写成
`RescueAudioFrameBytes * time.Millisecond / 32`——`32` 是"每毫秒 32 字节"的隐式知识，
一旦采样率变（或换成 24k），这个表达式就错了而没人会注意到。

### F6【中】`handleControl` 的 279 行里藏着 4 种错误策略

同一个"provider 调用失败"：

| 分支 | 策略 |
|---|---|
| `user.speech.start` 转发失败 | 发 `provider_control_failed` |
| `client.turn.abort` 转发失败 | **故意不发**（注释：iOS 会当 .failed 杀掉会话） |
| `interrupt` 转发失败 | 发 `provider_interrupt_failed` |
| `startCollectTurn` 里转发失败 | 发 `provider_control_failed`（但已在 goroutine 里） |

**四种策略各有理由，都写对了**——但它们没有共享任何结构，没有一处能看出"这个决定需要逐个 case 判断"。
加上 `!rt.started || rt.provider == nil` 的守卫在每个 case 重复，任何新帧类型都要重新推导一遍。

### F7【中】生产语音链路的传输层住在名为 `poc` 的包里

`internal/voicepoc`（3.4k 行）：

- `voicegateway` 通过它 `OpenDuplex` / `DuplexSession` / `TurnOutcome` —— **生产路径**
- 同包还有：WER 测量（`wer*.go` 441 行）、注入窗口 PoC（`window.go` 186 行）、
  `mock_provider.go`、`meta12.go` —— 与生产无关
- 包注释**一行都没有**（`package voicepoc` 直接开始）
- `defaultDuplexVoice = "zh_female_vv_jupiter_bigtts"` —— 今天确认这个 speaker 在本账号下**合成不出声**
  （`seed-tts-2.0` 只服务 `_uranus_bigtts`），即这个默认值已经和现实脱节
  - **【已推翻，2026-09-18 晚】** 这条结论是错的，别照 A7 去"修"它。核实结果：
    duplex 半边服务的是 **1.0 世代**说话人，而 text-TTS 半边（`content/tts`）服务 2.0 世代
    并拒收这个值——**两者是不同产品、不同音色目录**，所以它"看起来和 `content/tts` 的默认值
    不一致"是对的。现在的代码注释把这件事写在了值旁边（`internal/voiceduplex/volc_duplex.go`）。
    当时的误判来自一个真实现象（合成不出声）配了一个错的因果

**命名即文档**：一个叫 poc 的包出现在生产调用链上，下一个读代码的人会低估它。

### F8【低】注释与实现的漂移（今天已修两处，这是第三处）

`provider_volc_duplex.go:1030-1036` 有一段**没有挂到任何函数上的注释**：

```
// Deliberately plain, and there is no anti-alias filter ahead of the decimation …
// … If quality becomes a complaint, replace this with a polyphase filter
```

它描述的是重采样实现，但紧跟着的是 `resampleToPlaybackRate` 自己的文档注释。
读者会以为 `resampleToPlaybackRate` 就是那个"故意不滤波"的实现——实际滤波策略在
`pcm_resampler.go`。**悬空注释比没有注释更坏**。

### F9【低】`voicepoc` 里只有 1 个导出函数在生产被用到

`WaitTurnResult` 是唯一的生产调用（2 处）。`SendUserPCMAndWait`、`SendUserPCMInject*`、
`RunWER`、`MockProvider`、`InjectScore` 的生产调用数**都是 0**——它们服务于
`cmd/poc-injection-window`、`cmd/asr-wer`、`cmd/smoke-volc-realtime` 三个 PoC/工具。

不是死代码（工具要用），但**它们和生产代码混在一个包里**，使"这个包在生产路径上吗"
这个问题无法从包边界回答。

## 四、为什么会长成这样（推断，非事实）

从 git 历史看，`handler.go` 的 12 次提交里有 9 次是 `fix(voicegateway)`，
每条对应一个真机现象：`connection_silent` 超时不是空闲回收、长 TTS 打断要停转发、
透明重开不能重置序号、不产生字节的调用不该抢写锁、一次写要有上界……

**这是健康的排查方式，但每次修法都选了"在最近的调用点加一个分支"**。
12 次之后，`sessionRuntime` 有了 30 个字段，`handleControl` 有了 279 行，
turn 的状态有了 5 个家。

我的判断（置信度中）：**当时每个选择都对**——在真机问题面前，最小修法是正确取舍。
问题不是"当初做错了"，而是**没有人回头做那次收敛**。

## 五、建议的收敛方向（待你定，不在本次执行）

按"改动小、收益大"排序。每一条都给出**可观测的反证条件**。

| # | 动作 | 收益 | 反证条件 |
|---|---|---|---|
| **A1** | **turn 状态收进一个类型**（如 `turnState`），`sessionRuntime` 只持有它 | F1/F3：turn 状态有唯一所有者；turn id 只在一处解析 | 之后再出现"X 的 turn 状态不对"，应该能在该类型里一眼定位 |
| **A2** | `startCollectTurn` 解析一次 payload，`resolvedUserText` 成为唯一规则 | F2：消掉 3 次 unmarshal 与 2 份规则 | 给两份规则各写一个测试，若它们必须一致，则应只有一个函数 |
| **A3** | 二进制帧编码统一到 `voiceproto`（provider 也走 `AITTSAudio.Encode`） | F4：线上格式单一实现 | 若 `encodeAudioFrame` 还有存在理由（如性能），需写明并加一致性测试 |
| **A4** | 帧大小常量集中，并写出与采样率的关系（`frameBytes = ms * rate/1000 * 2`） | F5：采样率变化时不会静默错 | 换 24k 时，只有一处需要改 |
| **A5** | `handleControl` 拆成 per-frame 处理器；错误策略显式化（如 `onProviderError` 策略表） | F6：加新帧类型不用重推一遍策略 | 新增一个帧类型时，diff 只应包含新处理器 |
| **A6** | `voicepoc` 拆成 `voiceduplex`（生产）与 `voicepoc`（PoC/工具），或至少补包注释说明边界 | F7/F9：命名与现实一致 | `grep internal/voiceduplex` 应只出现在生产路径 |
| ~~**A7**~~ | ~~修 `defaultDuplexVoice` 的过时默认值~~ + 清掉悬空注释 | F8 ✅ 已清；"已知会失败的值"**是我判错了**——见 F7 末条的推翻说明，该值是对的，**不要动它** | 该默认值应在测试里被验证为"本账号可用"（无需施行） |

**建议先做 A1 + A2**：它们收益最大、风险最低（A1 是结构搬移，A2 是删重复），
且 A1 做完之后 A3–A6 会自然变简单。
