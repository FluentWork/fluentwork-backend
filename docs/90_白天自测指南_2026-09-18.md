## 1. 真机联调：四条链路怎么验

| 链路 | 验什么 | 怎么才算过 |
|---|---|---|
| ① 说 → 回顾 → 炼化 | 一场真实会话后，回顾页有真实评价、双栏对照、3–5 个三元组 | 锚点是**你确实说过的那半句**，不是模板 |
| ② 语料库 + 推荐 | 入库后语料库出现该块；开新会话时推荐位给出该场景的块 | 推荐项带 reason，状态灯是灰 |
| ③ 闪测 → 判定 → 申诉 | 说完答案后能看到**识别文本**与判定理由 | 答得对就 pass；答错可申诉恢复 streak |
| ④ 话题卡 → 打卡 | 语料 ≥20 块后出卡；打卡勾选"用上了哪几句" | 勾选后该块 `real_use_count` +1 |

### ① 的边界用例

| 情形 | 期望 |
|---|---|
| 整场只有 AI 说话（空会话） | 回顾**不产出**评价与块；日志记 `failure_kind=empty_session`（不是故障） |
| 用户说了半句就停（未完成句） | 救援出梯子；炼化出的块锚点 = **那半句原文** |
| 沉默 3 秒被救援后才开口 | 锚点 = **开口的第一句** |
| 始终没开口 | **不产块**；`rescue_events` 里有该事件（path=silent, user_opened=0） |
| 中途打断 AI | 转录里是**你听到的那部分**（`interrupted=1`），不是模型生成的全部 |

### ③ 的边界用例（本轮重点修复）

| 情形 | 期望 |
|---|---|
| 判定调用超时（模型慢） | 响应 `judged=false, retryable=true`；**streak 不变、状态不回退**；`drill_unjudged_total` +1 |
| 判定返回但 JSON 解不开 | 同上（`judge_reason=judge_parse_error`） |
| 说了要点但比目标句短 | **pass**（rubric：保留核心命题即通过，不要求复述每个细节） |
| 说了完全无关的句子 | fail |
| 判定失败后申诉 | streak 恢复到失败前，`next_due_at` 回到原到期时间 |
| 对**未判定**的记录申诉 | `restored=false`，note 说明"该次未判定，无可回滚" |
| 连续两次问同一个块 | 第二次不是"新块释放"，不计入每日上限 |

### ② 的边界用例

| 情形 | 期望 |
|---|---|
| 同一句被两场会话炼化出来 | 第二次**合并**（`merged_count=1`），语料库仍只有 1 个块 |
| 大小写/标点不同但同句 | 同上（归一化比较：`The deploy is blocked.` = `the deploy is blocked`） |
| 不同句子 | 各自成块 |
| 打卡勾选卡片没提供的块 | 该 id 回传到 `ignored_block_ids`，**不静默吞掉** |
| 同一张卡重复打卡 | 409；重复勾选不会二次计分（`(block, source, ref)` 幂等） |
| 命中重复上报 | 幂等（同 session+turn+block 只计一次） |

### ④ 的边界用例

| 情形 | 期望 |
|---|---|
| 语料 <20 块 | **不出卡**（H1 阈值），`topic_card_gen_skipped_total{reason="below_threshold"}` +1 |
| 卡片正文没引用你的原话 | 服务端**丢弃该卡**（H2 正文级校验），`topic_card_ungrounded_total` +1 |
| 与最近 3 天标题重复 | 丢弃该卡 |
| 打卡不勾选任何块 | 只记打卡与 streak，`recorded_use=0`（不惩罚） |
| 勾选 3 个块 | `recorded_use=3`，三块的 streak 各 +1（**视同成功**，与 App 内命中同权） |

## 2. P0-3 产品决策：三个待定问题

| # | 问题 | 选项 | 影响 |
|---|---|---|---|
| 1 | 空会话（用户点了"重新开始"但没说一句话）要不要进回顾管线？ | A 不进（入口不建会话，首次开口才建） / B 进但快速拒绝（现状） | A 干净但改动大；B 现状会产生空记录 |
| 2 | 「开始」时立刻建会话，还是首次说话才建？ | A 立刻（现状） / B 首次说话 | B 需要客户端配合（延迟建会话） |
| 3 | 工作台模块留不留？新建会话要不要主题输入（A1）？ | A 保留工作台 / B 入口改为会话列表 | 与 `79_` 的入口形态决策同源 |

**我的建议**：1 选 A（空会话是纯噪声，且现在已有 `failure_kind=empty_session` 可观测），2 选 A 保持现状（首次说话才建会话需要客户端配合，收益不抵复杂度），3 需要你结合 iOS 侧体验定。

## 3. 话题卡人工抽检（30 分钟）

评估报告里的 `review-sheet.md` 已经生成抽检清单（每 10 条取 1 + 全部争议项）。判断标准：

| 判定 | 标准 | 例子 |
|---|---|---|
| ✅ 贴 | 话题**只能**给这个用户——用到了他真实的场景/表达 | "用你在 standup 说过的那句 deploy is blocked，跟同事同步阻塞" |
| ⚠️ 半贴 | 引用了用户的句子，但套在通用模板里 | "Daily standup update：<用户的句子>" |
| ❌ 泛 | 换成任何学习者都成立 | "Technical interview: design a rate limiter" |

**边界判断**：卡片引用了用户原话、但场景是用户没做过的（例如用户只练过 standup，卡片却出面试题）→ 算 **⚠️ 半贴**，并记下来——这正是 §F3 那 44% 的来源。

**产出**：6 张卡的判定 + 一句结论（当前 prompt 够不够用）。这一项能 settle F3 剩下的争议——评估里的裁判指标我信不过。

## 4. badge / 命中注入：现状与本次优化

### 4.1 之前的问题（已在代码里修掉）

- badge 的候选来自**按用户隔离**的语料库；`scripts/corpus-seed` 只能给**一个固定 device_id** 播种，**真机用的是它自己的 guest id** → 真机上 badge **静默永不触发**，任何地方都不报错（`dev-up.sh` 自己留了警告）；
- 播种词表散落在 `cmd/corpus-seed`，与产品没有关系。

### 4.2 现在

| 场景 | 行为 |
|---|---|
| **本地 dev-echo provider** | 不需要语料：badge 候选由回显文本派生（自足，确定性） |
| **真机 / live provider（development）** | 该 guest **首次创建会话**时，app-server 自动播种同一份起始语料（`corpus.StarterProvisioner`），**零手工步骤** |
| 生产 | **不**自动播种（`cmd/app-server` 只在 `APP_ENV` 为本地值时挂载） |
| 想给某个 device 显式播种 | `go run ./cmd/corpus-seed -device-id <id>`（词表与自动播种共用一份：`corpus.StarterBlocks()`） |

**两条护栏**：仅在 development 挂载；仅在该用户**语料为空**时写入（有块就什么都不做，不是"补货"）。

### 4.3 怎么自测

```bash
# 1) 起服务（development）
./scripts/dev-up.sh

# 2) 用一个全新的 device_id 建会话 —— 应当自动播种
curl -sS -X POST localhost:8080/api/v1/auth/guest -H 'Content-Type: application/json' \
  -d '{"device_id":"probe-1"}' | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])'
# 用上面的 token：
curl -sS -X POST localhost:8080/api/v1/sessions -H "Authorization: Bearer <TOKEN>" \
  -H 'Content-Type: application/json' -d '{"scene_type":"standup"}' >/dev/null
curl -sS "localhost:8080/api/v1/corpus/blocks" -H "Authorization: Bearer <TOKEN>" | python3 -c 'import json,sys; print("blocks:", len(json.load(sys.stdin)["items"]))'
# 期望：blocks: 10（起始语料），且 app-server 日志有一行 "starter corpus provisioned (development only)"

# 3) 边界：再建一次会话 —— 不应再增加
#    期望：blocks 仍是 10（只在语料为空时播种）
```

## 5. 客户端（不着急）：后端已就绪的契约

| 能力 | 接口 | 新增字段 |
|---|---|---|
| 闪测判定 | `POST /api/v1/drill/judge` | `judged`（false = 未判定，请重试）、`retryable`、`promoted`（刚转绿）、`record_id`、`asr_text` |
| 申诉 | `POST /api/v1/drill/appeal` | body `{record_id}` |
| 话题卡 | `GET /api/v1/topic-cards` | `block_ids`、`source_note`、`blocks[{id,expression_en,intent_zh}]` |
| **打卡带块** | `POST /api/v1/topic-cards/:id/checkin` | body 增 `used_block_ids[]`；响应 `recorded_use`、`ignored_block_ids` |
| 实战转化率 | `GET /api/v1/topic-cards/stats` | `real_uses_hit`（服务端观测）与 `real_uses_checkin`（用户确认）**分列** |
| 语料推荐 | `GET /api/v1/corpus/recommendations?scene=` | 每项带 `reason`（scene_match / most_used / stale_green） |
| 质量反馈 | `POST /api/v1/corpus/blocks/:id/feedback` | body `{reason: not_idiomatic\|not_useful\|wrong_meaning}` |
