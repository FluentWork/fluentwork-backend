# 02 — 语音网关

> 基线 `c23cc38`。本章只看 `internal/voicegateway`（7133 行生产 / 11118 行测试 / 71 个文件）与它两侧的 `voiceproto`。
> **`103_tts_wss_architecture_audit/` 已经审过的部分（切帧层统一、`AITTSAudio.Encode` 唯一编码位置、`SeqAllocator`、救援路径与 AI 路径为何不合并流控制）这里不重复。**

## 1. 一帧的生命周期

```
client ──WSS──▶ serveVoice
                  │
                  ├─ handshake()                        handler.go:234
                  │    read auth (15s) → 必须是 text → DecodeType → 必须 == "auth"
                  │    → ticket 非空 → consumer 非空 → Consume → 回 session.ready
                  │
                  └─ loop()                             handler.go:504
                       │  rt := &sessionRuntime{...}
                       │  startRescueLoop()  ← 每连接一个 poller，不是每帧
                       │
                       └─ for { conn.Read(idleTimeout) }
                            ├─ MessageBinary → handleAudio()      handler.go:549
                            └─ MessageText   → HandleControl()    handler_control.go:101
                                                 └─ 7 个 handler 顺序扫描
                                                      └─ unknownFrame() 兜底
```

**两层超时是分开的，且各有各的理由**（`config.go:16-49`）：

| 常量 | 值 | 它管什么 | 注释里写明的边界 |
|---|---|---|---|
| `defaultIdleTimeout` | 2 分钟 | **每次读**的上限 —— 半开连接探测 | 「它**不能**发现『连着但闲着』的用户」，并指向 `77_` P1-17 |
| `defaultWriteTimeout` | 5 秒 | **单次写**的上限 | 到期会关**整条连接**（`coder/websocket` 的行为），这是刻意的：语音是实时的 |

**`defaultIdleTimeout` 的注释是本仓最好的注释之一**：它先说明这个旋钮**是**什么（半开连接探测），再说明它**不是**什么（空闲用户回收），最后指出后者**没有实现**。这挡住了最常见的误读。

## 2. 好在哪里

### 2.1 失败策略是一张表，而且「沉默」必须给理由（G3）

```go
// handler_control.go:37-75
type providerErrorStrategy struct {
	code string
	// silentBecause records why a frame sends nothing. Empty when code is set.
	//
	// It is required for silence rather than optional: silence is the choice that
	// needs justifying, because the failure it hides is a frame the client thinks
	// succeeded.
	silentBecause string
}

var providerErrorStrategies = map[string]providerErrorStrategy{
	voiceproto.TypeUserSpeechStart: announces("provider_control_failed"),
	voiceproto.TypeUserSpeechEnd:   announces("provider_control_failed"),
	voiceproto.TypeInterrupt:       announces("provider_interrupt_failed"),
	voiceproto.TypeClientTurnAbort: silent("an error frame maps to iOS .failed and would kill the session the abort exists to keep alive"),
}
```

三件事同时成立，缺一不可：

1. **表里只有 4 行**，而 `HandleControl` 有 7 个 handler。**多出来的那些不经过 provider**（`ping` 回 pong、`session.end` 落库、重复 `auth` 拒绝），所以它们不需要失败策略 —— 这个对应关系是能被读出来的。
2. **`silentBecause` 对沉默是必填的**。理由写在结构体注释里，不是写在调用点。所以「为什么这个帧失败不告诉客户端」这个问题，**答案住在类型定义旁边**。
3. **表外的帧落到 provider 时默认播报**（`:171-178`）：

```go
strategy, known := providerErrorStrategies[frameType]
if !known {
	// A frame that reaches the provider without a policy is a bug in
	// this package, not a client problem: it means a handler was added
	// without saying how its failures are reported. Announcing is the
	// safe default — silence would hide it.
	return rtSendError(ctx, conn, rt, "provider_control_failed", err.Error())
}
```

**这是「把新加的东西逼成一个必须做的决定」的一个实例。** 新加一个转发帧却忘了定策略，结果不是「静默通过」，而是「播报」——错得响，而不是错得静。

而且这张表**被导出供测试断言**：

```go
// ProviderErrorPolicies returns the failure policy for every frame the gateway
// forwards to the provider.
//
// Exported for the test that asks each frame type to have chosen: either a code
// to send, or a reason not to. The policy is the deliverable here, so it is worth
// being assertable from outside the package that owns the dispatch.
func ProviderErrorPolicies() map[string]ProviderErrorPolicy
```

### 2.2 两处枚举被一条反射测试逼成「必须做的决定」（**本仓最好的一个测试**）

`writableOutbound`（`:746`）与 `writeProviderOutbound`（`:755`）各自枚举了一遍「`ProviderOutbound` 的哪些字段会到线上」。两处必须一致。

**代码里没有把两处合并，而是把「不一致」变成了测试失败**：

```go
// handler_write_bound_test.go:237-274
// `writableOutbound` 与 `writeProviderOutbound` 各自枚举一遍"哪些字段会到
// 线上"。**两处分离是有意的，不是遗漏**：
//
//	漏更新谓词 → 多抢一次锁（无害，最坏是等一个 WriteTimeout）
//	漏更新写侧 → 字段静默不上线（丢数据）
//
// 所以合并成单一谓词反而把"无害的漏"换成"有害的漏"。真正该挡的是"有人
// 加了字段却两处都没想起来" —— 这条用反射把它变成一个**必须做的决定**。
func TestProviderOutbound_EveryFieldIsClassified(t *testing.T) {
	classified := map[string]bool{
		"Control":       true,
		"Binary":        true,
		"ServerASRText": false, // B14 徽章载体：服务端内部用，不上线
	}
	typ := reflect.TypeOf(ProviderOutbound{})
	for i := range typ.NumField() {
		if _, ok := classified[typ.Field(i).Name]; !ok {
			t.Fatalf("ProviderOutbound 新增了字段 %q，尚未分类。\n"+
				"  会写到线上 → 同时更新 writableOutbound 与 writeProviderOutbound，并在此标 true\n"+
				"  不上线     → 在此标 false，并写明它承载什么", typ.Field(i).Name)
		}
	}
	if len(classified) != typ.NumField() { /* 字段被删了、表没清 */ }
}
```

**为什么这是本仓最好的一个测试：**

1. **它挡的是「忘了做决定」，不是「做错了决定」。** 这是唯一能被自动化的一类错误。
2. **它是双向的。** 少一个条目 → 失败；多一个条目（字段已删）→ 也失败。多数「分类表」测试只做单向。
3. **它把「为什么不合并」写下来了**，并给出成本不对称的理由（无害的漏 vs 有害的漏）。**没有这段注释，下一个读代码的人会把两处合并，然后引入一个丢数据的 bug。**
4. **失败信息就是操作说明**（「会写到线上 → 同时更新 A 与 B 并标 true」）。

**这正是 iOS 侧还在一张票一张票地补的那个形状。** 对照 `80_/04` §3.1（8 份 `waitUntil` 已漂移）与 `70_/20_` §4（iOS 的带理由名单只有单向断言）：**backend 已经有双向反射版了。**

**确定性：【读码】。**

### 2.3 未知帧：忽略 + 计数 + 日志，且写明了为什么不能回错误（G8）

```go
// handler_control.go:465-486
// Emitting unsupported_frame used to map to iOS .failed and killed live sessions
// (client.turn.abort before 5c2e39f). A later protocol version adding a new
// client frame must not repeat that on an older gateway — so it is counted and
// logged instead.
func (h *Handler) unknownFrame(...) error {
	rt.unknownFrameCount++
	h.logWarn(rt, "unknown_frame", "ignoring unknown control frame", ...)
	return nil
}
```

**与 iOS 独立地选了同一策略，且都写了理由。** iOS 侧见 `URLSessionSocketTransport.swift:316-332`（未知类型 → `.unsupportedControlFrame` → `transport_control_frame_ignored`）。

**两侧的对称性是真的**（`80_/README` 的 G7）：都选了「忽略 + 计数」而不是「回错误」，都记录了那次事故。这是跨仓协议演进的一条重要约定：**新客户端帧不能在旧网关上炸掉会话。**

`unknownFrameCount` 还会在 `session.end` 时进入日志（`handler_control.go:439`）—— 所以它是可观测的，不是只躺在内存里。

### 2.4 三处「为什么这么写」的注释，各自挡住一个具体 bug

| 位置 | 注释说的 | 挡住的 bug |
|---|---|---|
| `sendOutbound:463-467` | 「先问有没有东西要写，**再**抢锁」 | `interrupt` 分支在 provider 返回 `nil,nil` 时也调它；不先问的话读循环会排在一次「写零字节」的写后面，`interruptedThisTurn` 永远设不上（`docs/67` §2.1） |
| `sendWithoutRescueState:487-492` | 梯子自己的音频**不能**喂给 B8 救援状态 | 会开一个新的静默窗口并重置梯级，于是「1→2→3 升级」变成永远说第 1 级 |
| `startCollectTurn:677-683` | 「一个帧解析一次」 | **以前这里 unmarshal 三次、「用户的文本是哪个」的规则写了两遍**，改一处会让徽章与锚点对同一个发言不一致 |

**第三条值得单独看**：它是 **iOS D6/D11 的同一形状**（一处判断被抄成两份，改一处不会红），**而 backend 已经修过了**，并留下了理由。这是跨仓对照里最有价值的一条：同一个坑，一侧踩过并记下，另一侧正在踩。

## 3. 不好在哪里

### 3.1 分派是线性扫描，同一个帧被 JSON 解码最多 8 次（B2）

```go
// handler_control.go:101-129
func (h *Handler) HandleControl(...) error {
	frameType, err := voiceproto.DecodeType(data)          // ← 第 1 次解码
	...
	handlers := []func(...) (controlOutcome, error){
		h.controlKeepalive, h.controlSessionStart, h.controlUserSpeech,
		h.controlTurnAbort, h.controlInterrupt, h.controlSessionEnd, h.controlAuth,
	}
	for _, handle := range handlers {
		outcome, err := handle(ctx, conn, session, data, rt)
		if err == nil && outcome == controlNotMine { continue }
		return err
	}
	return h.unknownFrame(...)
}
```

而**每个 handler 的第一件事**又是同一个调用：

```
handler_control.go:200  controlKeepalive     frameType, err := voiceproto.DecodeType(data)
handler_control.go:223  controlSessionStart  frameType, err := voiceproto.DecodeType(data)
handler_control.go:308  controlUserSpeech    frameType, err := voiceproto.DecodeType(data)
handler_control.go:361  controlTurnAbort     frameType, err := voiceproto.DecodeType(data)
handler_control.go:397  controlInterrupt     frameType, err := voiceproto.DecodeType(data)
handler_control.go:416  controlSessionEnd    frameType, err := voiceproto.DecodeType(data)
handler_control.go:458  controlAuth          frameType, err := voiceproto.DecodeType(data)
```

`DecodeType` 是 `json.Unmarshal(raw, &Envelope{})`。所以：

- **`session.end`（第 6 个）要解码 7 次**；
- **`interrupt`（第 5 个）要解码 6 次** —— 而 `interrupt` 在打断路径上，是延迟敏感的；
- 一次都没命中的未知帧要解码 8 次。

**两个独立的观察：**

1. **成本**：控制帧不是每帧热路径（音频走二进制分支，不经过这里），所以这不是性能事故。但 `interrupt` 在 6 次 JSON 解析之后才被认领，而它存在的意义就是「尽快停掉 AI 音频」。
2. **形状**：**同一个仓里，`voicegateway` 为「失败策略」建了表，却为「分派」用了线性扫描。** 而 iOS 的 `TransportEventRouter` 用的是 `[WSControlFrameType: ControlFrameHandler]` **字典**。两侧的分派结构不一致 —— 而且**方向是反的**：iOS 那条链路的帧种类更多，却做了 O(1)。

**公平地说**：这个 handler 列表**是按频率排的**（`ping` 最前、`sessionStart` 次之、`auth` 最后），所以常见路径的代价最低。这个排序看起来是有意的。问题不在于排序，在于**每次比较都先付一次 JSON 解析**。

**确定性：【实测】**（8 处 `DecodeType(data)` 由 grep 列出）。

### 3.2 `ai.audio.chunk` 声明了常量，全仓 0 处使用（P1）

```go
// voiceproto/frames.go:21
TypeAIAudioChunk = "ai.audio.chunk"
```

`grep -rn "TypeAIAudioChunk"` 在**非测试代码里 0 命中**。

**这与 iOS 的 D11 是同一件事的两侧。** iOS 侧的结论是：这是**唯一一类会承载音频、而客户端一个 handler 都没有**的控制帧；iOS 的修法是「收到就留一条痕」（`70_/20_`）。

**backend 侧的对应事实是：它没有生产者。** `frames.go:21` 是唯一的出现处，`frames_test.go:445-447` 把它记为「no producer, no consumer, no test, **on either side of the wire**」，`58_` 文档说「全仓再无一处引用 —— 连测试都没有」，V2 设计 `51_:169` 说「❌ 不加」。

**所以两侧合起来是一个完整的判断**：

| | iOS | backend |
|---|---|---|
| 这个类型 | 有 handler 位置，但**空着** | 有常量，但**没有生产者** |
| 现状 | 已改为「收到就留痕」（`de19195`） | 不需要改 —— 没有生产者就没有风险 |

**两边都没有错，但两边都是「一个看起来是机制的声明」。** 这种对称的冗余值得记一笔：协议定义里同时存在一个不会被发的类型，和一个不会被处理的 handler 位置。

**确定性：【实测】。**

### 3.3 二进制帧不带 `turn_id`（P2 —— 本仓唯一需要跨仓决策的改动）

```go
// voiceproto/frames.go:179-215
// AITTSAudio is a WebSocket binary TTS frame, not JSON.
// Wire layout matches iOS WSAudioFrameCodec: 4-byte big-endian seq + payload.

func (f AITTSAudio) Encode() ([]byte, error) {
	if len(f.Payload) == 0 { return nil, fmt.Errorf("ai.tts.audio payload must be non-empty") }
	out := make([]byte, 4+len(f.Payload))
	binary.BigEndian.PutUint32(out[:4], f.Seq)
	copy(out[4:], f.Payload)
	return out, nil
}

func DecodeAITTSAudio(raw []byte) (AITTSAudio, error) {
	if len(raw) < 5 { ... }   // 4 字节序号 + 至少 1 字节负载
	...
}
```

**`[4B seq][payload]` 是冻结格式**（`103_` 的 `04_` 已确认），payload 不能为空，且**没有任何位置能放 `turn_id`**。

**这直接导致 iOS 的 D7**：音频帧无法自述归属，所以 iOS 只能**用控制帧的时序推断**「这一帧属于哪一轮」。`80_/03` §4.1 记的后果是：网关违约时（旧轮的迟到帧在新轮 `ai.tts.start` 之后到达），旧轮音频会被当成新轮的播出去。

**两侧的 turn_id 现状对比（这才是关键）：**

| 帧 | `turn_id` 的 JSON tag | 说明 |
|---|---|---|
| `ai.tts.start` | `json:"turn_id"` | **无 `omitempty`** —— 声明为必然存在 |
| `ai.tts.end` | `json:"turn_id"` | **无 `omitempty`** |
| `ai.text.delta` | `json:"turn_id,omitempty"` | 可选 |
| `ai.turn.end` | `json:"turn_id,omitempty"` | 可选 |
| `client.asr.transcription` | `json:"turn_id,omitempty"` | 可选 |
| `feedback.badge` | `json:"turn_id,omitempty"` | 可选 |
| **`ai.tts.audio`（二进制）** | **不存在** | **放不下** |

**这张表本身就是证据**：**恰恰是两个必须可归属的帧（`tts.start` / `tts.end`）把 `turn_id` 声明成必填，而二进制音频帧一个字节都没有留给它。** 所以「这一帧属于哪一轮」这件事，只能从它**前后**的控制帧推。

而 `canonicalTurnID`（`turn_id.go`）保证了 turn_id **不会为空**（客户端不传就回落成 `sessionID`），所以问题不是「缺值」，是「音频帧拿不到它」。

**确定性：【读码】。** 这是 `05` §1 的 S0-1。

### 3.4 音频热路径上有一句逐帧 `Debug` 日志（P4）

```go
// handler.go:565-570（handleAudio 内，每个二进制帧都走）
// Log all incoming binary audio frames for debugging
h.logger.Debug("received binary audio frame",
	"payload_bytes", len(data),
	"session_started", rt.started,
	"provider_nil", rt.provider == nil,
)
```

**在每帧路径上无条件调用一次日志。** 两件事：

1. **变参切片分配**：`slog` 的 `args ...any` 在调用点就会构造切片并装箱 3 个值 —— **即使日志级别把这条消息丢掉**。
2. **量级**：客户端上行是 20ms 一块，即 **50 帧/秒/会话**。所以这是每秒 50 次无谓的分配与调用。

**公平地说**：这是 `Debug` 级别，生产环境大概率不输出；而且它确实是调试这条链路时最想要的一行。**判断：这不是缺陷，是一处该被量化的成本** —— 而这正好落在 B7（全仓 0 个 benchmark）上：**没有基准，就没法说清这行值不值。**

**确定性：【读码】**（分配行为是 Go 的语义，非本仓代码可读出的实测）。
