## 2. 依赖方向（实测）

### 2.1 分层

从边表能读出三层，且**没有任何一条反向边**：

```
                    cmd/*（25 个入口）
                         │
        ┌────────────────┴────────────────┐
        │                                 │
  internal/httpserver               internal/voicegateway
  （HTTP 组合根，                （语音组合根，入度 = 2）
    依赖 15 个 internal 包）             │
        │                                 │
        └──────────┬──────────────────────┘
                   │
        ┌──────────┴───────────────────────────────┐
        │  领域包（互相依赖，但无环）                 │
        │  session / corpus / topic / drill /       │
        │  content / account / materials / review / │
        │  aicost / sessionhistory / conversation / │
        │  orchestrator / reviewgen / eval          │
        └──────────┬───────────────────────────────┘
                   │
        ┌──────────┴───────────────────────────────┐
        │  基座（不依赖任何 internal 包）             │
        │  config · apierr · httpjson ·             │
        │  voiceproto · voiceduplex · eval          │
        └──────────────────────────────────────────┘
```

| 15 | `internal/session` | 领域枢纽 |

**`config` 的入度 22 = 包总数。** 这是一个诚实的观察，不是缺陷：环境配置本来就该被所有包读到。但它意味着 **`config.Config` 是一个无处不在的全局参数**，`httpserver.New(cfg, ...)` 只是它最显眼的一次出现。

### 2.3 环检测：0 个环

DFS 三色标记跑遍所有边：**0 个环**【实测】。

这是真的，且是有代价换来的 —— 见 §3.2 的 `depguard`。

### 2.4 叶子与死代码

- **`internal/voiceproto` 依赖 0 个 internal 包**（纯协议类型），被 `session` 与 `voicegateway` 依赖。**这是全仓最干净的一个包**：它只有帧类型、编解码、以及共享常量，没有任何行为。
- **`internal/voiceduplex` 也依赖 0 个 internal 包** —— 它是 vendor 传输层，被 7 处依赖。
- **`migrations/` 被 0 处依赖**（见 §4.2）。

### 2.5 唯一一条「被写下来的分层妥协」

```go
// internal/voicegateway/uplink_constants.go:4-12
// UplinkChunkBytes is the size of audio chunks sent from client to vendor:
// 20ms of 16 kHz mono s16le = 640 bytes.
//
// ... This constant is declared in voicegateway because it is conceptually part of
// the client audio format specification. However, voiceduplex (a lower layer)
// also needs it, so we accept the layering compromise to avoid an import cycle.
const UplinkChunkBytes = 640
```

**这是本仓注释质量的一个样本**：它承认这是一个妥协、说明了为什么（避免 import 环）、并且说清了它本该属于哪一层。

**但注释有一处对不上代码**（P3）：注释说「both uplink paths (`voiceduplex/volc_duplex.go` and `provider_dev_echo.go`) use this size」，而 `internal/voiceduplex/volc_duplex.go:958` 有**自己的** `uplinkChunkBytes = 640`。所以实际是**两份定义**，不是「一份共享 + 一处妥协」。

**确定性：【读码】。** 这是 B3 类问题的缩小版：改一处不会让另一处红。

## 3. 好在哪里

### 3.1 依赖图无环，而且是「能被跑出来」的无环

0 个环本身不值得夸——Go 编译器就禁止包环。值得夸的是**这里的无环是有方向含义的**：`voicegateway` 不认识 `content/tts`，`httpserver` 不认识 `voicegateway`，`voiceproto` 不认识任何东西。

### 3.2 纪律是机器执行的，不是口号（**本仓最强的部分**）

`AGENTS.md` 的「接缝纪律 R6」写着「依赖方向要能跑」，并说明它**已经进了 lint 配置**。核实结果：确实进了，而且**带理由**。

```yaml
# .golangci.yml
    depguard:
      rules:
        main:
          files:
            - "**/internal/voicegateway/**"
          deny:
            - pkg: ".../internal/content/tts"
              desc: "语音链路不进程内调 TTS；走 HTTPSessionClient/HTTPRescueSynthesizer 到 app-server"
            - pkg: ".../internal/reviewgen"
              desc: "回顾管线属于 app-server；语音链路不该依赖它"
            ...
        no-poc-in-production:
          files:
            - "**/internal/**"
          deny:
            - pkg: ".../internal/voicepoc"
              desc: "生产代码不依赖 PoC/测量包；传输层在 voiceduplex"
```

三件值得学的事：

1. **每条禁令都有 `desc`**。不是「不许依赖 X」，是「不许依赖 X，因为 Y」。半年后有人想加回这条依赖时，他要反驳的是那个理由，不是一条规则。
2. **`no-poc-in-production` 的注释记录了这个边界为什么需要被写下来**：*「这个边界此前只存在于读者的判断里，而 voicepoc 里当时装着**生产的语音传输层**（已拆到 voiceduplex，`docs/94_` F7）。规则写下来，它就不能再长回去。」* —— 这是「把判断变成判据」的一个具体案例。
3. **禁令被验证为真的**：我按边表核对，`voicegateway` 的 5 条出边（`config`/`conversation`/`session`/`voiceduplex`/`voiceproto`）里**没有** `content/tts`/`reviewgen`/`eval`/`account`；全仓 `internal/**` 里**没有**一处 import `voicepoc`（只有 3 个 `cmd/` 依赖它）。**规则与代码一致。【实测】**

**唯一的缺口**：`golangci-lint` 在本机**没有安装**（`dev-check.sh:18` 会 `need` 它并给出安装命令），所以这条纪律在本机跑不起来（P6）。`dev-check.sh` 的 `need()` 会在工具缺失时**直接退出 1**，这是对的做法——它不会假装检查过了。

## 4. 不好在哪里

### 4.1 `voicegateway` 是一个 71 文件的扁平包（B1）

```
internal/voicegateway/          ← 没有子目录
  handler.go                    (912)
  handler_control.go            (486)
  handler_rescue.go             (636)
  provider_volc_duplex.go       (1236)
  provider_dev_echo.go          (460)
  badge_emitter.go              (429)
  utterance.go                  (362)
  turn.go                       (342)
  config.go                     (317)
  silence_detector.go           (211)
  rescue_orchestrator.go        (228)
  ... 共 71 个 .go
```

`find internal/voicegateway -type d` 只返回它自己。

**为什么这是问题，不只是「文件多」：**

- 包内一切可见。`handler.go` 能直接读 `provider_volc_duplex.go` 的未导出字段，反之亦然 —— **Go 的包边界是这个仓唯一真实存在的边界**，而这个包把它放到了 71 个文件之外。
- **测试也在这个包里。** 11118 行测试中有大量 `*_internal_test.go`（`provider_volc_duplex_internal_test.go`、`extract_server_asr_text_internal_test.go`、`handler_logwarn_internal_test.go`），它们用 `package voicegateway` 而非 `voicegateway_test`。这是**有意的**（要测未导出行为），但代价是：**没有任何东西阻止测试去碰生产内部状态**。
- 对比：`internal/content`（29 文件）拆了 `tts` 子包；`internal/corpus`（32 文件）没有。**同一个仓里三种粒度。**

**确定性：【实测】。**

### 4.2 `migrations` 包 embed 了 SQL，但没有任何包 import 它（B4）

```go
// migrations/embed.go
//go:embed *.sql
var SQL embed.FS
```

全仓 `grep "fluentwork-backend/migrations"` → **0 命中**【实测】。

它唯一的消费者是 `migrations/embed_test.go`，那个测试读 `SQL` 来断言「至少有 7 个迁移文件」「合并后包含某些表」。

**所以这个包是一个「看起来是机制、实际是测试夹具」的东西。** 一个读代码的人会以为迁移是被 Go 程序应用的；实际上是被 shell 循环应用的（见 `03` §2）。

### 4.3 文档与代码不一致（P5）

`AGENTS.md:22` 的架构图：

```
│  internal/corpuss/     — 语料库服务                            │
```

实际目录是 `internal/corpus/`（单 `s`）。**照图找目录会找不到。**

这一条很小，但它和 `80_/04` §3.1 的 8 份 `waitUntil`、`70_/20_` §7 的 `handshake` 死面是**同一个形状**：一个「写着 `文件:行` 却对不上」的事实陈述，而**没有任何东西会因为它错了而变红**。

**确定性：【实测】。**
