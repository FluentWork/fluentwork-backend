## 2. 好在哪里

### 2.1 缺陷纪律的检查**知道自己查不了什么**（G4 —— 本仓最值得学的一个脚本）

`scripts/check-defect-discipline.sh`（71 行）检查「实现说明里有没有一节写测试证据」。它的注释里有三处**主动声明边界**：

```bash
# 规则要求实现说明里必须有一节「测试」，写明：哪个测试复现了这个缺陷、
# 它修复前的实际输出、修复后的门禁证据。本脚本检查这一节**存在**。
# 它检查不了内容是否诚实 —— 那需要人看。但"忘了写"是可以自动挡住的。
```

```bash
# 范围刻意限定为**本次工作区改动过的**实现说明，不追溯历史：
# 该规则从 docs/36 开始生效，之前的文档早于规则。追溯会让这个检查长期红着，
# 而一个长期红的检查等于没有检查。
```

```bash
# `-z` 是必须的，不是风格问题：git 默认 core.quotePath=true，会把非 ASCII
# 文件名输出成带引号的转义串（"docs/99_\346\265\x8b..."），路径随即失效。
# 而本仓的文档名全是中文 —— 用默认输出的版本会让这个脚本对每一篇新文档
# 都静默放行，也就是一个永远通过的检查。
```

**第三处是全部的重点。** 作者发现了一个朴素写法会让脚本**永远通过**（因为中文文件名被转义后 `[ -f "$file" ]` 为假，`continue` 跳过），然后修掉了它，并把这件事写在了脚本里。

**这和 iOS 侧是同一个形状的两面**：
- iOS 的问题（`80_/04` §3.2、`70_/15_` §7）：一批 2 秒超时的测试在 CI 上偶发失败，**无法区分新回归与既有抖动** —— 判据在，但它不稳定，所以失去了信号。
- backend 的做法：**主动检查「我的判据会不会永远通过」**。

**一个检查的价值等于它变红的概率。** 这个脚本的注释就是在守这一条。

**确定性：【读码】。**

### 2.2 反射分类测试把「两处枚举」变成必须做的决定

### 2.3 memory store 镜像真 store 的语义（而不是简化版）

`session` 的租约逻辑在两处各实现一遍：

| | 真实现 | 替身 |
|---|---|---|
| 文件 | `mysql_store.go:430-447` | `memory_store.go:320-334` |
| 抢占 | `FOR UPDATE` + `WHERE ... OR (processing AND locked_at <= cutoff)` | 同样的 `leaseCutoff` 判断 + `job.LockedAt == nil \|\| job.LockedAt.After(leaseCutoff)` |
| 租约常量 | `DefaultJobLease` | **同一个 `DefaultJobLease`** |

**所以单测跑的是真语义。** 这与 iOS 侧 `80_/04` §3.5 记的「生产代码里也住着 stub」形成对照：backend 的替身住在 `_test.go` 里（5 个 mock/stub/fake 类型，全在测试文件），**生产代码里 0 个**。

**确定性：【读码】。**

### 2.4 唯一的门禁脚本是完整的、且缺工具时会拒绝假装通过

```bash
# scripts/dev-check.sh
need gofumpt mvdan.cc/gofumpt@latest
need goimports golang.org/x/tools/cmd/goimports@latest
need golangci-lint github.com/golangci/golangci-lint/v2/cmd/golangci-lint@latest

goimports -l . → 非空即退出 1
golangci-lint run ./...        # ← depguard 在这里生效
go test ./...
go build ./...

```

`need()` 在工具缺失时**打印安装命令并退出 1**。**它不会在缺少 golangci-lint 的情况下报告「All checks passed」。**

**对比 iOS**：iOS 侧的门禁写在 `AGENTS.md` 里（三条命令），靠人读、靠人跑。backend 侧是**一个可执行文件**。这是 backend 在工程纪律上明确领先的一处。

**确定性：【读码】。**

### 3.2 `httpjson` / `apierr` 零测试，而 `httpjson.Error` 是每个 API 错误的唯一出口

```go
// internal/httpjson/httpjson.go:31-57（57 行，0 行测试）
func Error(c *gin.Context, err error) {
	var ae *apierr.Error
	if !errors.As(err, &ae) || ae == nil {        // 分支 1：非 apierr 错误 → INTERNAL
		ae = apierr.Internal("internal error")
	}
	if ae.HTTPStatus >= http.StatusInternalServerError {   // 分支 2：5xx 才记日志
		if value, ok := c.Get(LoggerContextKey); ok {
			if logger, ok := value.(*slog.Logger); ok && logger != nil {
				logger.Error("request failed", "err", err, "code", ae.Code)
			}
		}
	}
	status := ae.HTTPStatus
	if status < http.StatusBadRequest || status > 599 {    // 分支 3：状态码范围校验
		status = http.StatusInternalServerError
	}
	c.AbortWithStatusJSON(status, apierr.Body{...})
}
```

**四个分支，覆盖了三类真实错误：**

1. **任意非 `apierr.Error` 的 error → 500 + `INTERNAL`**。这是「不要把内部错误泄露给客户端」的防线，也是**唯一**的防线。
2. **`*apierr.Error` 的 nil 指针** → 也会落到 `Internal`（因为 `|| ae == nil`）。这个分支值得一个测试：`var e *apierr.Error; httpjson.Error(c, e)` —— Go 的 `errors.As` 对 nil 指针是成功的，所以 `ae == nil` 这个判断是**必需的**，不是多余的。
3. **状态码范围校验** —— 一个写错的 `apierr.Error{HTTPStatus: 200}` 会被夹到 500。

**这三个分支合起来决定「客户端看到什么」。** 而它们**没有测试**。`apierr` 本身（66 行）是纯构造器，零测试可以接受；`httpjson.Error` 不是。

**确定性：【实测】**（文件行数 + `[no test files]` 输出 + 【读码】的分支枚举）。

### 3.4 一个 `config.Config` 夹具被复制到 23 个文件（**本仓的 iOS-`waitUntil` 形状**）

| 项 | 值 |
|---|---|
| 构造 `config.Config{...}` 的测试文件 | **23** |
| 出现总次数 | **约 56** |
| 共享的测试构造器 | **没有**（唯一的 `testConfig()` 在 `internal/account/service_test.go:28`，局部） |

单文件最多的是 `internal/session/service_test.go`：**17 处完整字面量 + 5 处 `config.Config{}` + 1 处单字段**。

**重复的样板**（跨文件逐字相同）：

```go
cfg := config.Config{
	HTTPAddr:        ":0",
	AppEnv:          "development",
	AuthJWTSecret:   config.DevJWTSecret,
	AccessTokenTTL:  2 * time.Hour,
	RefreshTokenTTL: 24 * time.Hour,
	...
}
```

**与 iOS 的 8 份 `waitUntil` 相比，这个问题的严重程度低一档，理由要说清楚：**

| | iOS `waitUntil` ×8 | backend `config.Config` ×56 |
|---|---|---|
| 重复的是 | **行为**（轮询间隔、错误类型、超时默认值） | **数据**（字段取值） |
| 已经漂移 | **是**，5 类 | **未知**（未逐份比对） |
| 加字段会怎样 | 编译器不管，行为静默改变 | Go 的键值字面量：**编译通过**，但 `Validate()` 会在运行时让 23 个文件的测试一起红 |
| 危险程度 | 高（静默） | 中（响亮，但吵） |

**所以：这是一处该收敛的重复，但不是本仓最该先做的事。** 它的失败模式是「23 个文件一起报配置错误」，吵闹而不危险。

**确定性：【实测】**（文件数与次数为 `grep -c` 输出）；严重程度对比是【推断】。

## 4. 建议

| # | 动作 | 风险 | 价值 |
|---|---|---|---|
| 1 | 给 `httpjson.Error` 补测试（4 个分支：非 apierr 错误、nil `*apierr.Error`、5xx 记日志、状态码越界） | 低 | **高**（每个 API 错误的唯一出口） |
| 2 | 给 `DecodeAITTSAudio` 写一个 fuzz（`[]byte` 输入，断言不 panic、错误路径有界） | 低 | **高**（手写二进制解码器；也是全仓第一个 fuzz） |
| 3 | 给音频热路径加一个 benchmark（`handleAudio` 每帧分配量），用数据决定 `handler.go:566` 那句 `Debug` 留不留 | 低 | 中 |
| 4 | 抽一个共享的 `config.TestConfig(t)` 到测试支撑包，逐步替换 23 个文件的字面量 | 低 | 中 |
| 5 | 把 `golangci-lint` 装进 CI 镜像（并考虑写进 `SETUP.md` 的前置条件） | 低 | 中 |
| 6 | 在 `test/` 里放第一条跨层测试，**或**删掉 `.gitkeep` 并在 `README` 写明「跨层验证在 `scripts/smoke-*.sh`」 | 低 | 低（消掉一个空承诺） |

**第 2 条是我最推荐的一条**：它同时补上「全仓第一个 fuzz」和「手写解码器的输入边界」两个缺口，成本是几十行。
