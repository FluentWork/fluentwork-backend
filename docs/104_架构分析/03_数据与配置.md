# 03 — 数据与配置

> 基线 `c23cc38`。迁移文件数、表结构来自 `ls` 与 `cat migrations/`；工作队列语义来自 `internal/session` 与 `internal/materials` 的 store 实现。

## 1. 迁移机制

### 1.1 现状（实测）

| 项 | 值 |
|---|---|
| up 迁移 | **26**（`0001`–`0026`） |
| down 迁移 | **4**（只覆盖 `0013`–`0016`） |
| 版本表 | **没有** —— 全仓 0 处提及 `schema_migrations` |
| Go 侧的 embed | `migrations/embed.go`（`//go:embed *.sql`） |
| 谁 import 这个包 | **没有任何包** |
| 应用方式 | **5 份** shell 循环副本 |
| 幂等 | **不是** —— `0008` 起的 ALTER 重放会 `Duplicate column name` |

**5 份副本的位置：**

```
scripts/local-db-init.sh:26      for file in "$ROOT"/migrations/*.sql; do
scripts/dev-stack.zsh:72         for file in "$ROOT"/migrations/*.sql; do
scripts/dev-up.sh:156            for file in "$ROOT"/migrations/*.sql; do   ← docker compose exec
scripts/dev-up.sh:165            for file in "$ROOT"/migrations/*.sql; do   ← 本地 mysql
scripts/smoke-review-ready.sh:114 for file in "$ROOT"/migrations/*.sql; do
```

**应用策略是「按 glob 顺序，每次全部重放」。** 因为 ALTER 不幂等，所以必须有 `--skip-migrations` 才能重启：

```bash
# scripts/dev-up.sh:173-175
# Migrations are apply-once: 0008 onward ALTER existing tables, so replaying
# them against a current schema aborts on "Duplicate column name ..." and takes
# the whole bring-up with it. --skip-migrations is how a restart reuses the
# schema it already has.
```

**这段注释是诚实的**，它把限制写清楚了。但限制本身是结构性的：

- **没有任何地方记录「这个库已经应用到第几号」。** 判断依据是「重放会不会报错」。
- 所以**「这个库是什么 schema」这个问题，只能靠试**。
- 26 个 up 对 4 个 down：**`0017` 之后的 10 个迁移没有回滚路径**。

### 1.2 `migrations` 包是「看起来是机制、实际是测试夹具」（B4）

```go
// migrations/embed.go
// Package migrations embeds ordered SQL schema files for app-server.
//
//go:embed *.sql
var SQL embed.FS
```

全仓 `grep "fluentwork-backend/migrations"` → **0 命中**。唯一消费者是 `migrations/embed_test.go`，它读 `SQL` 来断言「至少有 7 个文件」「合并后包含某些表」。

**所以一个读代码的人会以为迁移由 Go 程序应用**（有包、有 embed、有测试），而实际上应用它的是 shell。这是**本仓最容易被误读的一处结构**。

**确定性：【实测】。**

### 1.3 判断

**这不是「没做好」，是「没做」——而它被一个假机制盖住了。** 三件事各自独立成立：

1. **开发环境够用**：`dev-up.sh` 一把梭，注释写清了限制。对本地开发这不是问题。
2. **生产环境没有答案**：一个没有版本表的 schema，回滚靠手工，26 个迁移里 22 个没有 down。
3. **最大的成本是「读错」**：`migrations` 包 + `embed` + 一个测试，构成一个**看起来完整的机制**。`01` §4.2 把它记为死代码，这里补上后果：**它让人以为不需要关心这件事。**

**确定性：第 1、2 条是【读码】；第 3 条是【推断】。**

## 2. 两种工作生命周期，一套有租约一套没有（**本章最重要的发现**）

这个仓里有**两条一模一样的后台生命周期**：

```
queued ──▶ processing ──▶ ready
                │
                └────────▶ failed
```

**但只有一条有持久化的抢占机制。**

### 2.1 `session_jobs`：有租约（G5）

```sql
-- migrations/0005_create_session_jobs.sql
CREATE TABLE IF NOT EXISTS session_jobs (
    ...
    status       VARCHAR(32) NOT NULL DEFAULT 'pending',
    attempts     INT NOT NULL DEFAULT 0,
    available_at DATETIME(3) NOT NULL,
    locked_at    DATETIME(3) NULL,
    locked_by    VARCHAR(128) NULL,
    last_error   TEXT NULL,
    ...
    KEY idx_session_jobs_claim (status, available_at, created_at),   -- ← 为抢占而建
```

```go
// internal/session/mysql_store.go:430-447
// ClaimNextJob claims one available pending job, or a stale processing lease.
func (s *MySQLStore) ClaimNextJob(ctx context.Context, workerID string, at time.Time) (Job, error) {
	tx, err := s.db.BeginTx(ctx, nil)
	defer func() { _ = tx.Rollback() }()

	leaseCutoff := at.Add(-DefaultJobLease)
	row := tx.QueryRowContext(ctx, `
		SELECT ... FROM session_jobs
		WHERE (status = ? AND available_at <= ?)
		   OR (status = ? AND locked_at IS NOT NULL AND locked_at <= ?)
		ORDER BY created_at ASC, id ASC
		LIMIT 1
		FOR UPDATE
	`, JobStatusPending, at, JobStatusProcessing, leaseCutoff)
```

`DefaultJobLease = 2 * time.Minute`（`session/types.go:40`）。

**这四件事同时做到了，才是对的：**

1. **`FOR UPDATE` 在事务里** —— 两个 worker 不会抢到同一个 job；
2. **过期租约可回收** —— 进程被杀留下的 `processing` 会在 2 分钟后被另一个 worker 捡起；
3. **`attempts` / `locked_by` / `last_error` 都在表里** —— 失败是**可查的**，不是只在日志里；
4. **`memory_store.go:320-334` 镜像同一语义**（包括 `leaseCutoff` 与 `locked_at` 判断）—— 所以单测跑的是**真语义**，不是简化版。

**这是本仓工程质量最高的一处。** 确定性：【读码】。

### 2.2 `materials`：同一个生命周期，没有租约（B10）

```go
// internal/materials/service.go:81-88
id := m.ID
go func() {
	bg, cancel := context.WithTimeout(context.Background(), 40*time.Second)
	defer cancel()
	if err := s.Refine(bg, id); err != nil && s.logger != nil {
		s.logger.Warn("material refine", "material_id", id, "err", err)
	}
}()
return CreateResponse{MaterialID: m.ID, RefineStatus: StatusQueued}, nil
```

**表结构（`migrations/0014`）：**

```sql
CREATE TABLE IF NOT EXISTS materials (
    ...
    refine_status VARCHAR(32) NOT NULL DEFAULT 'queued',
    block_count   INT NOT NULL DEFAULT 0,
    error_code    VARCHAR(64) NULL,
    ...
    KEY idx_materials_user_created (user_id, created_at),   -- ← 为「列出」而建
    KEY idx_materials_user_deleted (user_id, deleted_at),
```

**没有 `attempts`、没有 `available_at`、没有 `locked_at`、没有 `locked_by`。**

**四个后果，逐个说：**

1. **`processing` 是一个没有出口的状态。** `Refine` 的第一件事是：
   ```go
   // refiner.go:42-44
   if m.RefineStatus != StatusQueued { return nil }
   ```
   所以一个停在 `processing` 的行，**永远不会有第二次机会** —— 没有任何代码会再碰它。
2. **进程被杀就会留下这样的行。** goroutine 没有 join、没有 drain：`Create` 返回 200 之后进程随时可以退出，`Refine` 走到一半就没了。40 秒的超时只约束**不退出**的情况。
3. **它跑在 HTTP 请求的 goroutine 之外，不在 `cmd/worker` 里。** 而 `cmd/worker` **确实存在**，并且跑着 `topic.NewScheduler(...)`（`cmd/worker/main.go:92`）—— 所以「后台工作该放哪」这个仓已经有答案，refine 没走那条路。
4. **失败是可查的**（`error_code` + `StatusFailed`，见 §3.1），所以**只有「被杀」这一种失败是无声的**。

**对照的锋利之处**：**同一个人在同一年写了两条同样的生命周期，一条建了 `idx_..._claim` 索引和 `locked_at`，另一条只有 `refine_status`。** 这不是「不会做」，是「做的时候没有把另一条当作参照」。

**确定性：【实测】**（表结构、`grep` 结果、`go func` 位置均为命令输出）。

## 3. 幂等的两种实现

### 3.1 `materials`：状态守卫 + 数据库 CAS（G6）

```go
// refiner.go:42-51
if m.RefineStatus != StatusQueued { return nil }          // 守卫：非 queued 即 no-op
now := s.now().UTC()
if err := s.store.MarkProcessing(ctx, materialID, now); err != nil {
	if errors.Is(err, ErrConflict) { return nil }         // CAS 输了 = 别人在做，也算 no-op
	return err
}
```

`mysql_store.go:47` 的 `MarkProcessing` 是一条 `UPDATE ... WHERE ... AND refine_status = 'queued'` 式的 CAS。

**而且所有错误路径都归到一个带 code 的出口：**

```go
// refiner.go:90-96
func (s *Service) fail(ctx context.Context, materialID, code string) error {
	if err := s.store.MarkRefineFailed(ctx, materialID, code, s.now().UTC()); err != nil { return err }
	incTransition(StatusProcessing, StatusFailed)
	return nil
}
```

`refiner.go` 里 5 条错误路径（`ErrorLLMTimeout` ×2、`ErrorParse`、`ErrorDB` ×2）**全部走 `fail`**，且**每一次状态转换都进指标**（`incTransition`）。

**判断：这条路径的幂等与可观测性是做对了的。** 唯一缺的就是 §2.2 的租约。

**确定性：【读码】。**

### 3.2 `topic_cards`：先读后跳，没有唯一键（B11）

```go
// topic/generator.go:61-76
existing, err := g.store.ListTodayCards(ctx, userID, day)
if err != nil { ... }
if len(existing) > 0 { incSkip(SkipAlreadyGenerated); return nil }
if has, err := g.store.HasCardsForDate(ctx, userID, day); err != nil { ... } else if has {
	incSkip(SkipAlreadyGenerated); return nil
}
```

**两层检查（`ListTodayCards` + `HasCardsForDate`），但表上没有唯一键：**

```sql
-- migrations/0015
    KEY idx_topic_cards_user_date (user_id, for_date, deleted_at),   -- 普通索引，不是 UNIQUE
```

**而「今天跑过没有」这个判断只住在内存里：**

```go
// topic/scheduler.go:24-24, 31-47
type Scheduler struct {
	...
	lastRun time.Time      // ← 进程内存
}

func (s *Scheduler) RunIfDue(ctx context.Context, now time.Time) {
	...
	s.mu.Lock()
	if s.lastRun.Equal(day) { s.mu.Unlock(); return }
	s.lastRun = day
	s.mu.Unlock()
	...
}
```

**两个独立的缺口：**

1. **重启即重跑**：worker 在 04:00 UTC 之后重启，`lastRun` 归零 → 再跑一遍全天批次。
2. **多副本即双跑**：两个 worker 进程各自有一份 `lastRun`，**都**会跑。这时 `ListTodayCards` 的检查是 check-then-act —— 两个进程可能同时读到「还没有」然后都插入。

**公平地说**：`GenerateForUser` 的守卫是认真写的（两层检查 + `GenerateAttempts` 重试 + 6 种 `incSkip` 原因），而且**单副本重启时的重跑会被它挡住**。缺的是**把「唯一」交给数据库**。

**判断：这是一个「现在的部署形态下不会发生」的问题**（单 worker、不重启）。它的价值不在于「现在有 bug」，而在于：**唯一性靠的是一个可以被并发穿过的检查，而表上没有约束能让它穿不过去。**

**确定性：【读码】。**

## 4. 配置面

### 4.1 规模

| 项 | 值 |
|---|---|
| `config.Config` 字段 | **30** |
| 环境变量（`internal/config`） | 31 |
| 环境变量（`internal/voicegateway`） | 22 |
| **合计去重** | **51** |
| 配置来源 | **仅环境变量**（`LoadConfig`），可选 `.env.dev` / `.env.volc.local` |
| `config` 包入度 | **22**（全仓每个包） |

**51 个环境变量，没有配置文件格式、没有 schema、没有文档化的清单。** 唯一的「清单」是 `Config` 结构体本身 + 各包的 `envOr`/`envFirst` 调用点。

**这是一处真实的运维成本**：部署一个新环境需要知道 51 个名字，其中 22 个在 `voicegateway` 包里（另一个包，另一个 `LoadConfig`）。

### 4.2 `Validate()` 是认真的（好）

```go
// internal/config/config.go:182-212
if len(c.AuthJWTSecret) < 32 { return fmt.Errorf("AUTH_JWT_SECRET must be at least 32 characters") }
if !c.IsDevelopment() && c.AuthJWTSecret == DevJWTSecret {
	return fmt.Errorf("AUTH_JWT_SECRET must be set outside development environments")
}
if c.IsProduction() && c.MySQLDSN == "" { return fmt.Errorf("MYSQL_DSN is required in production") }
if c.AccessTokenTTL <= 0 { ... }
if len(strings.TrimSpace(c.InternalAPIToken)) < 16 { ... }
```

**三件做对的事：**

1. **长度下限**（JWT secret ≥ 32、internal token ≥ 16）；
2. **拒绝开发默认值出现在非开发环境** —— 这是最容易漏、后果最重的一条；
3. **生产环境要求 DSN** —— 不会拿一个空 DSN 起服务。

`voicegateway` 也有自己的 `Validate()`（`config.go:151`）。**两个 `LoadConfig`、两个 `Validate`、51 个变量** —— 结构上是「每个进程自己管自己的配置」，这在 Go 的多进程仓里是常见选择，代价是**没有单一事实源**。

### 4.3 两个「默认值即决策」的例子

| 变量 | 默认 | 注释里写的理由 |
|---|---|---|
| `VOICE_RESCUE_ENABLED` | **`isDevelopmentEnv(appEnv)`** | 「a ladder the client cannot render is not a rescue: iOS has no rescue handling yet ... Turning it on in production before then would record rescues that never reached anyone — **data that lies about the user's experience**」（`voicegateway/config.go:57-65`） |
| `VOICE_GATEWAY_PROVIDER` | `"mock"` | 生产必须显式设成 `volc-duplex` |

**第一条是本仓注释质量的一个高峰**：它说明的不是「默认关」，是**为什么默认关** —— 而理由是关于**数据诚实性**（宁可不记，也不记一条用户没经历过的救援），不是关于成本或稳定性。

**确定性：【读码】。**

## 5. 建议

| # | 动作 | 风险 | 价值 | 需决策 |
|---|---|---|---|---|
| 1 | 给 `materials` 补租约：加 `attempts`/`locked_at` 两列，把 refine 挪进 `cmd/worker`，或至少加一个「`processing` 超过 N 分钟则重置为 `queued`」的清扫 | 中 | **高**（`processing` 现在是没有出口的状态；同仓已有可照抄的实现） | 否（照 `session_jobs` 抄） |
| 2 | 给 `topic_cards` 加 `UNIQUE KEY (user_id, for_date)`，让唯一性由数据库保证 | 低（需先查历史数据有没有重复） | 中（把 check-then-act 变成约束） | **是**（要先确认现有数据干净） |
| 3 | 决定迁移的归属：上 Go 迁移工具（`golang-migrate` 等，顺带用上已有的 embed），**或**删掉 `migrations` 包并在 `embed_test.go` 位置写明「迁移靠 shell」 | 中 | **高**（消掉一个假机制 + 补上版本表） | **是**（要知道有没有计划） |
| 4 | 生成一份环境变量清单（从两个 `Config` 结构体导出），放进 `SETUP.md` | 低 | 中（51 个变量的唯一清单） | 否 |
| 5 | 给 26 个迁移里没有 down 的补 down，或明确声明「只前滚」 | 中 | 中 | **是**（要定回滚策略） |

**第 1 条是本系列最推荐的一条**：它**不需要新设计**（`session_jobs` 就是模板）、**风险可控**（加两列 + 一个清扫），而它关掉的是一个**用户可见的**失败模式（用户粘贴材料 → 卡片永远不出来，且没有任何机制会重试）。
