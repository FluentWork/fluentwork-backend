# 设计与实现纪律：以接缝为单位

**日期**：2026-09-18
**起因**：WSS/TTS 链路长成了补丁集合（`94_`），而 build 过、test 过都拦不住。
**回答的问题**：**怎么才能不再发生。**
**状态**：**已生效**。条款写进了 `AGENTS.md` §7，论证据此；本文保留七条的推导与案底。

---

## 一、为什么"测试过了"挡不住这类问题

先把话说透，否则后面所有规则都会被当成又一份"要写好代码"的劝告。

### 1.1 测试验证的是**函数**，问题是**结构**

| 现象（`94_` 发现） | 哪个测试会红？ | 为什么 |
|---|---|---|
| 二进制帧编码有两个实现 | **没有** | 两个都正确，各自有测试 |
| turn id 有 3 套取值规则 | **没有** | 每处单独看都对 |
| 同一份 JSON 解 3 次 | **没有** | 三次解析结果相同 |
| 帧大小常量 4 个 | **没有** | 四个值都对 |
| `handleControl` 里 4 种错误策略 | **没有** | 四种都符合各自注释 |

**每一条都是"局部正确、整体失控"。** 测试的粒度是函数，而问题的粒度是**关系**。
一个断言不了关系的测试集，再怎么加也拦不住关系坏掉。

### 1.2 测试是被 bug 牵着长的，不是被设计牵着长的

`94_` §二数过：`voicegateway` 的 12 次提交里 9 次是 `fix`，每条对应一个真机现象。
每个 fix 都带来了测试——**测的是"这个坑不会再出现"**，从来没有人测过
"这个系统的形状是不是我想要的"。

这是**必要的**（真机教的东西最值钱），但它有个后果：
**测试集描述的是历史，不是设计。**

### 1.3 结构问题没有触发点

代码重复不会让任何东西变红；状态分散不会让任何东西变红。
**没有反馈 = 没有压力 = 必然积累。** 这不是纪律问题，是缺了一条反馈回路。

---

## 二、根因：结构问题长在**接缝**上

把 `94_` 的发现按位置归类：

| 接缝类型 | 本项目的实例 |
|---|---|
| 进程之间 | gateway ↔ app-server 的 HTTP 契约（B8 信封、B7 命中回写） |
| 包之间 | `voiceproto`（帧）vs `voicegateway`（编码）；`drill` vs `corpus`（调度） |
| goroutine 之间 | 读循环 / collect goroutine / 救援轮询器三者共写 turn 状态 |
| 表示之间 | 同一段音频的三种表示：供应商 chunk、provider frame、`AITTSAudio` |
| 层之间 | 生产传输层住在叫 `poc` 的包里（命名与依赖方向不符） |

**结论**：补丁式演进不是"写代码不认真"，而是——

> **每个接缝在被创建时，没有被当成一个需要设计的东西。**

一个函数写得糙，review 会看见；一个接缝开得随意，review 看不见，
因为它表现为"多了一个类型"、"多了一个常量"、"多了一个 if"。

### 2.1 本项目已经证明这条路能走通

`docs/88_LLM_Provider_接入说明` 就是**一份接缝契约**，做法完全正确：

```
功能代码（不含厂商细节）
      │ 只依赖接口
      ▼
orchestrator.Client        ← 唯一的 LLM 接缝
      ├── ArkClient
      └── MockClient
```

并明确写出**不变量**：「功能包**不得** import 任何厂商 SDK 或自建 HTTP 调用」，
还留了案底：「2026-09-18 前 `reviewgen` 里有一个绕过接缝的 `ArkGenerator`，已删除
——那正是防腐层最怕的并行实现」。

**这个框架是对的。它只是只被应用到了一个接缝上。**

## 三、纪律：接缝驱动的七条

每条 = **症状**（怎么认出来）+ **动作**（怎么做）+ **案底**（本项目真实案例）+ **防护**（怎么拦）。

### R1 · 动手前先声明接缝

**症状**：任务描述是"加个功能"，没人问过它跨了几层。
**动作**：写代码前，用三行回答（写进 PR 描述或 issue）：

```
接缝：新增 | 修改（哪些）
状态所有权：<每个跨接缝的状态，归谁>
不变量：<这条接缝上什么必须永远成立>
```

**案底**：B7 命中回写的任务是「`real_use_count` 无写入方」——
它听起来是账本的事，**实际缺的是网关的调用方**。声明接缝的那一行会立刻暴露这一点。
**防护**：PR 模板加一节（`98_` §二 的同类做法）。

### R2 · 一份语义，一个实现点

**症状**：同一条规则在两处出现，且"目前恰好一致"。
**动作**：要么合并，要么**写明各自适用范围**（`devnotes` 规则 5）。
**案底**：`voiceproto.AITTSAudio.Encode()` 与 `encodeAudioFrame()`（**已合并**，M3）；
`resolvedUserText()` 与 badge 分支内联的那段（**已合并**，M4）。
**防护**：**一致性测试**——若两处必须一致，就写一个测试同时喂两边。
若写不出这个测试，说明它们其实不该是两份。

### R3 · 常量必须有出处（推导，而不是复制）

**症状**：同一个数字出现在几处，注释解释"这是什么"但不解释"为什么是这个数"。
**动作**：让常量成为**推导结果**。`FrameBytes(100ms)` 从 `AudioFormat` 算出来，
而不是再写一个 `3200`。
**案底**：`3200` × 2、`640` × 2；`RescueAudioFrameBytes * Ms / 32` 里那个 `32`
是"每毫秒 32 字节"的隐式知识。
（**前两项已由 `AudioFormat.FrameBytes` 取代**，M2/M3；`RescueAudioFrameBytes` 整个消失。
`640` × 2 这一半仍在，见 `98_` §七末条。）
**防护**：测试直接断言推导关系（`FrameBytes(100) == 3200`），采样率一变就红。

### R4 · 接口只服务今天的消费者

**症状**：为"将来可能要扩展"预留的参数、选项、接口。
**动作**：**今天的消费者是谁？** 答不上来就不加。
**案底**（两个方向都验证过）：
- ✅ 做对的：`VoiceProvider` / `VoiceProviderSession` 只服务两个真实适配器
  （`provider_volc_duplex.go`、`provider_dev_echo.go`），接口是诚实的
  - **【2026-09-20 更正】** 原文把这条正例写成 `DuplexTransport` —— 那是 `97_` 里**从未实现**的
    设计接口，写本文时把它当成了既存类型。正例本身成立，名字错了；照这个名字去找会找不到东西
- ❌ 做错的：`RescueSynthesizer` 最初按"返回 URL"设计，而**没有任何实现存在**——
  接口的形状是凭想象定的，后来真实现做出来时接口必须改
**防护**：接口的每个方法都指得出一个生产调用点。指不出的删掉。

### R5 · 先写契约测试，再写实现

**症状**：跨进程/跨包的调用，测试用的是手写的响应体。
**动作**：**驱动真 handler**（真 HTTP、真路由、真鉴权）。
**案底**：B8 信封 bug——客户端按 `{"data":{...}}` 解，测试 fixture 犯了同一个错，
所以它**替 bug 打了掩护**。
**防护**：这条已经在两处落地（`hit_writeback_test.go`、`rescue_client_test.go`），
写进规范即可。

### R6 · 依赖方向写下来，并且能跑

**症状**：包名与实际角色不符（`poc` 装生产代码）；层与层之间可以随意 import。
**动作**：把方向写成**判据**，能 grep、能 CI 检查。
**案底**：`docs/88` 的「功能包不得 import 厂商 SDK」就是一个可执行的判据。
**防护**：`go list -deps ./internal/voicegateway | grep voicepoc` 应为空（`98_` D4）。

### R7 · 踩过的坑，修法要落在**结构**上

**症状**：真机发现的问题，修法是"在这个调用点加一个分支"。
**动作**：问一句「这个坑的形状是什么」，然后让**形状**不可能重现。
**案底**：透明重开丢音频 → 序号在 provider 上。修法当时是搬运（`carryAudioSequence`），
形状（"序号属于易失对象"）还在。正确修法是让序号属于**会话**。
**防护**：`devnotes` 硬规则「同一个坑出现第二次 = 规范失效，必须产出防护」。

## 四、怎么让这些不停留在纸面

文档不产生约束，**机制**才产生。本项目的四条杠杆，按性价比排序：

| # | 杠杆 | 拦什么 | 成本 | 现状 |
|---|---|---|---|---|
| L1 | **接缝声明**（R1，写进 PR 模板） | 动手前就暴露"这跨了几层、状态归谁" | 3 行字 | **缺** |
| L2 | **契约测试驱动真 handler**（R5） | 信封/字段漂移；fixture 替 bug 打掩护 | 每个接缝一次 | 有两处先例 |
| L3 | **架构判据**（R6，`go list -deps` 之类） | 依赖方向被破坏 | 一条测试或 CI 步骤 | 有一处（`docs/88`） |
| L4 | **一致性 / 推导测试**（R2、R3） | 两份实现漂移、常量复制 | 小 | **缺** |

**为什么 L1 最值钱**：它是唯一在**问题发生之前**生效的一条。
L2–L4 是事后拦截，L1 是事前不犯。

**L1 具体长什么样**（放进 PR 模板，四行）：

```markdown
## 接缝
- [ ] 本次新增/修改的接缝：<HTTP / 包 / goroutine / 表示 / 层>
- [ ] 每条接缝上的状态，所有权归：<包 or 类型>
- [ ] 不变量：<什么必须永远成立>
- [ ] 证明：<哪个测试会在它被破坏时变红>
```

最后一行是**关键**：写不出测试的不变量，说明它不是不变量，是愿望。

## 五、现有资产与缺口（诚实盘点）

**已经有的**（不要重复建设）：

| 资产 | 覆盖 |
|---|---|
| `devnotes` 防复发规则表 1–6 | 组件接线、阈值断言、可注入时钟、写入方、单实现、先 grep 调用方 |
| `docs/88_` 接缝契约（LLM provider） | R6 的完整示范 |
| v1 schema 冻结测试 | 协议接缝的硬约束 |
| `hit_writeback_test.go` 等真 handler 测试 | R5 的先例 |
| `devnotes` 硬规则（二次踩坑必须出防护） | R7 |

**缺的**：

| 缺口 | 后果 |
|---|---|
| **接缝声明**（R1） | 接缝在无人察觉时被创建（本轮的 WSS/TTS 就是这样） |
| **一致性测试**（R2） | "目前恰好一致"的两份实现没有保护 |
| **推导测试**（R3） | 常量复制不会被发现 |
| **架构判据的普遍化**（R6） | 只有 LLM 那一条接缝有；语音链路没有 |
| **周期性接缝审计** | 防腐层审计（`d81e41d`）是一次性的，不是节奏 |

### 5.1 最硬的一条证据：那条接缝**被点名了，然后没人管**

`d81e41d` 的提交正文写着：

> 防腐层审计发现三处泄漏，本轮处理两处（**第三处是语音协议，单独评估**）

`docs/88_` §3.3 也专门写了这件事：

> 语音是另一条链路，接缝是 `VoiceProviderSession` 接口……但下面的火山双工协议
> （**二进制分帧、事件名、会话配置**）换厂商要重写 provider

**注意这句话里的三个词：二进制分帧、事件名、会话配置。**
`94_` 审核报告里最重的几条，正好落在同一个地方：

| `88_` 点名的 | `94_` 实际发现的 |
|---|---|
| 二进制分帧 | 帧编码有两个实现、帧大小常量 4 个 |
| 事件名 | turn outcome 跨包比较、`unknown event name` 那个坏掉的兜底 |
| 会话配置 | `poc` 包里的生产传输层、默认 speaker 已失效 |

**所以问题不是"没人想到语音这条接缝"——是想到了、点名了、然后没有下文。**

那次审计本身是有效的（消掉了 `reviewgen.ArkGenerator` 那条并行路径，
reviewgen 445 → 218 行）。它失效的地方在**收尾**：被推迟的第三项
没有归属人、没有复查日期、没有触发条件。

这是比"没有审计"更值得警惕的形态：**审计过一次的地方会给人一种已经审过的错觉。**
一条被推迟且无人跟踪的接缝，比一条从未被提及的接缝更危险——
因为再有人提起时，答案会是"那个审过了"。

### 5.2 机制缺口：强约束都挂在"修复"那一侧

`AGENTS.md` §6「缺陷修复纪律」是**强制的**，而且有机械检查
（`check-defect-discipline.sh` 在 `dev-check.sh` 最后一步跑）。它规定：

> **任何"有人报告了一个问题"的修复，必须先有一个能复现它的失败测试。**

这条很好，但它**只管修复**。它的开头那半句就是范围：

| | 修复路径 | 新建路径 |
|---|---|---|
| 触发 | "有人报告了一个问题" | "要做一个功能" |
| 强制要求 | 先写会红的测试 | **无** |
| 机械检查 | 有 | **无** |
| 结果 | 坑修得漂亮 | **坑被制造出来** |

**这就是为什么 build 过、test 过拦不住：**
新功能这条路没有任何与 §6 同等强度的要求，而 `94_` 里那九条恰恰全部长在新建路径上。

本项目的防御体系有一个**系统性的偏向**：修复侧强、新建侧弱。
它解释了今天看到的几乎所有现象——不是纪律没用，是纪律只覆盖了一半。

## 六、节奏建议（不增加会议）

| 时机 | 动作 | 时长 |
|---|---|---|
| 每个 PR | 填「接缝」四行（L1） | 3 分钟 |
| 每个新模块/新链路动工前 | 写一份接缝契约（照 `docs/88` 的形状） | 半天 |
| 每月（搭 `reflux-report.sh` 的车） | 挑**一条**接缝做审计：找并行实现、找两处定义 | 1 小时 |
| **审计被打断时** | 推迟的项必须写下：**归属人 + 复查日期 + 触发条件**，进 devnotes 未解决清单 | 2 分钟 |
| 每个真机坑修完 | 问「形状是什么」，把防护落在结构上 | 已在硬规则里 |

**每月一条接缝**：一年 12 条。本项目的接缝数量是个位数到十位数，
**一年能全审一遍**。这比"以后注意点"具体得多。

---

## 七、一句话总结

> **别在函数层面要求更好，在接缝层面要求存在。**
>
> 一个接缝被创建时，必须有：一个所有权声明、一个不变量、一个会在它被破坏时变红的测试。
> 这三样东西的成本是几行字，而它们拦住的，是今天 `94_` 里那九条发现。
