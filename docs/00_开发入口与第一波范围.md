## 二、第一波的目标

第一波只聚焦下面这条最小服务端闭环：

1. 签发游客身份
2. 创建 session
3. 建立 voice-gateway WSS 握手
4. 完成最小会话收发
5. `session.end` 后落库
6. 触发 review 异步任务并可查询状态

一句话概括：

> **第一波的 backend 目标不是把所有业务模块铺开，而是把 session / gateway / review 这条最小闭环站稳。**

## 六、第一波的代码边界

### 当前应该优先改的区域

1. `account` 中的 guest / merge
2. `session` 创建入口
3. `voice-gateway` 握手与协议骨架
4. `session.end` 最小落库
5. review worker 最小消费链路
6. review 查询接口
7. 文本降级接口占位

### 当前不应该抢先展开的区域

1. corpus 全模块
2. drill 全模块
3. content / daily reads / topic cards
4. billing 真正实现
5. 广泛 deploy / infra 抽象
6. 与第一波无关的大规模目录重构

---

## 七、必须遵守的禁区

1. 不模糊 `app-server` 和 `voice-gateway` 边界
2. 不把第一波目标扩张成完整业务单体
3. 不跳过游客身份与 `merge`，否则会破坏演示主路径
4. 不让 review 异步任务阻塞主链路
5. 不把非核心链路失败升级成主链路失败

---

## 八、提交与评审口径

1. 每个 PR 尽量只对应一个 backend issue 或一个 PR 级任务
2. 契约变化、schema 变化、状态变化应同步补测试或补文档
3. 若 iOS 依赖某接口，优先保证契约清晰，不用临时魔法值凑通
4. 若发现 PRD / 技术方案口径冲突，应先回写 `meta`，不要在本仓私下定案
5. 第一波能力是否可放行，以 `fluentwork-meta/docs/50_测试与验收/51_FluentWork第一波能力验证与第二波薄弱点检查门禁.md` 的门禁证据为准

---

## 九、最终口径

`fluentwork-backend` 当前第一波开发的标准口径应统一为：

1. 先做 guest / session / gateway / review
2. 只打通“session -> WSS -> session.end -> review 状态可查”最小闭环
3. 不复制上游真源，只在本仓保留开发入口索引

---

## 十、第一波遗留的功能薄弱点（供第二波承接）

1. 第一波的 `review` 异步链路只站稳了“可查状态”，没有站稳“真实生成结果”，所以回顾能力从功能上仍是骨架，不足以支撑完整产品闭环。
2. `voice-gateway` 在第一波以协议骨架为主，真实供应商接入、延迟指标、降级切换都未闭环；如果第二波不优先偿还这笔欠账，主路径的可发布性仍然存疑。
3. 文本降级接口只是末级兜底占位，不代表实时对话主链路已经足够稳；第二波仍需把它放在“最后保底”位置，不能反向驱动主架构。
4. 第一波未进入 `corpus` / `content` / `badge`，导致服务端虽然能把会话收尾，但还不能把结果沉淀成可复用语料、可消费内容和可见反馈；这正是第二波的真实功能缺口。
5. 第一波没有建立 `ai_cost_logs` 写入与 Prompt 回归基线，意味着第二波一旦接入真实 LLM，如果不补账本与回归，功能能跑但质量和成本都不可控。
