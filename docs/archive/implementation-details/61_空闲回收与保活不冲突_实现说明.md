# 保活与"空闲回收"：不是互相抵消，是名字错了

**日期**：2026-09-11
**状态**：实现与文档已齐。
**对应**：meta `77_` **P1-17**

## 1. 台账的诊断，核实后不成立

`77_` P1-17 写的是：

> 客户端每 30s 的应用级心跳，让网关那个 2 分钟读空闲超时**永远不会触发**。两个各自合理的设计合起来让其中一个失效。

**读代码之后，结论要改。** 那个超时不是"空闲回收"，它是**半开连接探测器**：

```go
for {
    readCtx, cancel := context.WithTimeout(ctx, h.idleTimeout)  // 2 分钟
    typ, data, err := conn.Read(readCtx)
    ...
}
```

它界的是**每一次读**。心跳每 30s 重置它一次，所以它**只可能在客户端停止发送时到期** —— 也就是客户端已经没了的时候。**那正是它的职责，而它在履行。**

台账说"永远不会触发"只在**客户端活着**时成立，而那时它**本来就不该触发**。

## 2. 真正的问题：`idle_timeout` 这个名字承诺了一个它看不见的类别

到期时记的退出原因是：

```go
case errors.Is(loopErr, context.DeadlineExceeded):
    reason = "idle_timeout"
```

**`idle_timeout` 说的是"用户空闲"，而机制只能观察到"连接沉默"。** 一个连着、一直在 ping 的客户端，无论用户多久不说话，都不会触发它。

后果很具体：**读会话记录的人会去一个只装尸体的列里找"空闲用户"。** 那一列里永远不会有活人。

## 3. 按业界惯例的处置：两个机制都留，改名字

| 机制 | 标准角色 |
|---|---|
| 客户端 30s 应用级 ping | **NAT 保活 + 活性**（每个生产 WebSocket 客户端都这么做；去掉它会破坏 NAT 穿透） |
| 服务端读超时 | **半开连接探测**（对端静默消失、没有 FIN 时兜底） |

**两者互补，不冲突。** 所以处置不是删掉一个，而是**让名字说它实际检测的东西**：

- `idle_timeout` → **`connection_silent`**

**为什么改得起**：旧值描述的是一个**没有任何路径能到达**的状态（在有心跳的前提下），所以不存在"历史数据可比性"的代价 —— 那一列里本来就没有值。

**顺带记清楚一件没有实现的事**：**"回收一个连着但不说话的用户"是一个独立能力，当前不存在。**
客户端持续 ping 会让会话（连同上游 vendor duplex）一直开着，直到用户离开。
这条写进了 `defaultIdleTimeout` 与 `Options.IdleTimeout` 的声明处，也写进了本文 ——
**免得下一个人把这个旋钮读成它做不到的东西。**

## 4. 为什么不在这一票里实现"用户空闲回收"

那是**产品行为**，不是缺陷修复：多久算空闲？结束会话会不会打断用户回来接着说的预期？
上游 duplex 的计费要不要成为驱动因素？——这些没有业界唯一答案，取决于产品要不要。
本票只负责把**现有的**机制说准，并把缺失的能力**登记为缺失**。

## 5. 测试与门禁

```bash
./scripts/dev-check.sh      # All checks passed.
```

本票是**语义与命名的更正**，不改变任何运行时行为：超时值不变、触发条件不变、连接生命周期不变。
唯一变化是会话记录里那个 `reason` 字符串的取值。

按 `agents/shared/defect-fix-discipline.md` 的例外一（**能力/语义标注，没有"失败"可复现**）：
旧的 `idle_timeout` 在任何测试里都不会红 —— 它不会红**正是因为**那条路径不可达，
而那正是要修的东西。**红/绿不适用于本票。**

## 6. 未做

- **没有实现用户空闲回收**（§4）—— 它是独立能力，且需要产品定义。
- **没有动心跳间隔或超时值**。两个数都是对的。
- **没有给"连接沉默"加新的可观测性**。它本来就会写进会话记录，只是换了个名字。
