# 继续上次：让新会话带着上一场的尾巴开场

**日期**：2026-09-12
**状态**：代码与测试已齐。**未真机验证** —— 判据是「新会话的第一句是否自然承接上一场」，只有真机能回答。
**对应**：meta `77_` **P0-10**（「昨天那场，今天进不去也聊不了」）

## 1. 为什么

用户的原话：「需要确认比如昨天的对话，我今天还能进去聊吗？」

**三层不能**，其中第三层是本票修的：

| | |
|---|---|
| ① 客户端进不去 | ios 侧，只读记录页刻意不通向房间（`ios docs/64` §2）|
| ② 服务端**恢复不了**那一场 | `77_` P1-15 已核实：无会话查找、票据一次性、`auth` 帧带不了 `session_id` |
| ③ **退路「新会话 + 带上旧上下文」也接不了** | **本票修的就是这一层**，见 `77_` P1-25 |

③ 之前接不了，是因为 `session.start` **两端字段名零重叠**（客户端发 `scene`，网关解 `scene_type`）—— 连「场景」都没送进过模型。本票先把这个对齐，再让它多带一样东西。

**这是「续接」，不是「恢复」。** 服务端仍然开一场全新的会话；变的只是**开场时模型知道上一场聊了什么**。这两件事必须分开说，否则下一个人会以为 ② 被修好了 —— PRD `21` §今日入口卡把这件事叫「继续上次（V1.2）」，写的正是「进房间后 AI 首句总结上次讨论」，本条兑现的是它。

## 2. 契约：**送 id，不送内容**

```
session.start { ..., "continue_from_session_id": "<上一场的 session_id>" }
```

这一条是本票唯一的设计决定，两个理由都独立成立：

1. **客户端不该能写 system prompt。** 如果改成「客户端把摘录发上来」，那句摘录会直接进指令 —— 任何拿到 token 的客户端都能往模型的系统提示里塞任意文本。
2. **转录必须留在服务端一手可见**（`77_` §0 已定的架构立场）。而且**数据本来就在服务端**（`practice_sessions` + `utterances`），让客户端把它读出来再发回来，是多一次往返、多一份可能不一致的副本。

## 3. **归属校验放在 app-server**，不在网关

`continue_from_session_id` 来自**客户端写的帧**，所以它指向谁都由客户端说了算。不校验 = 任何已登录用户可以点名**别人**的会话，把对方的转录拉进自己的模型上下文，然后直接问它说了什么。

校验需要两样东西，而它们分处两边：

| 需要 | 谁有 |
|---|---|
| 当前会话的 owner | app-server（票据是它签发的）|
| 上一场的 owner | 只有 store |

所以它**只能**发生在 app-server：新增内部端点
`POST /internal/v1/sessions/continuation-context`，body 带**两个** id。

**拒绝的答案与「没找到」逐字节相同**（都是 `NOT_FOUND`）。告诉调用方「这个会话存在但不是你的」，本身就是泄露。有一条测试逐字段比对这两种答案。

## 4. 取**尾巴**，不是开头

「上次聊到哪」是对话的**末尾**。截断一场长会话时，开头是最不相关的部分。

默认 6 轮、上限 20 轮（`continuationDefaultLimit` / `continuationMaxLimit`）。上限存在的理由：这段文字**逐字进 system prompt**，而 `limit` 来自客户端写的帧 —— 不封顶就是一条「把开场轮做贵」的路径。`limit <= 0` 读作「未指定」而不是「不要」，否则所有不设这个字段的客户端会静默地失去这个功能。

### 一处**没有**加的守卫，以及为什么

读路径**没有**过滤空文本、也不再 trim 一次。`normalizeEndUtterances` 保证文本非空且已 trim、speaker 只会是 `user`/`ai`，而 `store.EndSession`（它唯一的调用方）是**唯一**写 utterance 行的地方。

加了就是**看起来在防守什么的死代码**，比不加更糟：下一个读它的人会以为行可能是空的。（第一版真加了，测试写不出来 —— `End` 会拒收空文本 —— 于是删掉，改为把这条不变量记在注释里。）

### 一处**已知但没修**的边界

单轮上限是 32 KiB，所以最坏情况是 `limit × 32 KiB` 进 prompt：默认 6 轮约 200 KiB，上限 20 轮约 640 KiB。**当前没有任何东西能走到那里**（网关固定传 0 → 取默认 6），所以没加总预算。**将来调大 limit 的那一刻才是加它的时机**，注释里写着这句。

## 5. 顺带修掉的一处同类静默丢失

透明重开（B15-followup）用**空的** `SessionStart` 重开会话：

```go
reopened.Start(ctx, voiceproto.SessionStart{})   // 改前
```

那意味着重开之后**场景、素材全没了** —— 而重开是 10% 的轮次会撞上的路径（`77_` P0-9）。本票给 `sessionRuntime` 加了 `lastStart` / `continuation`，重开时原样重放。

**这是同一个家族的第二例**：会话在重开时丢掉「它是什么」。P0-9 记的是厂商侧那一半（上下文），这一句是 app 侧这一半（场景与延续）。

## 6. 一处**刻意没做**的：不写死开场白

指令块陈述事实、然后**要求一个行为**：

```
这是同一用户的上一场练习，以下是它的末尾几轮对话（最早在前）：
user: how do I say 限流?
ai: Rate limiting.
开场时用一句话自然承接上面聊到的内容，让用户知道你还记得，然后继续这次练习。
```

**没有**写「请说：上次我们聊到 X」。PRD 里那句「上次我们聊到限流方案，今天继续？」是模型**应该从转录里得出**的，写死会变成一句无论说得对不对都会出现的话。有一条测试断言指令里**不含**「上次我们聊到」。

`speaker` 原样写进 prompt，不查表翻译成中文 —— 一个没见过的值带着自己的名字进 prompt，比被贴错标签好。

## 9. 真机判据

1. 开一场，说几轮，结束。
2. 从列表点进那一场 → 继续。
3. **期望**：AI 第一句自然带出上一场聊的内容（不是「你好，我们开始吧」）。
4. 日志 `voice.handshake` 之后应有 `continuation context resolved ... turns=N`；`turns=0` 或没有这行，说明要么没送 id、要么解析失败（会同时有一条 `continuation context unavailable` 的 warn）。
5. **反面对照**：不走「继续」直接开新会话，第一句不应带上一场的任何内容。

> 本票把「继续上次」的**地基**补上了：`session.start` 从此能带上下文，而且带的是**服务端认过的**上下文。
> 它**不**交付「回到昨天那一场」—— 服务端仍然恢复不了会话（`77_` P1-15），那是另一件事。
> 客户端入口（列表 → 继续 → 带上 id）在 iOS 侧，与本票是同一次交付的两半。
