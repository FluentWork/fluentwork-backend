# 上游 duplex 连接寿命：判别实验

**日期**：2026-09-11
**对应**：meta `77_` **P0-9**
**状态**：**实验已备好，未跑。** 本文只写「跑什么、看什么、怎么读」。

## 1. 要回答什么

一场练习会话里，上游（火山）duplex 会话被重开 = **上下文丢了**。重开本身是恢复逻辑，没错；
错的是**没有任何东西把历史补回来**，于是用户看到的下一轮 AI「不认得上一轮说过的话」。

## ⚠️ 0. 先读这一节：本文档的第一版结论是**错的**

第一版在 4 个数据点上得出结论「**空闲时长就是自变量**」。把两份日志（重启前 + 重启后）的
**全部**样本配对出来之后，它被推翻了：

```
轮末 → 恢复说话之间的静默, 以及那次写入的结果
  成功   2.6s … 1436.2s   (61 次)   ← 一次 24 分钟的静默, 照样通
  失败  30.2s …  184.8s   ( 7 次)
```

**两段完全重叠。** 所以下面这些**都不解释死活**（逐条实测过）：

| 候选 | 实测 | 判 |
|---|---|---|
| 轮间静默时长 | 成功侧 2.6–1436s，失败侧 30–185s | **重叠，否定** |
| 会话总时长 | 一次 **364.8s / 10 轮** 的会话活到底；而 50.4s 的死了 | **否定** |
| 轮数 | 重开前有 1 / 2 / 3 / 4 轮的，无模式 | **否定** |

**发生率约 10% 的轮次**（7 / ~68 次轮开始），与静默、时长、轮数都无关。

**为什么会看错**：4 个样本里「间隔越长越容易死」的样子很合直觉，而且它正好符合
`keepaliveIdleThreshold` 那个已知常量 —— 一个**能自圆其说**的假说比一个空假设更容易被接受。
真正做对它的代价只是**把全部样本配对出来**，而那本来是十分钟的事。

**这条教训比结论本身值钱**：`--gaps` 那个输出会诱导人只看「重开前那一次有多长」，
而不去看「撑住的那 61 次有多长」。**没有对照的分布，就是没有分布。**

## 1. 于是现在要回答什么

不再是「阈值是多少」，而是：

> **什么情况下这台连接会死？** 静默、总时长、轮数都排除了。

候选（尚未测）：厂商侧的会话寿命/错误、代理的按连接启发式回收、我们自己的写入序列
（`input_audio_mute.commit` / `sendSilence` / `response.create` 的某种组合）、以及并发或时序竞态。

**判别手段仍是同一个检查器 + 传入了更多字段的日志** —— 只要把「重开前那次写入」与
「撑住的那 61 次」放在同一张表里比，而不是只看前者。

## 1.1 为什么现在**看不到**死因（读侧真空）

查了一遍代码，死因查不出来不是样本不够，是**观测点不存在**：

| | |
|---|---|
| **两轮之间没有人在读** | `recv()` 的调用点只有 `Open`、两处 drain、`collectTurn`、以及公开的 `Recv`。对端关闭时那个 close frame **躺在缓冲区没人看**，直到我们下一次写入才以 `broken pipe` 暴露 —— 我们看到的永远是「写失败」，不是「它关了」 |
| **关闭码被丢掉** | 读侧错误在 `collectTurn`（`provider_volc_duplex.go:687`）被归成 `ErrDuplexClosed` 就走了。`websocket.CloseError` 里的 **code 与 reason 一个字都没进日志** —— 而那正是区分「厂商主动关」与「中间盒掐断」的**唯一直接证据** |

**所以「谁关的、什么时候关的」从来没有被观测过。** 加一个空闲期的探活读者是显然的修法，
但：`coder/websocket` 只允许**一个**并发读者，而写路径（`HandleClientAudio`）与读路径
（`collectTurn`）在不同阶段跑，探活读者**有和对端读撞车的风险**；撞车的后果是 panic 或流损坏，
而这是**通向付费链路**的路径。

**结论：那是一条需要自己设计的改动，不是顺手打的补丁。** 在它落地之前，
**实验 D（绕过代理）是唯一不需要写代码就能给二值答案的手段**，优先级高于继续攒样本。

## 2. 为什么不需要精确控制间隔

**因为日志里有时间戳。** 间隔不需要跑准 —— 跑完用检查器把**实际**间隔算出来即可。
所以实验是「跑几次不同量级的间隔 + 用工具读日志」，而不是「写一个能精确控制时序的驱动」。

检查器已经把这件事固化了（`session_id` 在本仓日志里**指两个不同的东西**，这是最容易读错的地方）：

```bash
./scripts/check-duplex-lifetime.py --gaps /tmp/fluentwork-backend.log
```

exit 0 = 每个会话窗口只开了一次；exit 1 = 发现重开。`--gaps` 追加那一列「轮间静默」。

## 3. 跑什么

**跑之前**：确认日志是这一次的（陈旧文件会让结论无效，见 `ios docs/62` §0 第 5 项），必要时归档旧的。

```bash
mv /tmp/fluentwork-backend.log /tmp/fluentwork-backend.log.$(date +%H%M)
# 重启栈，输出接到手册期望的路径
./scripts/dev-up.sh --local-mysql --skip-migrations --host 192.168.2.111 > /tmp/fluentwork-backend.log 2>&1
```

**⚠️ 下面这套按间隔分格的实验设计已经作废** —— 它是建立在「静默时长是自变量」之上的，
而那个前提被推翻了（见 §0）。把它留在这里是为了记录**为什么它看起来那么合理**，
以及**下一次不要再按一个未经验证的前提去设计分格**。

| ~~#~~ | ~~间隔~~ | ~~目的~~ |
|---|---|---|
| ~~A~~ | ~~~15s~~ | ~~预期不重开~~ —— 真机数据里 15s 级和 30s 级都有通有死，无判别力 |
| ~~B~~ | ~~~35s~~ | 同上 |
| ~~B′~~ | ~~~25s~~ | 同上 |

**改成什么**：不再按间隔分格，而是**攒样本**。每跑一场真机会话，用检查器把
「每一次轮开始的静默 + 结果」记进同一张表；等失败样本从 7 个涨到几十个，
再去比两组的**其他**维度（厂商侧会话年龄、上一轮回复长度、是否刚发生过 mute/unmute、
并发连接数、代理侧状态）。**先攒够失败样本，再谈假说。**

| # | 做什么 | 目的 |
|---|---|---|
| **C**（仍然有效） | 一次会话里**故意长时间不出声**（几分钟） | 它现在问的是「长静默到底会不会死」—— 已有 1436s 存活的证据说**不会**，但样本只有一个方向，值得再压一次 |
| **D**（优先级最高） | 让火山域流量**绕过代理**再跑 | 代理仍在候选名单上，且这条不需要攒样本就能给一个二值答案。见 §3.1 |

### 3.1 D 怎么跑（本机是 FlClash / Mihomo）

本机到火山的那条连接**穿过一个 tun 代理**（`utun7` 持 `198.18.0.1`，fake-IP 特征；
进程是 `/Applications/FlClash.app` 的 `FlClashCore`）。厂商域名是
**`openspeech.bytedance.com`**（`voicepoc/volc_duplex.go:21`）。

**⚠️ 不要靠「停很久」去触发它。** 自变量不是静默（见 §0），
**要靠轮数** —— 约 10% 的轮开始会撞上，所以分母要够。一场正常的多轮对话跑 30 轮以上，
按 10% 期望能看到 ~3 次。

```bash
# 0) 基线就在手边: 当前两份日志 7 / ~68 ≈ 10%
./scripts/check-duplex-lifetime.py /tmp/fluentwork-backend.log /tmp/fluentwork-backend.log.pre-aec

# 1) FlClash 里加一条规则, 只把这一个域名放行, 其它照旧
#    DOMAIN-SUFFIX,openspeech.bytedance.com,DIRECT
#    (改完在 FlClash 里重载配置)

# 2) 归档旧日志, 重启后端 —— 必须重启
mv /tmp/fluentwork-backend.log /tmp/fluentwork-backend.log.beforeD
./scripts/dev-up.sh --local-mysql --skip-migrations --host 192.168.2.111 > /tmp/fluentwork-backend.log 2>&1

# 3) 真机跑一场, 说 30 轮以上(不需要故意停顿)

# 4) 读结果
./scripts/check-duplex-lifetime.py --gaps /tmp/fluentwork-backend.log
```

**为什么必须重启**：到厂商的 TCP 连接是**在旧路由下建立的**，而路由规则只影响**新**连接 ——
不重启的话，实验跑的还是老路径，结论无效。（这与代码无关，纯粹是连接生命周期。）

**怎么读**：

| D 的结果 | 结论 | 修法 |
|---|---|---|
| 不再重开（或明显低于 10%） | **中间盒**掐的空闲连接 | 防止空闲即可（探活 ping 就够）；生产在机房、无此中间盒，不受影响 |
| 照样重开（仍约 10%） | **厂商侧** | `input_mod: "keep_alive"` 成为正当候选（官方对错误码 `52000042` 明确建议用它） |
| 重开但更频繁 | 说明放行反而有害 | 先把规则撤掉，再回头查 |

> 分母要记下来（多少轮 / 多少次重开），否则「明显低于 10%」是不可判的。
| **C** | ~35s，**间隔期间持续出声/发音频** | **判别实验的本体**。字节在流的情况下若**不再重开** → 杀连接的是「空闲」，且**修法（轮间发静音）成立**；若**仍然重开** → 指向中间盒或另有机制 |

**C 怎么做到「持续发音频」**：真机上两轮之间保持说话或哼声即可 —— 客户端在语音窗口内会持续上行，
网关也就持续写上游。**注意这会让厂商的 VAD 认为用户在说话**，可能触发一轮新对话 ——
那本身也是信息（说明「发音频」和「保持静音」在协议上是两件事）。

**可选的 D（更干净的判别）**：让火山域的流量**绕过代理**再跑一次 B。
- B 重开、D 不重开 → **中间盒**。生产（无代理）不受影响，本地开发环境要单独说明。
- B、D 都重开 → **厂商侧**，`input_mod: "keep_alive"` 是正当候选。

## 4. 怎么读

```bash
./scripts/check-duplex-lifetime.py --gaps /tmp/fluentwork-backend.log
```

输出里只要看两处：

- **`duplex 开了 N 次`** —— N > 1 就是上下文丢了，这一场之后的所有轮次都算废
- **`轮间静默`那一列** —— 与它上面那行有没有 `← 这次之后重开`

**读的时候别踩这个坑**：`session_id` 在 `voice.duplex.*` 里是**厂商侧**会话 id，
在 `turn result captured` 和重开那行里是**我们的 app** 会话 id。
两者都是 uuid 形状、都叫 `session_id`，当成一回事会得出完全相反的结论
（比如把「provider 换了」读成「用户换了会话」）。检查器是按这个区分分组的。

## 5. 结论怎么写回台账

按 `77_` 的老规矩：**贴原始输出，不贴转述**。特别是**不通过那次的** —— 它是唯一能回放的东西。

三行足够：

1. A/B/C 各自的**实际**轮间静默（检查器的数字）+ 有没有重开
2. 若跑了 D：D 的结果
3. 一句话结论：死因是空闲（→ 修法：轮间发静音）/ 是中间盒（→ 本地环境单独说明，生产待观察）/ 另有机制（→ 重开一票）

> **`docs/53` §5 那条「未核实」现在可以更新了**：它问的是 `input_mod: keep_alive`
> 「是不是 mute/unmute 事件的前置条件」。目前**没有任何证据支持它是前置条件** ——
> 而**发了静音事件之后连接照样死**，这本身就是一条证据。
> 至于它是不是一条**有效的备选修法**，取决于本实验 A/B/C 的结论，不取决于它是不是前置条件。
