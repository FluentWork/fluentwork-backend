# 音频流的终止标记：不能靠"没声音了"来推断

**日期**：2026-09-11
**状态**：后端已实现并测试。**iOS 消费半边见 §6。**
**对应**：meta `77_` **P1-16**

## 1. 为什么

`ai.tts.end` **只有本地 mock 会发**。生产路径上它从不出现，于是客户端**无法从协议上**区分：

| | 客户端看到的现象 |
|---|---|
| AI 说完了 | 音频不再到达 |
| AI 卡住了 | 音频不再到达 |

**两者长得一模一样。** 台账把后果写得很准：*"实现者会用**计时器去逼近一个信号**，而两者不等价。"*
计时器对每一条回复都**要么早要么晚** —— 它不是信号，是一个猜测。

## 2. 这是被反复踩过的经典错误

**流需要一个显式的终止符。** HTTP chunked 用长度 0 的块、SSE 用 `[DONE]`、WebSocket 用 close frame ——
没有一个协议是靠"对面不发东西了"来判断流结束的。

本票就是那条规范在语音链路上的实例。

## 3. 为什么现在能发，而 `ai.tts.start` 不能

P1-21 核实过：`ai.tts.start` **必须不发**。`TTSFrameDispatcher` 只在见过它之后才认领二进制帧，
而绑进它的解码器不驱动 `AVAudioEngine` —— 发了会把音频从"真的出声"挪到"只记录不出声"。

**`ai.tts.end` 不一样，而差别正好在解码器那个状态机上：**

```swift
case let .aiTTSEnd(turnID, completionStatus, durationMs):
    switch stream {
    case .idle: return            // ← 没发过 start，就永远走这里
    ...
```

`stream` 只在见过 `ai.tts.start` 之后才变成 `.active`。**既然 start 从不发，end 就落在 `.idle` 分支 —— 一个 no-op。**

所以它加了一个终止符，**而没有把音频挪到解码器那条路上**。

## 4. 发什么、什么时候发

在 `turnToOutbound` 组装完音频**之后**：

```go
outbound = append(outbound, ProviderOutbound{Control: voiceproto.AITTSEnd{
    Type:             voiceproto.TypeAITTSEnd,
    TurnID:           canonicalTurnID(s.activeTurnID, s.nextSeq),
    CompletionStatus: ttsCompletionStatus(turn.Outcome),
    DurationMs:       audioDurationMs(len(turn.AudioPCM)),
}})
```

三个决定：

1. **必须在音频之后。** 一个抢在流前面的终止符**比没有更糟** —— 它以权威的口吻告诉客户端"结束了"。
2. **没有音频的轮次也发。** "说完了但没什么可说"和"还在进行"是两件事，只有一件是问题。
3. **`duration_ms` 是精确的**：vendor 输出固定 24 kHz 单声道 s16le，所以字节数就是时长
   （48 字节/毫秒）。不估算。
4. **`completion_status` 复用 `turn.Outcome`**，为空时回落 `"ok"` —— 空字符串会读成"未知"，
   而"未知"正是这个标记存在的意义要排除的那一种。

## 5. 测试

`internal/voicegateway/provider_tts_end_marker_test.go`，两条：

| 测试 | 守什么 |
|---|---|
| `…TerminatesTheAudioStreamAfterTheAudio` | 恰好**一个**终止符；**在最后一帧音频之后**；`turn_id` 对得上；`duration_ms` 精确（48000 字节 → 1000ms） |
| `…StillTerminatesWhenThereIsNoAudio` | 静默轮次也发终止符 |

### 红验证（两次，第二次抓出我自己的测试漏洞）

**第一次**把标记挪到音频**之前**（只留一个）→ 红，信息精确：

```
--- FAIL: TestTurnToOutboundTerminatesTheAudioStreamAfterTheAudio
    provider_tts_end_marker_test.go:54: ai.tts.end at 0 precedes the last audio frame at 11
```

**但在此之前，我做了一次更弱的破坏 —— 在开头*加一个*重复标记 —— 而测试全绿。**
原因是循环里 `ttsEndIndex = i` **取最后一个**，两个标记时它取到的仍是对的最后一个。
**顺序断言对"多一个抢跑的"是盲的。**

所以补了"**恰好一个**"的断言，并用同一个破坏验证它真的咬得住：

```
--- FAIL: … provider_tts_end_marker_test.go:67: emitted 2 ai.tts.end markers for one turn, want 1
```

> 这一条值得单独记：**顺序断言与唯一性断言是两个维度。** 只断言顺序时，
> "正确的那条在最后"会让一个重复且抢跑的标记蒙混过去 —— 而那在客户端是"同一个流被结束两次"。

## 6. 影响面与未做

| 维度 | 影响 |
|---|---|
| **协议 / schema** | **零改动**。`ai.tts.end` 早已在 v1/v2 schema 里冻结 |
| **线上新增** | 每轮多一个控制帧（约 100 字节） |
| **音频路由** | **不变**（§3：`stream` 停在 `.idle`，end 是 no-op） |
| **iOS** | **已能解码并记录**：`tts_end` tracker 事件带 `turn_id` / `completion_status` / `duration_ms` / `audio_frames` |

**iOS 那半边是"已有消费者"，但不是"已消费"** —— 这一句要说清楚：

- **现在有的**：标记到达后会产生一条 `tts_end` 埋点，于是"这一轮的音频流**结束过**"在日志里成为**事实**，
  而不是从"音频不再到达"推断出来的。排查时可以问"有没有 `tts_end`"来区分**卡住**与**说完了**。
- **还没有的**：把这个标记喂给**状态机或播放路径**（例如用它来界定轮次边界、或驱动 P1-7 的水位线失效）。
  那是**独立的改动**，且要先有明确要用它的地方 —— 否则就是又一个"有生产、没消费"。

所以本票的产出是**把信号放上线路**（这一步是纯收益且不可回退），并把消费侧的缺口写明。
