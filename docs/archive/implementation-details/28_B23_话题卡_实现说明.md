# B23 话题卡实现说明

**对应 issue**：#49 / #84–#89  
**门禁**：`./scripts/dev-check.sh`（`gofumpt` / `goimports` / `golangci-lint` / `go test ./...` / `go build ./...`）

## 原理与背景

H1/H2/H3 要给活跃用户每天 3 张可说的职场话题卡，并支持打卡和连续天数。iOS（I18）只消费 `GET /topic-cards` 和 `POST /topic-cards/:id/checkin`。

每日一读的 D-5 批处理在 `content.RunScheduledGeneration` 里仍是骨架日志，`cmd/worker` 原先只消费 session review 队列。B23 不能再等一个还不存在的「B16 daily-broadcast cron」；在 worker 空闲轮询里挂 04:00 UTC 的 `RunIfDue`，本地 `APP_RUN_REVIEW_WORKER=1` 的 in-process worker 同样会跑。

B16 Orchestrator 仍未独立。生成走与 B18/B21 相同的 `Completer` 缝（`drill.NewArkCompleter`）。

## 方案

独立包 `internal/topic`。0007 只有 `daily_reads`，话题卡表不在里面，因此新增 `0015_create_topic_cards.sql`：`topic_cards` / `topic_checkins` / `topic_streaks`。

| API / 批处理 | 行为 |
| --- | --- |
| `GET /api/v1/topic-cards` | 当天 UTC `for_date` 的活卡；若还没有，则现场 `GenerateForUser`（方便本地无 worker） |
| `POST /api/v1/topic-cards/:id/checkin` | 归属校验、反射 ≤500 bytes、首次打卡 200、重复 409、跨用户 403 |
| Worker `RunIfDue` | UTC 小时 ≥ 4 且当天未跑过 → 最近 30 天有 `practice_sessions` 的用户各生成 3 张 |

生成：15s 超时、最多 3 次；失败跳过该用户并打 `topic_card_gen_skipped_total{reason}`。空标签分布仍调 LLM（prompt 写明用通用职场话题）。同一 `user_id+for_date` 已有卡（含 A4 软删）则不再插入，避免删除后 GET 再造一套、撤销出现 6 张。

打卡 streak 按 **UTC 日界**：连续昨天 → +1；中断 → 回到 1；同一 UTC 日第二次打卡不叠加。`longest_streak` 只升不降。

批处理并发上限 64（15s LLM 时 1000 用户可落在 10 分钟内）。没有做成 10 QPS 起步间隔：单测里那会把 200 用户拖成 20 秒以上，生产上 64 in-flight 更贴近 P95 预算。

A4：`topic.PrivacyWiper` 软删三张表；GET 看不到已删卡；`HasCardsForDate` 仍挡住重复生成。

## 缺口根因

票面写「0007 已包含 topic_cards」。实际 0007 只有每日一读。若按票去 ALTER 0007，会改历史迁移。B23 用 0015 补表。

D-5 cron 并不存在可复用的 TaskType。若只做 HTTP、不做 worker 钩子，04:00 批处理永远不会跑，只能靠 GET 现场生成，活跃用户不打开 App 就没有卡。

## 新方案理由

- **独立 topic 包 + 三张表**：卡、打卡流水、streak 聚合的变更速率不同；streak 按用户一行更新，不必扫 checkins。
- **Completer 而不是等 B16**：与 B18/B21 同一决策。
- **UTC 日界**：与批处理 04:00 UTC、`for_date DATE` 一致，避免按用户本地时区把同一批卡切到两天。
- **GET 可现场生成**：本地和无 worker 的环境仍能打通 I18；cron 负责「用户当天没打开 App 也有卡」。
- **软删计入 HasCardsForDate**：A4 是隐藏不是重做当天内容。

## 明确不做

- 真实用户时区 / 本地 04:00
- 给每日一读补完整 D-5 批处理
- 把 `topic_cards` 塞进 0007
