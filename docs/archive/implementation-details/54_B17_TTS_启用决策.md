# B17 TTS：启用决策

**日期**：2026-09-11
**状态**：决策已定。代码标记与测试落地见 §5。门禁见 §7。
**对应**：meta `77_` **P1-1** · 执行计划**步 7**

## 1. 决定

**标记未启用,不接线。** B17 保持"已建成、未通电"的状态,把这一状态**写进代码**,而不是只写在文档里。

## 2. P1-1 的风险是文档风险,不是代码风险

P1-1 的原话:

> `tts.Provider`/`Manager` 全仓只被 `tts.NewHandler(...)` 引用;`POST /internal/v1/tts/synthesize` 无人调用。**闲置代码会被误读成"已完成的能力"**

关键在于:**代码本身没有任何缺陷。** 1830 行实现 + 784 行测试,协议正确,错误映射正确,nil 降级正确。坏的是它的**存在暗示了一项能力** —— 有人读到这个包,会合理地认为"TTS 已经有了"。

**所以修法不是改行为,是把状态变得可读。** 这也是为什么本票的产出主要是注释和一个决策,不是功能。

## 3. 为什么不"接上"

接上需要两样东西,现在**一样都没有**:

| 缺什么 | 现状 |
|---|---|
| **消费者** | 每日一读的 `AudioURL` 字段**只有读写、没有生成者**(全仓 grep 确认);iOS 闪测在导航里只是一个 tab。这两个正是 B17 为之而建的下游 —— 它们都还没到能用 TTS 的阶段 |
| **生产授权** | prod SKU 返回 `403 / code=55000000`(meta `77_` **P2-4**,未关闭) |

**第二条是决定性的。** 即使今天硬接一个调用方,结果是一个**在 dev 通过、在 prod 失败**的功能 —— 比不接线更糟:它会把一个环境问题伪装成代码问题,消耗排查时间。凭据不到,接线就是给自己埋一个只在生产爆的雷。

## 4. 为什么不"删掉"

| 理由 | 说明 |
|---|---|
| **研究价值** | `docs/29` 里那条根因混淆(产品 SKU `seed-tts-2.0` 是 `X-Api-Resource-Id` header,而 voice 进 `req_params.speaker`)是踩出来的。删掉就要重踩 |
| **零运行时风险** | 没有调用方 = 不参与任何请求路径。它的存在**不会**让线上出错 |
| **回滚成本** | `0dcad87` 已收口。将来消费者到位时,接线是几行的事;重建是几天的事 |

### 代价(说清楚)

**它仍然占着维护面:** 1830 行实现 + 784 行测试每次 CI 都要跑、要过 lint、要跟着 Go 版本升级。`tts_fallback_triggered_total` 这个指标**永远不会被触发** —— 一个只存在于 dashboard 配置里、从没有数据的指标,是将来某次误判的来源。

**这个代价是可接受的**,因为它有界且已知;而"删掉后重做"的代价无界。

## 5. 代码里落了什么

### 包注释:`internal/content/tts/provider.go`

包注释原本写的是 `Package tts implements B17 TTS: ...` —— 一句话读起来就是"这是个可用的能力"。现在它开门见山:

> **Status: built, not turned on**
>
> Nothing calls this package in production. … Read this package as "built and tested but unexercised" — not as a capability available to callers.

并列出两条缺失(消费者、生产授权)与**降级契约**(未配置 → UNAVAILABLE,不是 panic)。

### 测试:钉住"未启用"时必须是安全的

标记的前提是:**没配凭证时,这个端点必须干净地失败。** 否则将来第一个调用方到达时,拿到的是 500 或 panic —— 那才是真事故。

| 测试 | 守住的 |
|---|---|
| `TestPostSynthesize_UnconfiguredProviderIsUnavailable` | nil provider + 合法 body → **503 / `UNAVAILABLE`** |
| `TestPostSynthesize_UnconfiguredOutranksMalformedBody` | nil provider + **畸形** body → 仍是 **503**,不是 400 |

### 红验证抓出来的东西

第二条测试不是设计出来的,是**第一条测试被证明是空洞的**之后才写出来的。

第一版只写了 `Unavailable` 那条。按惯例做红验证 —— 把守卫改成 `if h == nil` —— **它依然通过。** 原因:

```go
// Collect 自己也会挡 nil
func Collect(ctx, provider, ...) {
    if provider == nil { return nil, ErrClosed }   // → mapTTSError → 同一个 503
```

**两条完全不同的路径产出逐字相同的 503 与消息**,所以那条测试分辨不出守卫在不在。真正能区分它们的是**顺序**:没有守卫时,`ShouldBindJSON` 先跑,一个畸形 body 会得到 `400 INVALID_ARGUMENT`。于是有了第二条测试 —— 去掉守卫,它给出:

```
FAIL: status = 400 body = {"code":"INVALID_ARGUMENT",...}, want 503
```

**这个顺序值得钉住**,不只是为了测试:未配置的服务器回答"你的 JSON 是错的",会把正在排查"TTS 为什么不能用"的人**引向自己的请求体**,而真正的原因是凭据没配。环境问题优先于调用方问题。

那条冗余守卫**保留**并加了注释说明它为何在这里 —— 否则下一个人会"顺手简化"掉它,悄无声息地把诊断方向调反。

## 6. 什么条件下重新评估

两条**同时**满足才接线:

1. **消费者到位** —— 每日一读开始生成音频,或闪测进入实现
2. **P2-4 关闭** —— prod SKU 授权不再 403

**任一条单独满足都不够。** 只有消费者没有授权 = 埋雷;只有授权没有消费者 = 依旧是闲置代码(但那时可以重新评估"是否先删后建")。

## 8. 本票不做

- **不接线**:见 §3。
- **不删除**:见 §4。
- **不改 `Collect` 的 nil 检查**:它与守卫重复但各自成立 —— `Collect` 是包级入口,不能假定调用方先挡过 nil。
- **不关 P2-4**:它是**外部**阻塞(厂商侧授权),不是本票能推进的。P1-1 因本票关闭,P2-4 保持开启。
