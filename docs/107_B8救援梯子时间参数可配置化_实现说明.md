# 107 — B8 救援梯子的时间参数可配置化（实现说明）

> **任务**：让 B8 卡壳救援梯子的 5 个时间参数可以不重新编译就调
> **真源**：`fluentwork-meta/agents/shared/defect-fix-discipline.md`、`docs/99_设计与实现纪律_接缝驱动_2026-09-18.md`
> **范围**：`internal/voicegateway/`（11 个改动文件 + 2 个新测试文件）+ `internal/content/tts/consumer_test.go`（调用点）
> **性质**：**新能力**，不是缺陷修复 —— 见 §测试 的红/绿说明

---

## 接缝

- **接缝**：**包接缝**（`voicegateway.Config` → 三个消费组件）+ **表示接缝**（环境变量字符串 → `time.Duration`）。两者都是**修改**，不新增跨进程接缝。
- **状态所有权**：5 个时间参数由 `voicegateway.Config` **独占拥有**。三个组件（`SilenceDetector` / `HTTPRescueGenerator` / `HTTPRescueSynthesizer`）与 `RescueOrchestrator` 只**消费**，不各自读环境变量。这一条是本次的结构性要求 —— 见「为什么不是各组件自己读环境变量」。
- **不变量**（四条，每条都有测试）：
  1. **未设置时行为与之前完全一致**：默认值就是原来那两个编译期常量，不是「大概 3 秒」。
  2. **设置但畸形 → 启动失败并点名变量**，不回退到默认值。
  3. **梯子单调**：`Level2 ≥ Level1`、`Level3 ≥ Level2`。
  4. **合成超时必须落在第一档之内**（`SynthTimeout < Level1`）—— 它是**有效**上界。
- **证明**：
  - 不变量 1 → `TestLoadConfigDefaults`（扩充）、`TestWireRescue_ZeroTimingsFallBackToDefaults`
  - 不变量 2 → `TestLoadConfigRescueTimingRejectsMalformedValue`
  - 不变量 3、4 → `TestValidateRescueTimingsRefuseBrokenLadders`
  - 接线本身 → `TestWireRescue_CarriesConfiguredTimings`

---

## 为什么

梯子的默认档距（3s / 6s / 9s）与两个预算（生成 2500ms、合成 1000ms）此前是**编译期常量**。真机反馈是「救援计划时间太长了」—— 这是一条**关于档距**的抱怨，而档距是梯子最核心的产品参数。

调它需要改代码 + 重新编译 + 重新部署。这次把它们变成环境变量，**同时把梯子的不变量从「注释里的约定」变成「`Validate` 拒绝的东西」**。

### 为什么不是各组件自己读环境变量

那是最省事的写法，也是本仓 `AGENTS.md` §7 的 R2 明令禁止的形状（「一份语义一个实现点」）。若三个组件各自 `os.Getenv`：

- **没有一处能校验它们之间的关系**。`Level2 < Level1` 这种梯子只有把值收在一起才看得见。
- **`Validate()` 就管不到它们**，于是「配错一个值会怎样」在这条链路上没有答案 —— 正是 `docs/105_` F6 记的那个形状。
- 每个组件还要各自处理「零值怎么办」，那是四份关于同一个问题的答案。

所以值全部收进 `Config`，组件只拿结果。

## 方案

### 1. 五个新变量与它们的解析

| 变量 | 默认 | 消费者 |
|---|---|---|
| `VOICE_RESCUE_LEVEL1_AFTER` | `DefaultRescueLevel1After`（3s） | `SilenceDetector` 阈值 + `RescueOrchestrator.rungBudget` |
| `VOICE_RESCUE_LEVEL2_AFTER` | 6s | `SilenceDetector` 阈值 |
| `VOICE_RESCUE_LEVEL3_AFTER` | 9s | `SilenceDetector` 阈值 |
| `VOICE_RESCUE_GEN_TIMEOUT` | **新增常量** `DefaultRescueGenTimeout`（2500ms） | `HTTPRescueGenerator.Client.Timeout` |
| `VOICE_RESCUE_SYNTH_TIMEOUT` | `DefaultRescueSynthTimeout`（1000ms） | `HTTPRescueSynthesizer.timeout` |

`DefaultRescueGenTimeout` 是**新抽出来的常量**：2500ms 此前是两处裸字面量（构造函数里一处、`GenerateRescue` 的 nil-client 兜底一处）。按 R3「常量必须有出处」，两处同一个数就该有一个名字。

### 2. `durationStrict`：设置过的值不许静默变成默认值

```go
// internal/voicegateway/config.go:353
func durationStrict(key string, fallback time.Duration) (time.Duration, error) {
	raw := strings.TrimSpace(os.Getenv(key))
	if raw == "" {
		return fallback, nil          // 未设置 → 默认值，这是对的
	}
	parsed, err := time.ParseDuration(raw)
	if err != nil {
		return 0, fmt.Errorf("%s=%q is not a duration (want a Go duration such as 3s or 2500ms)", key, raw)
	}
	if parsed <= 0 {
		return 0, fmt.Errorf("%s=%q must be positive", key, raw)
	}
	return parsed, nil
}
```

**这是本次唯一一处「行为上的严格化」，也是最需要说清的一处。**

`durationOr`（同文件 `:373`，梯子之外的一切都用它）在解析失败时静默返回默认值。它的注释说得很准确：*"durationOr's silence is defensible where the fallback is also a defensible answer."* 但梯子的档距不满足这个前提：一个写了 `VOICE_RESCUE_LEVEL1_AFTER=5` 以为「五秒」的操作者拿到的是**三秒**，而且**没有任何办法发现**。

`parsed <= 0` 之所以在这里拒绝而不是在 `Validate` 里，是因为**只有这里知道这个变量被设置过**。下游看到的零值与「字段从未被填充」不可区分，而后者有合法含义（手写的 `Config`，会被解析成默认值）。把两件事混在一起会让手写 `Config` 被误拒 —— 这个坑本仓已经踩过一次（`TestValidateRescueTimingsTolerateHandBuiltConfig` 的注释记着）。

`loadErr` 是 `Config` 的**非导出字段**：`LoadConfig` 没有 error 返回值，所以解析失败先存下来，由 `Validate` 优先报出（`config.go:206-208`）。一个手写的 `Config` 该字段为 nil，不受影响。

### 3. `validateRescueTiming`：拒绝塌掉的梯子

三条规则（`config.go:261-303`）：

1. `Level2 ≥ Level1`
2. `Level3 ≥ Level2`
3. `SynthTimeout < Level1`

**规则 3 的理由是不对称的，值得单独说。** `RescueOrchestrator` 把**外层 context**（无 deadline）交给 `Synthesize`，所以客户端的 timeout 才是合成音频的**有效**上界。音频活过了档距就会在下一档已到期之后才落地 —— 正是这个上界要防的失败。

**`RescueGenTimeout` 被刻意排除在同一规则之外。** 它**不是**有效上界：`generateText` 把每次调用包在一个由档距限定的 context 里，所以生成被 `min(RescueGenTimeout, Level1)` 卡住，context 更小时 context 赢。若也要求 `GenTimeout < Level1`，**只缩短档距就变成不可能** —— 2s 档距会要求一个改了也不起作用的亚 2s 生成超时。`TestValidateRescueTimingsAllowShorteningRungsAlone` 把这条钉住了。

### 4. 零值在 `Validate` 里先解析成默认值

`validateRescueTiming` 开头把 `<= 0` 的字段解析成编译期默认值，**再**跑规则。这样：

- 手写的 `Config`（字段全零）按它**实际会跑的值**受检；
- 而一个**被显式设置的**零值到不了这里 —— `durationStrict` 已经拒了它。

两件事各有各的归属，不共用一条路径。`docs/devnotes/2026-09-16-b8-rescue-handler-integration.md` 记着上一次把「填充默认」和「单调钳制」塞进同一条 if 序列的后果（三层梯子塌成一瞬间）。

### 5. 接线：`WireRescue` 把值交给组件

```go
// internal/voicegateway/rescue_wiring.go:19-46
NewSilenceDetectorWithThresholds(RescueThresholds{
	Level1: cfg.RescueLevel1After,
	Level2: cfg.RescueLevel2After,
	Level3: cfg.RescueLevel3After,
}),
NewRescueOrchestrator(
	NewHTTPRescueGenerator(cfg.AppServerInternalURL, cfg.InternalAPIToken, cfg.RescueGenTimeout, logger),
	NewHTTPRescueSynthesizer(cfg.AppServerInternalURL, cfg.InternalAPIToken, "rescue_ladder", cfg.RescueSynthTimeout, logger),
	cfg.RescueLevel1After,
	logger,
),
```

**附带修掉的一处 R4 违规**：`NewSilenceDetectorWithThresholds` 与 `RescueThresholds.withDefaults` 此前**只有测试在用**，生产路径调的是 `NewSilenceDetector()`。一个「指不出生产调用点」的接口按 R4 该删；现在它有了真实消费者，于是它留下。

### 6. `rungBudget` 跟着档距走，而不是固定的 3s

`RescueOrchestrator` 新增 `rungBudget` 字段，`generateText` 用它替代原先写死的 `DefaultRescueLevel1After`：

```go
// 原：genCtx, cancel := context.WithTimeout(ctx, DefaultRescueLevel1After)
// 新：genCtx, cancel := context.WithTimeout(ctx, o.rungBudget)
```

**这是本次最容易漏的一处。** 只把档距调小、把生成预算留在 3s，会让一档的生成活过下一档的到期时间 —— 而那个上界存在的唯一目的就是防这件事。构造函数的 `rungBudget <= 0 → DefaultRescueLevel1After` 兜底，让不传这个参数的老调用点（测试替身）保持原行为。

## 测试

### 红/绿不适用（新能力）

本次是**新能力**，不是「有人报告了一个问题」的修复，所以 §6 的红/绿不适用：这些字段在旧代码上**不存在**，写不出一个能在旧代码上编译并失败的测试。

例外的是 `durationStrict` 那一条，它**有**一个可红的行为面：旧代码里 `VOICE_RESCUE_LEVEL1_AFTER=5` 会被**完全忽略**（变量根本没被读）。这一点由 `TestLoadConfigRescueTimingRejectsMalformedValue` 覆盖 —— 它在旧代码上的「红」表现为编译失败，而不是断言失败，所以仍归入新能力。

### 新增的测试

| 测试 | 钉住什么 |
|---|---|
| `TestLoadConfigRescueTimingsAreConfigurable` | 5 个变量都能从环境到达 `Config`，且一个自洽的梯子能过 `Validate` |
| `TestLoadConfigRescueTimingRejectsMalformedValue` | 5 种畸形值（无单位 / 非时长 / 忘写单位 / 显式 0s / 负数）都失败，且**错误信息同时点名变量与值** |
| `TestValidateRescueTimingsRefuseBrokenLadders` | 三条关系各一例（档 2 早于档 1、档 3 早于档 2、合成活过档距） |
| `TestValidateRescueTimingsAllowShorteningRungsAlone` | 只缩短档距必须允许（生成超时**不**参与那条规则） |
| `TestValidateRescueTimingsTolerateHandBuiltConfig` | 全零的手写 `Config` 必须通过 |
| `TestWireRescue_CarriesConfiguredTimings` | 5 个值**真的接到了消费者身上**（读的是 `handler.silenceDetector.Thresholds()`、`gen.Client.Timeout`、`synth.timeout`、`rungBudget`） |
| `TestWireRescue_ZeroTimingsFallBackToDefaults` | 零值接线后落到编译期默认值，而不是「碰巧能跑的零值」 |

`TestWireRescue_CarriesConfiguredTimings` 值得单独说：它住在**内部包**（`rescue_wiring_internal_test.go`），因为 `rescue_wiring_test.go` 在外部包、只能证明 `WireRescue` 返回了 `true`。**一个「被读取但从未被传递」的 `Config` 字段，从外面看和一个正常工作的字段完全一样。** 这是本仓反复出现的那个形状（「看起来有保护，实际没有」）在这一处的具体形态，所以每个旋钮都对着**消费它的那个组件**断言。

### 已有测试的改动

- `TestLoadConfigDefaults`：新增 5 个键的 `t.Setenv(k, "")`，并断言默认值**就是那两个编译期常量**（不是「大概 3s」）。
- `TestLoadConfigPicksVolcSpeechDefaults` / `TestLoadConfigPicksVolcDuplexFromVolcLocal`：把 5 个新键加进它们的中和环境循环 —— 否则本 checkout 的 `.env.volc.local` 会注入真实值。`t.Setenv(k, "")` 把键标记为**已设置**（空），这正是阻止 `loadDotenvIfPresent` 注入的机制。
- 构造签名变化的调用点：`rescue_client_test.go`、`rescue_orchestrator_test.go`、`handler_rescue_test.go`、`content/tts/consumer_test.go` —— 一律传 `0`（即「用默认值」）。

## 未覆盖的部分（明确声明）

1. **`.env.volc.local` 与 `configs/voice-gateway.env.example` 没有登记这 5 个新变量。** 两个文件都只列「缺了就会坏」的键（前者）或最小骨架（后者），而这 5 个有可用默认值。代价是「有哪些旋钮」只能从 `Config` 结构体读 —— 这正是 `docs/104_架构分析/03_数据与配置.md` §5 建议 #4（导出环境变量清单）要解决的问题，那条建议目前仍挂着。**本次新增后，`104_03` §4.1 的「51 个环境变量」已过期，实际是 56。**
2. **`VOICE_GATEWAY_IDLE_TIMEOUT` 仍走 `durationOr`（静默）。** 于是同一个文件里，救援梯子 5 个严格、idle timeout 1 个静默。这不是本次的范围，但它是 `docs/105_` **F6 / D1** 那条决策在同一个文件里的具体样子。
3. **合成超时的「有效上界」性质没有被测试直接钉住。** `TestValidateRescueTimingsRefuseBrokenLadders` 钉的是 `Validate` 会拒绝，不是「音频真的会在档距内停住」——后者需要可控时钟 + 一个会慢的合成替身，属真机/集成范围。
