## 2. 契约 A：`ai.rescue.ladder`（要新写）

用户在 **AI 说完话之后沉默** 时到达（阈值见 §2.2）。

```json
{
  "type": "ai.rescue.ladder",
  "turn_id": "turn-3",
  "level": 1,
  "text": "I think the main risk is...",
  "audio_url": "",
  "duration_ms": 0,
  "ts": 1726502400000
}
```

| 字段 | 说明 |
|---|---|
| `level` | 1=句首骨架、2=中文思路提示、3=完整例句。**同一轮只会升不降**，三级各最多一次 |
| `text` | 要显示的内容。1/3 是英文，**2 是中文** |
| `audio_url` / `duration_ms` | **永远为空，这是设计**。音频走 §3 的 `ai.tts.*`，不在这里。不要等它、不要因为它是空就判失败 |
| `turn_id` | AI 那一轮的 turn id；AI 从未发 `ai.turn.end` 时回落到 `session_id` |

### 2.1 iOS 要做的

1. 把 `text` 显示在**对话气泡**里（淡色背景区分，`78_` §2.2）
2. **不记入回合**：不要用它触发 `feedback.badge` 检测、不要改你的状态机
3. 用户可继续录音或打断，梯子**不阻塞**任何交互

### 2.2 触发时机（照这个调测试节奏）

沉默从 **AI 的 `ai.tts.end` / `ai.turn.end`** 开始计（谁先到算谁，都到只算一次）。之后：

| 沉默 | 出第几级 |
|---|---|
| 3s | level 1 |
| 6s | level 2 |
| 9s | level 3 |

三级之后不再出。用户一开口，窗口关闭、下一次从 level 1 重新开始。

> **注意**：DevEcho provider **测不了**这条（它会立刻答、窗口根本不开）。用 `volc-duplex` 或 `mock`。

## 3. 契约 B：梯子的声音（走已有的 `ai.tts.*`）

**协议零新增**。后端复用 AI 说话那条通道，只是换了一个 turn id：

```
{"type":"ai.tts.start","turn_id":"<ladder turn>","voice_id":"zh_female_vv_uranus_bigtts","sample_rate":16000,"codec":"pcm"}
<binary frame>            ← 4 字节大端 seq + PCM
<binary frame>
...
{"type":"ai.tts.end","turn_id":"<ladder turn>","completion_status":"ok","duration_ms":3770}
```

### 3.1 你这边**不需要写新代码**，但要确认这四条

| # | 你的现状 | 为什么重要 |
|---|---|---|
| B1 | 二进制帧只在 `ai.tts.start` 之后播（`TTSFrameDispatcher` `.idle` 直接丢） | 梯子音频**没有** `ai.tts.start` 就播不出来——这是后端按你的实现挑的方案 |
| B2 | 播放缓冲 = 16 kHz 单声道 PCM16（`RawPCM16FrameDecoder`） | 后端就是按这个格式合成的，**不需要你重采样** |
| B3 | 序号门（`AudioFrameDropGate`）按水位丢帧 | 梯子帧的序号接在**本会话已有的音频序号之后**，不是从 0 开始；你打断过一次之后梯子仍能播 |
| B4 | 新的 `ai.tts.start` 会结束上一个流（`testTTSDispatcher_NewStartEndsAStuckDrainingStream`） | 连着来两级梯子时，第二级会自动接上 |

**要新写的只有一件事**：梯子的 `ai.tts.start` 会打断 AI 那一轮的流。
如果 AI 的 `ai.tts.end` 还没到，你的 dispatcher 会把上一个 turn 标成 `interrupted` —— **这是对的，别修**。

### 3.2 两个产品要求（`78_` §8.3 的冻结参数）

| 参数 | 值 | 谁施加 |
|---|---|---|
| 语速 | 0.9（比对话慢） | **后端**已在合成时施加，你不用管 |
| 音量 | 0.85（比对话轻） | **你**：播放梯子时降增益。PCM 里没有音量信息 |

判断"这一帧是不是梯子"的办法：它的 turn id 不等于当前对话轮的 turn id。建议显式记下来，
不要靠"时间上比较近"猜——两级梯子间隔 3s，而 AI 的话可能刚好插在中间。

### 3.3 用户开口即停（要和后端配合）

用户开始说话时，后端会发：

```json
{"type":"ai.tts.end","turn_id":"<ladder turn>","completion_status":"interrupted"}
```

- 你要做的就是**停播**（你的 dispatcher 收到 `ai.tts.end` 本来就会 finish）
- 后端同时会停止发送**尚未发出**的帧；已经在路上的最多一帧
- **边界**：如果用户开口时梯子正好播完，你可能收到的是 `completion_status: "ok"` —— 两者都正常

## 4. 验收清单

每条都留证据：**后端日志行 + iOS 现象**。只记听感不算。

过滤后端日志：终端里看 `B8 rescue ladder emitted` / `feedback.badge emitted`。

### 4.1 主链路：沉默 → 听到梯子 → 开口

| # | 操作 | 预期（后端） | 预期（iOS） |
|---|---|---|---|
| 1 | 说一句 → 松手 → 等 AI 答完 → **不说话** | 3s 后 `ladder emitted level=1 spoken=true` | 3s 后：**听到**一句英文半截话，同时气泡里出现同样文本 |
| 2 | 继续不说话到 6s | `level=2 spoken=true` | 6s：**听到中文**提示（"先说结论…"），气泡显示中文 |
| 3 | 继续到 9s | `level=3 spoken=true` | 9s：**听到**一个完整英文例句 |
| 4 | 现在开口 | 无新的 ladder | 梯子**停**；你正常说话、正常走后续流程 |

### 4.2 打断

| # | 操作 | 预期 |
|---|---|---|
| 5 | 阶梯正在播时立刻开口 | 后端 `ai.tts.end completion_status=interrupted`；**立即**停播，不留尾巴 |
| 6 | 开口 → 又沉默 | 3s 后**重新**从 level 1 开始（不是接着 level 2） |

### 4.3 边界（这些最容易出问题）

| # | 场景 | 预期 | 怎么造 |
|---|---|---|---|
| 7 | **梯子没有音频**（TTS 关掉） | 只收到 `ai.rescue.ladder`，**没有** `ai.tts.*`。文本照常显示，**不报错** | 起服务时**不** source `.env.volc.local` 里的 speech key |
| 8 | **梯子文本也没有**（模型失败） | `text` 是静态库短句（level1 `I think...`／level2 `先说结论`／level3 `I think we should consider the trade-offs carefully.`），**音频仍可能有** | 清掉 ARK key |
| 9 | **AI 只发文本、没发 tts.end** | 窗口仍会开（`ai.turn.end` 也算开窗信号），梯子照发 | provider 不走 TTS 时 |
| 9b | **AI 那轮以 `timeout` / `error` 结束** | **不开窗**，不发梯子——那轮用户不欠一句话 | abort 或 B15 超时后静默 |
| 10 | **用户半句话后被救援**（未完成句路径） | 梯子照发；下一次炼化的锚点是你那半句原文 | 说半句就停 |
| 11 | 连按两次「重新开始」/ 会话切换 | 梯子不跨会话；新会话从 level 1 起 | 结束会话再开 |
| 12 | 梯子播到一半断网 | iOS 断线逻辑照常（`41_` 场景 4）；后端不补发 | 飞行模式 |
| 13 | 三级都出完后继续沉默 | **不再有任何帧**（不是每 3s 无限循环） | 等 20s |

### 4.4 顺带验：B7 命中回写（今天刚接通）

| # | 操作 | 预期 |
|---|---|---|
| 14 | 说出语料库里某个块的表达 | `feedback.badge emitted` + `phrase_block_id=...`；随后语料库页该块「用上过」**+1** |
| 15 | 同一轮里把同一句说两遍 | **只 +1**（按 session+turn+block 去重） |

## 5. 重难点

| # | 难点 | 为什么难 | 建议 |
|---|---|---|---|
| 1 | **梯子的 turn id 与对话轮的 turn id 不混同** | 两者都在 `ai.tts.*` 里，靠 turn id 区分。混了就会把梯子当 AI 的回复 | 记住 ladder turn id，别用"最近一次 tts"推断 |
| 2 | **序号水位** | 你打断过一次之后水位会升；梯子帧序号接在后端会话序号之后。**如果序号从 0 重来，整段梯子会被静默丢掉** | 后端已按此设计；你验收时若"听到一半没了"，先怀疑这里 |
| 3 | **文本帧与音频帧的先后** | 后端**先发** `ai.rescue.ladder`（文本），**再发** `ai.tts.start`。所以文本总是先到 | 别等音频才显示文本 |
| 4 | **三级级联** | 用户一直不说话时，第 2 级的 `ai.tts.start` 会打断第 1 级还在播的音频 | 这是期望行为，不是 bug |
| 5b | **两条开窗信号** | `ai.tts.end` 与 `ai.turn.end` **都**能开窗；provider 只说文本时后者是唯一的信号。`timeout`/`error` 两种 outcome 不开窗 | 别自己推断"AI 说完了"，用协议给的信号 |
| 5 | **DevEcho 测不了梯子** | 它会立刻回答，沉默窗口不开 | 梯子必须用 `volc-duplex` / `mock` |
