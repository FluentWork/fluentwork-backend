# 月度回流机制：让数据回到产品（86_ M12）

**文档版本**: V1.0
**创建日期**: 2026-09-18
**对应缺口**: `86_` M12（回流无定义）——飞轮要转，必须有"谁读、读什么、多久、产出什么"

---

## 一、两种节拍，不要混

| 节拍 | 触发 | 工具 | 回答的问题 |
|---|---|---|---|
| **改动前** | 改 prompt / 模型 / 调度参数 | `./scripts/eval-gate.sh` | 这次改动**相对基线**是变好还是变坏？ |
| **每月** | 日历（建议每月 1 号） | `./scripts/reflux-report.sh` | 上个月的数据**指向什么产品动作**？ |

前者已经写进 `CLAUDE.md` 第 0 条纪律；后者是本文档定义的。

---

## 二、四个输入 → 四类产出

| 输入（报表里的节） | 产出 | 验证方式（下个月回看） |
|---|---|---|
| §1 卡壳视图（按 function_tag） | 该补什么素材、哪类意图要降难度 | 该意图类型的**平均判定/转正**下降 |
| §2 实战转化率（hit / checkin 分列） | 投入方向：App 内练习 vs 真实会话 | 打卡率与 L2（用户确认）使用数上升 |
| §3 "没聊成"原因分布 | `no_partner`→系统内模拟；`not_confident`→更低的第一步；`no_time`→卡片更短；`not_relevant`→话题生成要调 | 该原因的占比下降 |
| §4/§5 门禁差异 + 负反馈率 | 改写规则或 prompt 的修订 | 负反馈率下降、门禁无退化 |

## 三、每月怎么做（30 分钟）

```bash
# 1) 取一个活跃用户的 access token（例如你自己的账号），然后：
./scripts/reflux-report.sh --user <user_id> --token <access_token>
# 输出：eval-out/reflux-<date>.md（stdout 同时打印）

# 2) 按报表末尾的"本月要做的事"挑 1–3 件（不要贪多）

# 3) 每做完一件，在 eval/moat/revisions.md 记一条：
#    依据（哪个信号）→ 改动 → 前后指标 → 结论
```

**用户少的时候**：`--user` 选一个最活跃的用户即可；等有了一批用户，再考虑把卡壳视图做成
**跨用户聚合**（现在它是按用户隔离的，运营视角的聚合需要另开一个内部端点，属 V1.1 的事）。

---

## 四、纪律（这是这套机制唯一不可妥协的部分）

> **没有前后指标的修订，不算修订。**

`eval/moat/revisions.md` 是这条纪律的载体，已经有三条真实记录（判定修复、话题落地、
端点路由）。它同时是给未来的自己看的：三个月后回看"为什么当时这么改"，答案在表里，
不在记忆里。

**什么时候该回滚**：如果一条修订在下个月的报表里让对应指标**变差**，就回滚并在表里
记一条——记录失败和记录成功同样重要，否则这张表会退化成宣传材料。
