# 接缝纪律内核（可复制到任何项目）

> 这是一页纸。**复制它，不要复制整套。** 项目特有的坑与规则在使用中长出来（见 `100_` §5.1）。
> 真源：`fluentwork-backend/docs/99_`、`docs/100_`。

---

## 为什么需要它

测试验证的是**函数**，结构问题出在**接缝**上：两份实现都正确、每处状态各自看都对、
四个常量值都对——**没有一条能让测试变红**，于是静默积累。
`build 过、test 过` 拦不住，因为它们的粒度不对。

而强约束通常只挂在**修复**那一侧（"有人报告了问题 → 先写会红的测试"）。
新建路径上什么都没有——**而结构债几乎全部长在新建路径上。**

---

## 一、动手前：声明接缝

每条新增/修改的接缝（HTTP / 包 / goroutine / 表示 / 层），写清楚四件事：

```
接缝：<哪条，新增还是修改>
状态所有权：<每条跨接缝的状态，归哪个包或类型>
不变量：<这条接缝上什么必须永远成立>
证明：<哪个检查会在它被破坏时变红>
```

**最后一行是关键**：写不出检查的"不变量"不是不变量，**是愿望**。

---

## 二、七条

| # | 规则 | 一句话 |
|---|---|---|
| R1 | 动手前声明接缝 | 见上 |
| R2 | 一份语义一个实现点 | 两处"目前恰好一致"→ 合并，或写一致性检查 |
| R3 | 常量必须有出处 | 用推导（`FrameBytes(100ms)`）而不是复制数字 |
| R4 | 接口只服务今天的消费者 | 指不出生产调用点的方法删掉 |
| R5 | 先写契约检查再写实现 | 跨进程调用**驱动真件**，不手写对方答应返回什么 |
| R6 | 依赖方向要能跑 | 写成 linter 规则 / `go list -deps` 之类可执行的判据 |
| R7 | 坑的修法落在结构上 | 问"这个坑的形状是什么"，让形状不可能重现 |

---

## 三、修复纪律（两种都适用）

**有人报告了问题**：先写一个会**复现它**的失败测试 → 确认它红 → 再改代码 → 留下测试。

**发现结构问题**：同一个套路，**把"形状"当成被测对象**——
"这条边不存在"、"只有一处实现"、"这个常量是推导的"、"这个迁移是合法的"。

**检查可以住在任何地方**：单元测试 / linter 配置 / 脚本 / SQL。介质不重要，**可执行**才重要。

### 先证明它会红

写完一条检查，**故意破坏一次**，确认它变红。
在"从不工作"的实现上也会通过的检查，等于没有检查——而且比没有更糟，它给人已经覆盖的错觉。

---

## 四、节奏

| 时机 | 动作 |
|---|---|
| 每个改动 | 声明接缝（四行） |
| 每个新模块/新链路动工前 | 写一份接缝契约 |
| 每月 | 挑**一条**接缝做人工审计：找并行实现、找两处定义；**产出新检查** |
| 断言本身 | **每次提交都跑**（在已有的那条 check 命令里），不是每月跑 |

> 每月**产出**新断言，每天**执行**已有断言。混为一谈就白做了。

**审计被打断时**：推迟的项必须写下**归属人 + 复查日期 + 触发条件**。
一条被推迟且无人跟踪的接缝，比从未被提及的更危险——再有人提起时，答案会是"那个审过了"。

---

## 五、一个坑出现第二次怎么办

**同一个坑出现第二次 = 这套规范失效。** 第二次必须产出**防护**
（检查 / 断言 / 类型 / 校验 / linter 规则 / 监控），而不是再写一篇总结。
