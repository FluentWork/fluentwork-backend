# 核心机制里有三个「有字段、没写入方」的空壳

**标签**: 间隔重复 / 命中回写 / 死代码 | **模块**: `internal/corpus`、`internal/drill` | **深度**: BRIEF | **状态**: **已查清（2026-09-18）——见文末「修订记录」：三处里一处是我判错的**
**日期**: 2026-09-17 | **相关**: `meta/docs/20_产品设计/20_FluentWork产品需求文档PRD.md` §5.5、本目录 `2026-09-16-b8-rescue-handler-integration.md`

## 3 行速览

- **结论**：写 PRD 完善时对着实现核对核心机制，发现三处"字段存在、类型存在、schema 存在，唯独没有写入方或没有调用方"——`ease_factor` 恒为默认值、`real_use_count` 恒为 0、调度规则有两处实现只有一处被调用。
- **影响**：`real_use_count` 那处**直接对用户可见**——UI 设计文档把"开会用上过 N 次"当卖点，而它会恒显示 0。
- **细读建议**：只看「本质」与「以后怎么避」两段。

## 现象

起因是给 PRD §五 补「机制口径」一节，需要逐条核对"文档写的规则"和"代码跑的规则"。核对方式是 grep 每个字段的**写入方**（不只是读取方），结果：

| 字段 / 规则 | 读了什么 | 写了什么 |
|---|---|---|
| `ease_factor` | `corpus/service.go` 读取并拷贝；`mysql_store` 读写列 | 只在建块时赋默认值 `2.5`。**两处调度实现都不读它** |
| `real_use_count` | 同上，读取 + 拷贝 + 序列化 | **全仓非测试代码零写入**。没有 `IncrementUse` 之类的函数 |
| 调度规则 | `drill.ApplyJudge` 被 `drill/service.go:102` 调用（生产路径） | `corpus.ApplySuccess/Failure` **只被自己的测试文件调用**——生产上是死代码 |

## 本质（BRIEF 档，未做可切换性验证）

**因为** 这三者的落地顺序是「先建 schema（表里预留字段，为后续版本）→ 再实现计算」，而**第二步被排到了后面且没人跟踪**：
- `ease_factor` 是 SM-2 的血统（`39_` 技术文档写了 `calcEaseFactor`），MVP 简化成固定阶梯后字段留下了；
- `real_use_count` 是 B7 闭环的**最后一环**，而 B7 的"发出徽章"先做完了；
- `corpus/schedule.go` 是先写的版本，`drill/scheduler.go` 是闪测路径后来写的版本，**新版本没有回头删掉旧版本**；

**导致** 每一个都是"看起来在工作"：字段会被序列化进 API 响应、函数是导出的、表列有默认值。任何单边的评审都发现不了——
- 静态检查不报：`unused` 不看导出符号（实测 `golangci-lint --enable-only=unused` 在 `internal/corpus`、`internal/drill` 上报 **0 issues**）；
- 代码评审不读 schema，所以"字段没人写"看不出；
- 文档评审不读代码，所以"文档承诺了"看不出。

**产生** 三类后果，严重程度递增：死代码误导（改错文件）→ 展示数据恒为 0（用户可见）→ 需求被按实现读（PRD 里写着要回写，实际没有，谁也不知道）。

**置信度: 高**（三处都是全仓 grep 写入方得出的，不是推断）
**如果我错了，会怎么发现**：`real_use_count` 若被写入，会在某处出现对它的赋值或 `+1`；`ease_factor` 若参与计算，会在某个调度函数里被读进表达式；`corpus/schedule.go` 若有调用方，`grep -rn "ApplySuccess\|ApplyFailure"` 会在非测试文件里命中。

## 以后怎么避

1. **核心机制的字段，写入方与字段同时提交。** 做不到就先不建字段——预留字段的代价是它会被当成已完成。
2. **凡是要展示给用户的数据，验收必须端到端**（发一次真实的命中 → 看 API 里的数字有没有变），不能只验证"接口返回了这个字段"。这条已登记进 §5.5 与 PRD §十二 风险表。
3. **同一规则不允许存在两处实现。** 新实现落地时必须删除旧实现，或把两者的适用范围写进注释；否则下一个改调度的人有 50% 的概率改错文件。
4. 排工时把"字段的写入方"当成功能的一部分计入——`real_use_count` 的写入方（B7 命中回写）本就是 B7 的一部分，只是被拆散了。
