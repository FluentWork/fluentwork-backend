# 开发手记（devnotes）

本目录记录**看代码看不出来的东西**：为什么是这样、当时怎么想的、走过哪些弯路。

**这里不是 ADR。** 读者是本项目的开发者本人，目标是「看懂」，不是「存档决策」。所以允许第一人称、允许写没解决的、允许写推断错的部分。

## 与其他产物的分工

| 产物 | 回答什么 |
|---|---|
| commit message | 改了什么 |
| PR | 怎么验 |
| `.workbuddy/memory/YYYY-MM-DD.md` | 今天做了什么 |
| **本目录** | **为什么是这样 / 当时怎么想 / 哪条路不通** |

## 三条铁律

1. **先「我当时怎么想」，再给结论** —— 顺序不可反。结论导向的文档会隐去弯路，而弯路才是最省时间的信息。
2. **事实与推断分开标注**（观察到 / 猜测 / 待验证）。
3. **每个结论带置信度 + 可观测的反证条件**。反证条件必须能观测，禁止「不对就是错的」。

## 必写四类

1. 值得解释的 bug 修复
2. 新任务 / 功能落地
3. 重构或接口变更
4. 排查未解、但把地形摸清了

**豁免**：错别字、纯样式、加日志、一行配置、重复性操作。

自检：**「下次遇到类似情况，这份记录能让人少走一段路吗？」** 不能则不写。

## 深度分级

| 档位 | 何时 | 篇幅 |
|---|---|---|
| `BRIEF` | 小改动 + 一个值得记住的坑 | 5–15 行 |
| `FULL` | bug 修复 / 功能落地 / 重构 | 60–150 行 |

超过 200 行拆成两篇。

## 归档与命名

- 目录：`docs/devnotes/`（本目录）
- 文件名：`YYYY-MM-DD-<kebab-slug>.md`，slug 用 ASCII；同主题追加 `-2`
- 头部固定四段：`标签 | 模块 | 深度 | 状态` + 日期 + 相关文档
- 正文最前放 **3 行速览**（结论 / 影响 / 细读建议）
- 收尾时**主动**写，不用等人开口

## 图一律用 mermaid

流程 / 结构 / 时序 / 实体关系全部用 ` ```mermaid ` 代码块。**不用 ASCII 字符画、不贴截图**（不可检索、不可 diff、会过期）。

| 要表达 | 用什么 |
|---|---|
| 排查路径、决策分支、因果链 | `flowchart TD` |
| 数据流、模块依赖 | `flowchart LR` |
| 调用时序、状态流转 | `sequenceDiagram` |
| 表结构、实体关系 | `erDiagram` |

只画主干，节点 ≤ 12，只用基础语法。

## 问题本质：怎么写

先分层，再写本质。根因写糊几乎都是因为四层混成一句：

1. **触发条件** —— 直接引发的那一下
2. **机制** —— 系统实际执行了什么
3. **根因** —— 让机制得以成立的条件（**「本质」只写这一层**）
4. **系统性原因** —— 为什么没人拦住

「本质陈述卡」逐栏必填，见 `_TEMPLATE.md`。四条硬标准缺一即未到本质：解释力（须能解释「偶发」）、可切换性（移除→消失、加回→复现，**双向**）、条件性（说得出边界）、终止性（再追问已进入协议/物理/数学层）。

**禁止**：写「由于历史原因 / 架构耦合导致」这类无可验证内容；说不出 `文件:行号` 的「本质」视为未到本质；「解释不了 / 反例」两栏不许顺手写「无」。

本质会过时 —— 带复核提示；被推翻时**不删原文**，在 `## 修订记录` 追加新证据。

## 防复发规则表

会重复的教训必须在这里登记一条防护，否则手记写完就等于没写。

| # | 规则 | 防护手段 | 来源 |
|---|---|---|---|
| 1 | 特性"接线柱装好"不等于接线完成：新增可配置组件后，必须有一条**从外部输入到外部输出**的集成测试，只测组件内部的单测不算 | 集成测试（`handler_rescue_test.go`） | [B8](2026-09-16-b8-rescue-handler-integration.md) |
| 2 | 构造参数类函数（阈值 / 缺省值 / 限流值）必须有直接断言其取值的测试，不能只测行为 | 单测（`TestSilenceDetector_ZeroThresholdsUseDefaults`、`..._ThresholdsAreClampedNonDecreasing`） | [B8](2026-09-16-b8-rescue-handler-integration.md) |
| 3 | 引入"时间阈值"类逻辑时，时钟必须可注入；测试用假时钟推进，不用 sleep | `Handler.RescueTick` + 可注入 `h.now` | [B8](2026-09-16-b8-rescue-handler-integration.md) |
| 4 | 核心机制的字段，**写入方与字段同时提交**；做不到就先不建字段 | 评审时 grep 写入方；UI/接口会展示的数据必须端到端验证一次 | [空壳字段](2026-09-17-silent-fields-and-dead-scheduler.md) |
| 5 | 同一规则不允许存在两处实现，新实现落地时必须删除旧实现或写明各自适用范围 | 删除死代码；保留两处时在代码注释里写明分工 | [空壳字段](2026-09-17-silent-fields-and-dead-scheduler.md) |
| 6 | **"XX 没做/没接线"这类任务，先 grep 调用方再读组件**：本仓最常见的缺陷不是组件坏了，而是组件齐全、各自有测试、唯独没人调用它 | 派活/接活时的第一个动作：`grep -rn "<端点或 setter>" --include="*.go" . \| grep -v _test`。命中数就是答案 | B8、B7 三次同形（见下） |

### 6 号的证据：同一个坑出现了四次

| 时间 | 组件（齐全且各自有测试） | 缺的那一行 | 症状 |
|---|---|---|---|
| 之前 | `SetRescueComponents` + 沉默检测 + 三级梯子 | `cmd/voice-gateway` 里没人调用 | B8 在所有环境都是暗的（23f5262） |
| 2026-09-18 | `corpus.RecordHits` 的整条回写事务（772ce2a 就做完了） | 网关上没有任何调用方，全仓唯一 POST 的是 `cmd/smoke-moat` | "用上过 N 次"恒为 0（1e4b0e4） |
| 2026-09-18 | 客户端按 `{"data":{...}}` 解码 | app-server 从来只发扁平结构 | 每一级梯子静默掉进静态库（4f113e6） |
| 2026-09-20 | `Turn` 状态机（白名单 + 单点 id + 拒绝计数，`turn_test.go` 全套） | `EvAIFirstOutput` 一个生产调用点都没有；结束事件被 `rescueEnabled()` 挡住 | 干净会话每轮报"协议违规"；`speaking` 状态不可达（见下第 4 例） |

四例的共同点：**测试全绿**。因为每个组件自己的测试都通过，而洞永远在两个包的接缝上——没有哪个包的测试套件看得见它。

第四例还多一层：`3cb3774` 的**提交说明与代码注释都写着正确意图**（`before any audio frames`），只有代码不是。所以"读说明和注释"这条评审习惯在这里也失效了——顺序、次数、来源这三类属性看不见，必须落到断言上。

对应的防护手段有两条，缺一条就还会再犯：

1. **发现**：接"XX 没做"这类任务时，先看调用方（规则 6 的 grep）。四次里有三次，组件其实已经写好了（命中数 0 = 没有调用方）。
2. **证明**：跨进程/跨包的调用，测试必须**驱动真 handler**（真 HTTP、真路由、真鉴权），不能用一个复述了同样假设的 fixture。B8 那次正是 fixture 与客户端犯了同一个错，所以它替 bug 打了掩护；第四例里是同一种掩护——测试走批处理路径，生产走流式路径。

> **硬规则**：同一个坑出现第二次 = 这套规范失效。第二次必须产出**防护**（测试 / 断言 / 类型 / 校验 / 监控），而不是再写一篇手记。第四例的防护是 `TestCleanTurnsProduceNoRejections` 与 `TestStreamedAudioIsPrecededByTTSStart`——注意它们是**驱动真实装配**的测试，不是又一批单测。
