## 一、原来的三个缺口的处置

| # | 残留项 | 处置 |
|---|---|---|
| 1 | `voice.hit_detect` 记账 | **不写行**（决定，见 §3.1） |
| 2 | `voice.asr` / `voice.tts` 记账 | `voice.tts` **已实现**；`voice.asr` **不写行**（决定，见 §3.2） |
| 3 | `ai_cost_logs` 聚合统计 | **已实现** `GET /internal/v1/ai-cost-logs/summary` |

**先说结论**：三项里只有一项真的缺账（TTS）。另外两项是**看起来像缺口**——按 51_ §4.3 的纪律（"账本里一个按猜测算出的数字看起来权威"），错误的记账比不记账更贵，所以它们以"写明为什么不记"结案，而不是补两行凑数。

## 三、两项"不写行"的决定

### 3.1 `voice.hit_detect`：没有可变成本可归因

B7 命中检测是**本地**的 token 重叠打分（PRD §5.2.3 定案），不调用任何供应商。它读的 ASR 文本，其成本已经记在 `voice.duplex` 那一行里。再写一行 `voice.hit_detect` 会把同一段音频/文本算两遍。

> 这条残留项的前置条件是"B10 语料数据基础"——语料现在有了，但结论是**当时设想的那个 LLM 判定并没有落地**（V1.7 把判定改成了确定性打分）。所以它不记账，不是"还没做"，而是"不需要做"。

### 3.2 `voice.asr`：今天没有独立的 ASR SKU 被调用

- 服务端侧：所有需要付费的 ASR 都发生在 duplex 会话内，其 SKU 已经把 ASR 打包计价 → 单独写行会重复计费；
- 客户端侧：B13 的 ASR 跑在设备上，不产生服务端成本。

**重启条件**：当出现**独立的 ASR 调用**（例如非 duplex 链路的服务端识别）时，它按 `audio_sec` 记 `voice.asr`。这条写在 `internal/aicost/voice_usage.go` 的注释里——那是将来会去改代码的人第一眼会看的地方。

## 四、`voice.tts` 实现细节

```
tts.Handler（POST /internal/v1/tts/synthesize）
    ↓ 合成成功之后
tts.UsageRecorder（窄接口，纯数字，不依赖账本类型）
    ↓ aicost.TTSRecorder
aicost.Service.Record → ai_cost_logs(task_type=voice.tts, model=voice_id, chars, cost_micro_yuan=0)
```

三个刻意的选择：

1. **`cost_micro_yuan` 记 0**。供应商费率未核实（P2-2），沿用 51_ §4.3：**用量是事实，费率是待核实**。
2. **不记 `audio_sec`**。流式合成返回 `ogg_opus`，压缩流无法由字节数还原时长；而时长本来也不是计费单位。猜一个时长正是那条纪律要挡的东西。
3. **记账失败不失败合成**。写账用**脱离请求的 context**（客户端断连也要记——供应商已经收了钱），失败只记 warn。用量没入账是账本问题，不是不给用户说话的理由。

**字符数用 rune 计**：这是本地能做到的、最接近供应商口径的代理；准确口径属 P2-2 的账单问题。这一半是"用量"那一半。

## 五、聚合统计

```http
GET /internal/v1/ai-cost-logs/summary?since=&until=&group_by=task_type|model|day&user_id=
```

- 回答 51_ §4.3 说的**归因与熔断**：哪个 task_type / 哪个 model / 哪一天在花用量；
- 每个单位**各自一列**（tokens_in / tokens_out / audio_sec / chars / cost_micro_yuan）——把字符和音频秒加在一起的总数没有意义；
- 默认窗口 7 天（不传参不会变成全表），窗口上限 180 天；窗口语义**半开 `[since, until)`**；
- 响应带 `cost_caveat` 字段，写明"费率待账单核实（P2-2），用量列是事实，fen 列还不是钱"。**这是防误读的承重字段**，不是装饰。

## 六、顺带收口：定价表外部化与"猜出来的价格"（doc 79 / P2-2）

做 §5 的 caveat 时发现两件必须一起修的事——它们决定了 `cost_micro_yuan` 到底能不能读：

### 6.1 未知模型被静默按 doubao-pro-32k 计价

`CalculateCost` 此前对不在表里的模型**回退到 pro-32k**。而 Ark 实际返回的名字形如 `doubao-seed-2-1-pro-260628`——它落在启发式推断里；真正落到兜底的模型会被按贵约 2.7 倍的 pro 费率记账，且**看不出来**。这正是 51_ §4.3 那条纪律针对的东西。

现在把价格来源分成三态，并在指标里区分：

| 来源 | 含义 | 记账 |
|---|---|---|
| `exact` | 定价表精确命中（含 endpoint → 模型显式映射） | 按表计费 |
| `heuristic` | 由模型名推断家族（如名字含 "pro"） | 计费，并计入 `HeuristicPricedModels{model}` |
| `unknown` | 任何规则都不认 | **记 0**，计入 `UnpricedModels{model}` |

两个指标就是给运维的待办清单：**该往定价表里补哪个模型**。零是"看得见的未知"，猜出来的数是"看不出错的错"。

### 6.2 定价表外部化（doc 79）

`ARK_PRICING_FILE` 指向一个 JSON 费率表，设置后**整张替换**内置表：

```json
{"doubao-mini-32k": {"input_price_per_k_token": 3, "output_price_per_k_token": 6}}
```

- **解析失败 → 启动失败**。文件在那里意味着有人打算改费率；静默沿用的旧费率是"没人选过的数字"。
- **全量替换而非合并**：避免一半模型来自文件、一半来自默认，谁也不知道哪行是哪个。
- P2-2 的"以账单为准"因此落成一次改数据 + 重启，而不是改代码 + 发版。

### 6.3 修正后的 fen 口径

`cost_caveat` 的文案改为精确版：**用量列是事实；fen 列既不是发票也不完整**——voice 行是 0（费率待账单），LLM 行是按一张尚未对账的费率表算出的估计，靠名字猜的和认不出的都另有计数。

## 七、账本单位从"分"改为"微元"（10^-6 元）

做 §6 的 caveat 时算了一笔账，发现账本的金额列**在真费率进来之前就已经坏了**：

| 模型费率 | 换算 = 分/1K | 一次 1000+500 token 调用 |
|---|---|---|
| 0.8 元/百万 | 0.08 分/1K | 0.12 分 → 整数运算归 0 → 撞 1 分地板价 |
| 4.0 元/百万 | 0.40 分/1K | 0.60 分 → 同上 |
| 10 元/百万 | 1.00 分/1K | 1.50 分 → 仍归 0 |

**只要费率低于 10 元/百万，整数"分"就表达不了单次调用成本**，账本会退化成"1 分 × 调用次数"——一个看起来像钱、实际与费用无关的数。

因此（趁账本里还没有任何真实费率）：

- 列改为 `cost_micro_yuan BIGINT`（微元，10^-6 元），migration 0022；旧值**不迁移**——它们是按一张错表（模型认错 + 与自身注释差 100 倍）算出的估计，换个单位搬运只会给假精度；
- 定价表单位改为**微元 / 百万 tokens**，与供应商公布口径一一对应；
- **定价文件的单位是供应商公布的口径**：`{"doubao-seed-2-1-pro-260628": {"input_cny_per_million": 0.8, "output_cny_per_million": 2.0}}`——运维照抄账单，不用在脑子里换算。

### 7.1 顺带发现并修掉的两处

1. **内置表与自己的注释差 100 倍**：`doubao-mini-32k` 标注 0.3 元/百万，表里写的是 3 分/1K（= 30 元/百万）。除 mini 外其余条目既无来源也差同样的量级，已**全部删除**——没有价格就是没价格（记 0 并被 `UnpricedModels` 计数），而不是借一个别的模型的价。
2. **两条计价路径**：`session/review.go` 自己写了一套硬编码 Ark Mini 费率（还忽略了 `result.Model`），与 orchestrator 的表单位不同、结论不同。已删除，统一走 `orchestrator.CalculateCostMicroYuan`。

### 7.2 端点 → 模型的权威答案（探针）

`cmd/ark-endpoint-probe` 直接问 API"你是谁"，六个端点实测为**两个模型**（此前代码声称六个都是 mini）：

```
REVIEW_REFINE / DAILY_READ / TOPIC_CARD → doubao-seed-2-1-pro-260628
HIT_MATCH / DRILL_JUDGE / TEXT_DEGRADE  → doubao-seed-2-1-turbo-260628
```
