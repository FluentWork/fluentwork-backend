# 重开后的音频序号

**日期**：2026-09-11
**状态**：实现与测试已齐。门禁见 §5。
**触发**：真机 —— 「上下滑动，触发声音无法播放后，**可以继续对话，返回文字，但是没有语音播放了后续轮次**」
**关联**：`docs/45`（上游断开后的会话恢复）· iOS `docs/45`（中断悬挂）· meta `77_` F18

## 1. 守住的不变量

**网关→客户端的二进制帧序号在整个 WebSocket 会话内单调不减 —— 包括透明重开之后。**

## 2. 契约本来就在代码里

`volcDuplexProviderSession` 的字段注释写得清清楚楚：

```go
// nextAudioSeq numbers the gateway→client binary audio frames. Monotonic
// across the session because the client drops frames at or below its
// barge-in watermark.
nextAudioSeq uint32
```

客户端确实如此：`AudioPlaybackGate.shouldAccept` 丢弃 `sequence <= interruptWatermark` 的帧，而那个水位线由 `interruptNow()`（barge-in / 系统中断）设下，**只在 `startCapture()` / `stopCapture()` 重置 —— 从不按轮清理**。

## 3. 但透明重开破坏了它

`handler.go` 的 reopen-once 路径（`docs/45`）：

```go
reopened, openErr := h.provider.Open(ctx, session)   // ← 全新的 provider session
if openErr == nil {
    if _, startErr := reopened.Start(ctx, voiceproto.SessionStart{}); startErr == nil {
        rt.provider = reopened                        //    nextAudioSeq 从 0 重来
```

`Open()` 返回一个**新建的** `volcDuplexProviderSession`。序号从 1 重新开始，而客户端的水位线还停在几百。

于是**之后每一帧都 `sequence <= 水位线` 被丢弃**。表现完全对应真机报告：

| 现象 | 原因 |
|---|---|
| 文字照常返回 | 文字走的是另一条分支，不经过播放门禁 |
| 音频永久消失 | 门禁的水位线整场不清 |
| 会话继续、不报错 | 门禁丢弃是**静默**的，不发任何事件 |

复现输出（先红）：

```
--- FAIL: TestHandler_AudioSequenceSurvivesTransparentReopen
    frame after the reopen is numbered 1, at or below the 3 already sent:
    the client discards every frame at or below its barge-in watermark,
    so the rest of the session would be silent
```

**为什么之前没被发现**：单看任何一侧都自洽 —— 后端的注释是对的，客户端的水位线逻辑也是对的。**它们是两个仓之间的一条隐式契约，而重开这条路径把它踩了。**

## 4. 方案

序号是**面向客户端的**，客户端比 provider session 活得久，所以新 session 必须**接着数**，不能从头数。

```go
// provider.go
type SequencedVoiceProviderSession interface {
    VoiceProviderSession
    NextAudioSequence() uint32
    AdoptAudioSequence(uint32)
}
```

```go
// handler.go —— 重开成功后、替换 rt.provider 之前
carryAudioSequence(rt.provider, reopened)
```

`carryAudioSequence` 对两侧都做类型断言，**不实现该接口的 provider（mock / dev-echo）原样放过** —— 它们本来就不给帧编号。

### 为什么不改客户端

客户端的门禁逻辑本身没错（丢弃被打断那一轮的在途音频），错的是它依赖了一条被破坏的前提。在后端修复这条前提，比在客户端加一个"序号看起来变小了就重置"的启发式要诚实 —— 那种启发式会在真正的乱序场景下帮倒忙。

**残留风险（已记录，未处理）**：客户端的水位线仍然是整场黏住的。如果将来出现别的序号回退路径，症状会一模一样（文字正常、音频全无、无任何日志）。见 §6。

## 6. 本票不做

- **不给客户端加序号回退启发式**：见 §4。
- **不改重开策略**：reopen-once-per-turn 是 `docs/45` 的结论，本票只保证重开不破坏序号契约。
- **不给"门禁静默丢弃"加日志**：那是 iOS 侧的事，见 meta `77_` F18 的备注。
