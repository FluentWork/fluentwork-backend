# 静音保活：`input_audio_mute.commit`

**日期**：2026-09-11
**状态**：实现与测试已齐。门禁见 §6。
**对应**：meta `77_` **P0-4** · 执行计划**步 6**

## 1. 守住的不变量

**上行音频流是 duplex 会话的保活信号 —— 它一停，会话就开始等一个永远不会来的输入。** 客户端在两轮之间停发音频是**有意的**，必须说出来；沉默和掉线在服务端看来是一样的。

## 2. 事件语义（来自官方文档）

| 事件 | 作用 |
|---|---|
| **`input_audio_mute.commit`** | 声明麦克风静音。客户端关麦后不再发音频**必须**发它，否则服务端收不到输入会超时，模型无响应 |
| **`input_audio_unmute.commit`** | 恢复麦克风时发送,解除静音 |

### 一个必须分清的区分

**它和我们已经在发的 `input_audio_buffer.commit` 不是一回事：**

| | 做什么 |
|---|---|
| `input_audio_buffer.commit` | **强制端点** —— 结束当前音频查询,让模型开始回答 |
| `input_audio_mute.commit` | **声明麦克风静音** —— 告诉服务端"接下来没有音频了,这是有意的" |

两者在轮末**几乎同时发出**,做的是不同的事。仓库里此前只有前者。

## 3. 为什么正好是个缺口

代码里**已经有一个保活机制**:`DuplexSession.sendSilence` 每 20ms 发一块静音帧。

**但它的生命周期是 `collectTurn` 的:**

```go
silenceCtx, stopSilence := context.WithCancel(ctx)
defer stopSilence()          // ← collectTurn 返回即停
go s.sendSilence(silenceCtx)
```

所以分工是:

| 时段 | 谁在保活 |
|---|---|
| **轮次收集期间** | `sendSilence`(静音帧) |
| **两轮之间** | **没有任何东西** ← 本票补的就是这里 |

而 `docs/40` 之后客户端**只在说话窗口内**发 PCM —— 也就是轮次之间**确定**是静默的。这个窗口正是 P0-4 描述的"客户端两轮之间确实什么都不发"。

**为什么不干脆让 `sendSilence` 一直跑**:在两轮之间持续灌静音帧会把这些静音**喂给 ASR**,可能干扰服务端 VAD 的判断,而且一直在传无用的带宽。协议给了专门的事件,就用它。

## 4. 实现

```go
// 轮末:声明静音(在 CommitAudio 之后、WaitTurnResult 阻塞之前)
if !s.inputMuted {
    if err := s.session.CommitInputMute(ctx); err != nil { return nil, err }
    s.inputMuted = true
}

// 下一轮第一块音频到达:先解除静音
if s.inputMuted {
    if err := s.session.CommitInputUnmute(ctx); err != nil { return nil, err }
    s.inputMuted = false
}
```

三处要点:

1. **声明必须在 `WaitTurnResult` 阻塞之前。** 轮末就是客户端静默的起点,而 `WaitTurnResult` 会阻塞整个轮次收集 —— 把声明放在它后面等于没发。
2. **解除静音挂在"第一块音频到达"上,不是挂在 `user.speech.start` 上。** 音频才是事实;控制帧可能缺失或乱序。
3. **状态必须真的被跟踪。** 静音事件每段静默**只能发一次**,没有前置静音的解除静音(或连续两次)是协议违规。

### 一次被测试抓出来的实现缺陷

第一版把"重置静音状态"放进了 `defaultResetDuplex`。但 `resetDuplexFn` 是**可注入的缝** —— 一个自定义 reset 会绕过它,把旧会话的静音状态带到新会话上,新会话**永远不会被解除静音**。

测试直接抓到:

```
✘ TestVolcDuplexResetClearsMuteState
  mute state survived a duplex reset; the new session would never be unmuted
```

改为放在 `resetDuplex` 分派处 —— 这个不变量属于**任何** reset,不属于某一个实现。

## 5. 未核实（记录在案）

官方 SDK 文档提到一个**会话级输入模式** `input_mod: "keep_alive"`,描述的场景与静音事件相同("麦克风可能被静音、没有音频到达服务端")。

**它是不是这些事件的前置条件,没有核实。** 往 `session.create` 里塞一个猜来的配置字段,比不塞更危险 —— 猜错只会得到一个静默失效的会话。**本票只发有明确文档的事件**;`input_mod` 待查官方文档原文后再定。

### 顺带发现（本票不做）

`collectTurn` 的读错误分类只区分 `context.DeadlineExceeded`:

```go
if errors.Is(err, context.DeadlineExceeded) {
    // 优雅降级 → timeout / partial
} else {
    collectErr = fmt.Errorf("%w: %w", ErrDuplexClosed, err)   // ← context.Canceled 也走这里
}
```

而 provider 拿到 `ErrDuplexClosed` 就 **reset 整个 duplex**(丢弃服务端会话上下文)。也就是说:**一次调用方的取消(context cancelled)会被当成"上游连接已死"。**

生产上 `HandleClientControl` 拿到的是 WSS handler 的 ctx,客户端断开时取消 —— 那种情况下 reset 无害(会话本来就要结束)。但这是**分类过宽**,与代码里另一处的注释所持的立场("provider error 事件不同于连接死亡,reset 会丢弃服务端上下文")不一致。

**记录,不在本票修** —— 它和静音保活不是同一件事,改它要单独评估。
