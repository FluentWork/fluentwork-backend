# 语音链路重构设计 2/3：真机坑 → 结构性防御

**系列**：`96_`（架构）、`97_`（接口）→ **`98_`（本文）**
**状态**：设计 + 实施结果（M1–M6 已落地，见 §七；其中 §五 已被后续提交越过去，见该节下的现状说明）。

这份文档是这套设计**存在的理由**：把过去踩过的每一个坑，
映射到一条**结构上不可能重犯**的机制。没有对应坑的设计一律不做（`96_` §5）。

**表格里"来源"一列是有意的**：区分"真机踩过"、"审核发现"、"已有测试钉住"。
把审核发现写成真机踩过，是造假；把真机踩过的当成推测，是浪费。

## 一、坑 → 防御 对照表

| # | 现象 | 来源 | 根因（当时的修法） | 本设计的防御 | 怎么证明 |
|---|---|---|---|---|---|
| 1 | **透明重开后整段音频消失**：转写还在，声音没了 | 真机 | 序号是 provider 的字段，重开即从 1 重来；iOS 的丢帧水位活整个 WSS，把新帧全丢了。修法：`carryAudioSequence` 手工搬运 | 序号属于**会话**（`SeqAllocator`），provider 无权拥有它 | 测试：重开后 `Next()` 严格大于重开前的值；且**删掉搬运代码仍绿** |
| 2 | **梯子音频被当成 AI 的输出**，每级说完就重开沉默窗口 → 永远停在 level 1 | 审核发现（今天） | 梯子音频走了 provider 那条记账路径 | `Utterance.Kind` 决定策略分流（`97_` §四） | 测试：连出三级，第二级必须是 level 2 |
| 3 | **一次把整段音频写进 socket**，用户还没来得及反应就播完了 | 审核发现（今天） | 帧在内存里连着写，全堆在内核缓冲 | `UtteranceWriter.Audio` 按**真实耗时**发送；节奏可注入（`streamWriter.pace`） | 测试：注入非零 `pace`，确认"未到时间不发下一帧" |
| 4 | **客户端按 `{"data":{...}}` 解码，服务端发扁平结构**，每级静默掉静态库 | 真机 | 两份形状声明，测试 fixture 与客户端犯同一个错 | 跨包契约测试**驱动真 handler**，不手写响应体 | 现有 `rescue_client_test.go` / `hit_writeback_test.go` 的做法推广为规范 |
| 5 | **`55000000` 看起来像"没授权"**，实际是说话人与资源代际不匹配 | 真机 | vendor 的错误码语义模糊，且默认值就是个错的值 | 配对规则前置校验（已在 `content/tts` 落地）+ 默认值必须有测试证明"本账号可用" | 测试：默认 speaker 必须通过与 resource 的配对校验 |
| 6 | **空会话进回顾管线产生垃圾** | 真机 | 上游没有拒绝，下游各自处理 | 边界在**入口**判：`Turn` 状态机拒绝非法迁移并**记录** | 测试：`Idle → Speaking` 被拒且计入计数器 |
| 7 | **`client.turn.abort` 转发失败发 error 帧会杀掉会话** | 真机 | 策略散在 case 里，没人能看全 | 策略表（`96_` §4）显式写出"不告知"及其理由 | 测试：断言该路径**不发** error 帧 |
| 8 | **写路径无限期阻塞**（长 TTS 打断时） | 真机 | 写锁没有上界 | 每次写都有 `resolveWriteTimeout` | 已有测试；设计中收敛为 `Writer` 的默认行为 |
| 9 | **不产生字节的调用抢写锁**，导致 interrupt 设置的标志没生效 | 真机 | `sendOutbound` 无条件取锁 | `writableOutbound` 前置判断（已有）；设计收敛为 `Writer` 的契约 | 已有测试 |
| 10 | **B15 超时被当成答错** | 真机（在**闪测判定**里，不在语音链路） | 判定与超时混在一起 | 同一条教训搬到语音侧：超时是**产品决策**，集中在 `TurnTimeouts`（`97_` §2.3） | 测试：各超时值有直接断言（不是只测行为） |
| 11 | **`ease_factor`/`real_use_count` 建了字段没有写入方** | 真机 | 字段先建、写入方后补，中间没人跟踪 | 跨进程调用必须**驱动真 handler**；字段与写入方同提交 | devnotes 规则 6；`TestSynthesizeEndpointHasAConsumer` 是范例 |

## 二、新增的四条防御（现有规范里没有的）

前十二条都是"把已经发生过的坑钉住"。下面四条是这次设计**新引入**的，
针对的是"还没发生但结构上允许"的失败。

**落地情况（2026-09-20 核对）**：**D1 与 D4 已实现**——拒绝计数在 `turn.go`（`rejected`
计数器 + `NoteFirstOutput`/`NoteAIEnd` 幂等），边界判据在 `.golangci.yml` 的
`no-poc-in-production`。**D2 与 D3 没有实现**：`turn_id_source`、
`audio_in_bytes` / `audio_out_bytes` / `frames` 全仓零命中（`streamWriter.sentBytes`
只用来算时长，不是 D3 说的那个核对）。这两条仍在下表里，但读者不该以为它们在跑。

### D1：状态机拒绝非法迁移并**计数**

```go
// 被拒的迁移不是错误，是证据。它们说明有人在错误的时机发了帧，
// 而现状下这种帧会被静默地"按当前状态"处理掉。
rejectedTransitions.WithLabelValues(from, to).Inc()
```

**为什么**：现状里 `user.speech.end` 在 `collecting` 时会被静默丢弃
（`startCollectTurn` 的 CAS 失败路径只打一条日志）。如果 iOS 有重发行为，
我们看不到频率。计数之后，"客户端是否重发"变成一个可观测的事实。

### D2：每一帧的**来源**在日志里

现状日志有 `session_id` / `turn_id`，但**没有"这个 turn_id 是怎么来的"**——
是客户端给的、还是回落到会话 id 的？排查时靠猜。

设计：turn id 确定的那一次记录 `turn_id_source=client|session`。
一个字段的成本，换掉"为什么这轮的 id 长得不一样"这类问题。

### D3：音频链路的**端到端字节数核对**

现状：没有任何地方核对"发出去的音频字节数"与"合成/收到的字节数"是否一致。
坑 #1（序号重置）与坑 #3（一次写完）都是**静默**的——用户端只是"没声音"或"听完了"。

设计：每个 `Utterance` 结束时记录
`audio_in_bytes`（供应商/合成给的）、`audio_out_bytes`（写出去的）、`frames`。
两者不等就是 bug，且**当场可见**。

### D4：`voicepoc` 的边界写进 CI

现状：包名骗人（生产传输层住在 `poc` 里，`94_` F7）。

设计：拆包后，用一条测试或 lint 规则钉住"生产代码不依赖 poc 包"。
**判据**：`go list -deps ./internal/voicegateway | grep voicepoc` 为空。

### 每步的**停手条件**（重要）

| 信号 | 含义 | 动作 |
|---|---|---|
| 任何现有测试需要**改断言**才能过 | 行为被动过了，而不是结构 | **停手**，重新设计 |

## 五、M3 为什么被重新界定（2026-09-18 实测）

原计划让 provider 也走 `UtteranceWriter`。实施时发现**这会静音**，于是停在上线前，
改为只共享切帧层。

### 现状说明（2026-09-20 追加，本节其余部分是当时的实测记录）

**这一节的结论已经被越过去了，理由没有变。** 当时的结论是"不能给 AI 的音频发
`ai.tts.start`"；今天的结论是**必须发，而且必须发在该轮首帧音频之前**。

变的是客户端那半边：legacy 回退路径已经拆掉，没被 start 认领的帧不再"漏"到引擎，
而是被当作归属未知直接丢弃。于是失败形态仍然是静音，只是方向反了过来——
**不发 start = 静音**。网关侧的落地见 `provider_volc_duplex.go` 的 `AssistantAudio`（流式
路径，首帧之前发，每轮恰好一条）与 `turnToOutbound`（批处理路径，且不重复发）；
被打断的轮不发 start。真机判据见 `docs/101_` §1。

下面保留 2026-09-18 当天的实测与判断——它是 M3 只共享切帧层、不共享流的理由，
"为什么当初不能发"这件事只有这里有记录。

### 机制

iOS 用"有没有见过 `ai.tts.start`"决定二进制帧的归属。**下面是当时的代码形状，今天已不存在**
（那条双路径分叉在客户端侧被整条删除，见 iOS `docs/70_tts_wss_refactor/07_`）：

```swift
let consumedByTTS = try ttsDispatcher.handle(audio: frame)
if consumedByTTS { /* 交给解码器 */ } else { await audioEngine.play(frame: frame) }
```

- **见过 start** → 帧进 TTS 解码器
- **没见过 start** → 帧进 `audioEngine.play`（就是当时让 AI 出声的那条路）

当时生产绑的解码器是 `MockTTSDecoder`：**只记录，不驱动引擎**。那个绑定也一起拆掉了。

于是当时的算式是"给 AI 的音频加一个 `ai.tts.start`"= 把每一帧交给一个会丢掉的解码器
= 静音。今天这条算式两端都已消失：既没有那个空壳解码器，也没有"漏到引擎"这条路径。

### 这不是推断

iOS 侧 `AppDependencies.swift` 的原话（2026-09-12 回滚）：

> `EngineBackedTTSDecoder` … wiring it in silenced the assistant on device the
> moment the gateway started sending `ai.tts.start`. … Both were rolled back …

**他们那半边是一行，我们这半边是这一处。** 两边必须同批重新上线，中间做真机验证
——失败形态是静音，两边都没有单测看得见。前置是他们的 Opus 解码器（ADR-0073）。

**（2026-09-20 追加）实际没有按"同批"走。** 客户端先把回退路径整条删掉（`d004869`），
网关随后开始发 start（`3cb3774`，顺序在 `afe5eb5` 修正）。两步之间的空窗期正好是
这条警告描述的危险窗口——它没有造成静音，只因为两侧的落地顺序恰好是"先拆旧路、
再开新路"。这条经验仍然成立：**跨仓的行为改动没有一个能对齐的开关**。

### 所以这一步做了什么

| 共享 | 不共享 |
|---|---|
| 切帧：`audioFramer`（切片、编号、留尾） | 流的开合：`ai.tts.start` / `ai.tts.end` |
| 帧编码：只剩 `voiceproto.AITTSAudio.Encode()` | 发送节奏（梯子按说话速度，AI 由供应商决定） |
| 帧长：`AudioFormat.FrameBytes` 推导 | |

共享的那一半正是 `94_` F4/F5 说的重复；不共享的那一半恰好是**会改变线协议**的
部分。等前置到位，`streamWriter` 直接接上 provider 即可——framer 已经在它下面了。

### 剩下的一条（2026-09-20：前置已不成立，这一步以另一条路走完了）

| 步骤 | 前置 |
|---|---|
| ~~让 `ai.tts.start` 覆盖 AI 的音频（真正统一两条流）~~ | ~~iOS ADR-0073 解码器落地 + 恢复 `EngineBackedTTSDecoder`；两边同批上线，中间真机验证~~ |

**走完的方式不是当初设想的那条**：没有等 ADR-0073，也没有恢复 `EngineBackedTTSDecoder`，
而是**删掉回退路径**——客户端不再需要"没有 start 时也能出声"，于是"发 start 会让帧进
空壳解码器"这个前提自己消失了。`ai.tts.start` 现在覆盖 AI 的音频，但流控制仍然没有
合并到 `streamWriter`：发 start 的是 `AssistantAudio`，framer 依旧只负责切帧。
`96_` §6 的 M3 判据（`encodeAudioFrame` 消失）因此仍然成立，而"两条流统一"这件事
只统一了信封，没有统一发送方。

## 六、如果只做一件事

**做 M1（`SeqAllocator`）**。

理由：它最小、最独立、收益最直接——**真机坑 #1 就是它**（重开后整段音频消失），
而且它是 M2/M3 的地基（`Utterance` 里"谁分配帧号"的答案是它）。
一个下午的量，208 个测试兜底。

## 七、实施结果（2026-09-18，M1–M6 全部落地）

| M2 | `b18664b` | `Utterance` / `UtteranceWriter`：救援先走它。帧长由 `AudioFormat` 推导 |

| F6 四种失败策略散在 case 里 | ✅ 关闭（M5） |

### 仍未关闭的两条（下一轮，不在 M1–M6 范围）

1. **provider 侧仍有一套 turn id 回落**（F1/F3 的残余）：客户端没给 turn id 时，
   handler 回落 session id、provider 回落 `turn-<seq>`，同一个 turn 仍会以两个名字
   出现在不同帧上。修它要动 provider 对客户端 id 的处理。
2. **上行块 640 仍是两处字面量**（F5 的残余）：`voiceduplex.pcm16kChunkBytes` 与
   `voicegateway.devEchoChunkBytes` 都是 20ms@16k 的两个名字。现在两处都在，
   `TestAudioSizesAreDerivedFromTheSampleRate` 钉住了它们与该采样率的关系。
   （前者的包名是 `voiceduplex`——M6 把它一起搬出了 `voicepoc`。）

### 一条必须说清的话

**M1–M6 全部落在无法用单测验证真机行为的地方。** M3 碰的是主音频路径，M4 改了 badge
与救援锚点的取值路径，M5 改了所有控制帧的错误策略。单元测试与契约测试全绿，但
"AI 还出声吗、梯子还听得见吗、打断还灵吗"只有真机能回答。
