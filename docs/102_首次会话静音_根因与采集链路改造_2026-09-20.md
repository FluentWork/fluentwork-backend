# 102 · 首次会话静音：根因分析与采集链路改造

**日期**: 2026-09-20
**范围**: iOS 采集链路为主，跨 backend（第 1、2 起事故在服务端/配置侧）
**状态**: 根因已定位并取证；改造设计已定，尚未实施
**分支**: `fluentwork-ios` @ `refactor/voice-capture-best-practice`（从 `ff2c142` 起）

---

## 0. 一句话

冷启动后的**第一次会话**里，麦克风 tap 在用户说话的整整两秒内**一个 buffer 都不产出**——引擎 `isRunning == true`、tap 已安装、没有任何错误日志、两端测试全绿、房间显示"正在转写"。根因是 **`AVAudioEngine` 的输入渲染在第一次播放之前不启动**，而链路上每一处能发现这件事的闸门都是静默的。

---

## 1. 症状：三次静音事故，同一个形状

本轮真机联调中，同一条链路上出现了三次"用户说完话，AI 没有任何反应"。三次的**成因各不相同**，但**形状完全相同**：

> 两侧测试全绿 · 日志里没有 error · 房间看起来正常 · 用户看到"正在转写"

| # | 静音成因 | 分层 | 靠什么才发现 | 状态 |
|---|---|---|---|---|
| 1 | 后端 `ai.tts.start` 发在它所引出的音频**之后** | 服务端 | 人耳听到没声音 | 已修 |
| 2 | `.env.volc.local` 重建时丢了 provider 与音频格式两行 → 上行每帧被丢 | 配置 | 逐帧日志对比 | 已修 |
| 3 | 引擎在跑、tap 已装，但 **tap 在前 11 秒一个 buffer 都不产出** | 客户端 | 时间线对齐 | 根因已定，未修 |

三次都不是"某个函数写错了"，而是**链路可以在无人察觉的情况下断掉**。所以本轮的改造目标不是修某一个 bug，而是**让这一类失败在结构上无法静默**。

---

## 2. 证据链（事故 3）

### 2.1 时间线

```
 3974ms  capture_armed        running=true，tap 已装
 3975ms  用户按下"开始说话"
 6048ms  用户按下"说完了"      （实际说了 2.07 秒）
 6050ms  回合 partial、audio_frames=0、上行 0 字节
15210ms  救援梯子开始播放      （ai_first_chunk）
15494ms  capture_first_buffer  ← tap 的第一个 buffer
```

**用户说话的整整两秒里，tap 一个 buffer 都没产出。** 第一个 buffer 出现在第一次播放之后的 **283.9ms**。

### 2.2 关键：这个延迟是稳定的

| 运行 | `capture_first_buffer` 与 `ai_first_chunk` 的间隔 |
|---|---|
| 上一轮 | 283.638ms |
| 本轮 | 283.937ms |

两次几乎相同 ⇒ 不是竞争、不是偶发，而是**一个确定性的启动顺序**：输入渲染由输出启动，延迟约 284ms。

### 2.3 这不是"第一次会话偶发"

复现条件明确：**app 冷启动后的第一轮会话**。因为只有第一轮处于"引擎已启动但还没有任何东西播放过"的窗口里；一旦放过一次 TTS，I/O 就起来了，后续轮次不再复现。这也解释了为什么它给人"时好时坏"的印象。

## 3. 已证伪的假设（含走过的弯路）

记录下来是为了**不要在改造里重复**。

### 假设 A：采集格式不对（转换器 / channel map / 源格式）

加了格式诊断（`captureDropped` 现在带源格式、目标格式、buffer 格式、帧数）。结果：**格式全部正常**，转换器非 nil，`convertToPCM16` 从未走到 `return nil`。

⇒ 证伪。诊断保留（它确实值得留）。

### 假设 B：引擎没真正在跑

从**一次** `engine_running: false` 的读数推断"引擎没起来"，据此加了 `guard engine.isRunning else { throw }`。

**这是我的错误**：那次的 `false` 与下一轮的 `true` 不一致，我拿单次观测当成了根因。守卫本身无害（"`start()` 返回 ≠ 在跑"确实值得断言），**但它不是根因的修复**，并且它的存在一度掩盖了真正的证据（引擎在跑、却依然没有输入）。

### 假设 C：给渲染周期一个源，输入就会被拉动（`ff2c142`）

往 Mixer 接一个渲染静音的 `AVAudioSourceNode`，期望"有源在拉，输入就会跑"。

**实测无效**：`capture_first_buffer` 仍然只出现在第一次播放之后，间隔 283.9ms（对比 283.6ms，**没有变化**）。

⇒ **机制假设已证伪。** 拉得动输入的不是"渲染周期有源"，而是 **`playerNode.play()`** 这一个动作。这条弯路不要在新设计里重复。

---

## 4. 根因

**`AVAudioEngine` 的输入 I/O 不会因为 `engine.start()` 和 `installTap` 就产出数据；在本项目的图（`playAndRecord` + `.voiceChat` + 单一引擎同时承担采集与播放）里，它由第一次 `playerNode.play()` 触发，之后稳定约 284ms 开始投递。**

而客户端**从未自证过"我在听"**：

- `startCapture()` 只断言了引擎 `isRunning`（本会话新加），**没有断言过麦克风真的产出**
- 于是会话可以在**一支从未产出过任何音频的麦克风**面前宣布"可以说话了"
- 用户 tap → 窗口开 → 没有数据 → 上行 0 字节 → 后端的空回合快速失败（本会话已从 60s 收紧到 3s，带明确原因）

**这就是三次静音的共同形状**：链路可以在"看起来正常"的状态下不传输任何东西。

---

## 5. 为什么测试没发现

三个结构性缺口，都不是"少写了一条测试"：

1. **测试 double 只在窗口内发 PCM。** `MockAudioEngine.emitChunk` 被 `isSpeaking` 守卫，只在一次 utterance 内产出；它**无法表达"窗口外没有音频"**。真机上的失效形态（engine armed 但零投递）在 mock 里不存在。
2. **没有上行回环测试。** `DevEchoFixtureGenerator`（1kHz 正弦）只覆盖**下行**。上行缺一个等价物——喂一个已知音调进采集路径，断言它到达传输层。**这是三次静音都不被单测发现的直接原因。**
3. **失效发生在 mock 表达不了的层。** 三次都住在"引擎/hardware/配置"这一层，而这一层的可测性依赖五个注入点（`requestMicrophonePermission` / `startEngineForPlayback` / `applyVoiceProcessing` / `installCaptureTap` / `startCaptureEngine`），没有一个能模拟"tap 装上了但永不投递"。

## 6. 采集链路的静默闸门全清单

这是本次排查最有复用价值的产出：**每一处"音频可以不声不响地消失"的地方**。改造的第三原则就是逐个消灭它们。

### 6.1 引擎侧（`LiveAudioEngine`）

| 位置 | 今天的行为 | 可观测性 |
|---|---|---|
| `processInput` 的 `guard !isSystemInterrupted` | 整个中断期间静默丢弃 | 无 |
| `guard converter != nil, sourceFormat != nil` | `captureDropped(reason:)` | ✅ 每采集会话一次 |
| `convertToPCM16` 四处 `return nil` | `captureDropped(reason:)`（含三个格式） | ✅ |
| 采集 tap 弱引用 `guard let self` 后 buffer 消失 | 静默 | 无 |
| **引擎 isRunning 但 I/O 未真正运行** | **完全无人知道** | ❌ **根因所在** |

### 6.2 中间件侧（`SpeechSessionMiddleware`）

| 位置 | 今天的行为 | 可观测性 |
|---|---|---|
| `guard speechCaptureGate.shouldForwardPCM else { continue }` | 窗口外丢弃（**策略**，非错误） | ❌ **无计数、无日志、无事件** |
| `guard speechCaptureGate.isOpen`（I20 abort 抑制尾帧） | 静默 `continue` | ❌ |
| `.speechStarted` 触发的那个 buffer 先于事件到达 → 被闸门吃掉 | 静默 | ❌ |
| `sendAudioPCM` 抛错 → `return nil` | **永久杀死该 store 的音频泵** | 仅一次 dispatch |

> **注意**：`SpeechCaptureGate` 是上行**唯一一个完全静默**的闸门。引擎侧为了报告格式级丢弃写了一大堆诊断，而闸门连一个计数器都没有——**"闸门吃掉了多少音频"在今天没有任何数字可以回答。**

### 6.3 下行侧

`TTSPlaybackCoordinator` 已有 `TTSFrameOutcome`，但未接进计数；"收到帧"与"真的出声"没有分开断言。

## 7. 改造设计

分支 `refactor/voice-capture-best-practice`，从 `ff2c142` 起。

### 第一原则：「就绪」必须同时意味 socket 与麦克风都成立

今天 `.connecting` 只等 `socketReady`（`SpeechSessionMachine.swift:38`）：

```
.idle --sessionStartTap--> .connecting --socketReady--> .aiSpeaking
```

于是房间可以在从未产出音频的麦克风面前宣布"可以说话了"。

改成：

```
.connecting --socketReady-->  .connecting（记下 socket 好了，继续等）
.connecting --captureLive-->  .aiSpeaking
```

- 两条**都**成立才进 `.aiSpeaking`
- **不需要新相位**：`.connecting` 的语义本来就是"会话正在建立"，把麦克风也算进去是把它说准
- **界有现成的**：`scheduleConnectWaitTask`（中间件 `:1400`）已经在 `.connecting` 上挂了 `connectWait` 看门狗，超时 → `.failed("连接超时，请重试")`——用户可见、可重试。采集等待天然被它盖住
- UI 文案不用改：多等 ~300ms 的「连接中」是正确的

### 第二原则：先把 I/O 拉起来，再等它证明自己

光有门不够——如果什么都没在播，输入永远不产出，门会一直等到看门狗超时。所以要在 `startCapture()` 之后**主动踢一下输出**：

- 一个**专用的 keep-alive player node**，会话开始时播放一次极短的静音缓冲
- **与 TTS 的播放节点分开**：`interruptNow()` 会 `playerNode.stop()/reset()`，共用节点会在每次 barge-in 之后把 I/O 再关掉
- 复用既有的 `FWTryCatch` 包住 `play()`——它是会抛 `NSException` 的调用

> ⚠️ **这是待验证的机制假设。** 证据是"输入在第一次播放之后 284ms 才启动，且两轮几乎相同"，指向"`playerNode.play()` 才是启动 I/O 的动作"。但本会话已经错过两次（假设 A、B），**假设 C 更是实测被证伪**，所以这一条必须真机验证通过才算数。

### 第三原则：没有静默的 `return`

| 位置 | 改成 |
|---|---|
| `convertToPCM16` 各处 `return nil` | `captureDropped(reason:)`（已加） |
| `processInput` 裸 `return` | 同上 |
| `isSystemInterrupted` 守卫 | 计数（中断期丢弃是正常的，但要看得见） |
| `SpeechCaptureGate` 为假 | 计数：窗口外丢弃是**策略**，不是错误，但数量要能读 |
| 引擎 `isRunning` 但 I/O 未跑 | `captureLive` 门 + `captureArmed` 四态（已加） |

### 第四原则：「帧到了」≠「出声了」

两端各一套独立计数，断言分开写：

- **上行**：captured / sent / dropped(gate) / dropped(convert)
- **下行**：received / dropped(reason) / **played**

外加**上行回环测试**（第 5 节缺口 2）。

### 落地顺序

| 步 | 内容 | 依赖 | 验证方式 |
|---|---|---|---|
| 1 | 采集存活：`captureLive` 事件 + `.connecting` 双条件 | 无 | 单测（状态机）+ 真机 |
| 2 | keep-alive player 踢 I/O | 1（否则无法确认踢没踢到） | **真机** |
| 3 | 可观测性补齐（第 6 节各处 + 两端计数） | 无 | 单测 + 真机 |
| 4 | 上行回环测试 | 3 | 单测 |

**1 和 3 可以先做**，它们不依赖未验证的机制假设，且**立刻**把静音变成可见失败。**2 是让首次会话真正可用的那一步，但必须真机确认。**

## 8. 验收

- `swift test`：**改造后 575 条，失败集合与基线逐条相同**（见 §9.5——5 条播放测试因本机无 IO cycle 而红，基线同样红）。判定标准是"未引入新失败"，不是"全绿"。
- **真机**：首次会话（冷启动后第一轮）——`capture_first_buffer` 出现在 `vad_speech_start` **之前**；用户说完后有真实转写与 AI 应答
- **真机**：把 keep-alive 关掉跑一次，应当看到「连接超时，请重试」而**不是**静默的「正在转写」——**这条验证的是第一原则本身**

## 9. 待验证 / 未解

1. **`playerNode.play()` 是否真的能稳定拉起输入 I/O。** 只有一次真机确认才算数。
2. **首次播放之后的 284ms 从何而来。** 数字很稳定，但成因未解（可能是 AEC/voiceChat 的参考信号建立，也可能是 I/O 缓冲的固有延迟）。不影响修复，但值得记一笔。
3. **`interruptNow()` 之后 I/O 是否会再次停摆。** 若会，则每次 barge-in 都在重演事故 3 的局部版本——需要在真机上专门验一轮"打断后立刻说话"。

## 9.5 同一机制的第二例（macOS，排查改造时撞到）

实施改造期间，本机 `swift test` 里 5 条断言"真的在播放"的测试变红。用**未改动的基线提交**在独立 worktree 里复跑，**同样的 5 条、同样的 9 个 issue** —— 与本次改造无关，是环境问题。

独立探针（一个最小 `AVAudioEngine` + `AVAudioPlayerNode`）给出的话是：

```
engine.start OK, isRunning=true
*** Terminating app due to uncaught exception 'com.apple.coreaudio.avfaudio',
    reason: 'player did not see an IO cycle.'
```

**`engine.start()` 返回成功、`isRunning == true`，但渲染循环从未 tick**；此时 `playerNode.play()` 抛 `NSException`。设备列表正常（Mac mini 扬声器，默认输出，2 声道）。

这和 §4 是**同一个机制的第二例**，而且是在完全不同的平台上：

| | 观察 | 共同的错误假设 |
|---|---|---|
| iOS 真机（§4） | `isRunning == true`，tap 一个 buffer 不产出 | "引擎在跑 = 麦克风在工作" |
| macOS 本机（本节） | `isRunning == true`，IO cycle 从未发生 | "引擎在跑 = 扬声器在工作" |

三点结论：

1. **`isRunning` 不是任何东西的证据。** 它证明"启动调用没失败"，不证明"音频在流动"。两个平台、两个方向，各自独立地证伪了它。
2. **生产代码在这条路径上是正确的**：`play()` 被 `FWTryCatch` 包住，异常被转成 `.failed("player start raised: …")` 而不是崩溃。所以真机上表现为"没声音 + 一条 failed"，不是闪退。
3. **改造后的门正好盖住它。** 若 iOS 上出现同样情况（播放起不来 → 无 IO cycle → tap 不产出），`captureLive` 永不成立，会话停在 `.connecting`，10 秒后以「连接超时，请重试」失败——**这正是第一原则要的形状**，而不是"房间正常显示正在转写"。

**未处理**：那 5 条测试本身是环境相关的（需要真实可用的输出设备）。改造成"无 IO cycle 时跳过"会让这套件在该环境下变绿，但**跳过也是一种说谎**——它们问的问题（"真的出声了吗"）在无声设备上无法回答。留作独立事项。

## 10. 附录：取证方法（可复用）

三次事故靠的都是同一类证据：**把两条独立的时间线对齐到同一个时钟上**。

- 客户端 `timings` tracker 打点：`audio_capture_armed` / `vad_speech_start` / `ai_first_chunk` / `audio_capture_first_buffer`，每条带 `total_ms` 与 `prev_event` / `delta_ms`
- 服务端逐帧日志：`audio_frames=N`、上行字节数、`ai.tts.start` 的位置
- 判定方法：**如果"用户说话"与"上行有字节"这两段区间不重叠，问题一定在采集侧，且必然在引擎与 tap 之间**——不要再往后端找

另外两条纪律，本轮踩过：

- **密钥永不打印**，**截断也不行**。检查用存在性判断（`grep -c "^VOLC_SPEECH_API_KEY=."`），不要 `ps eww | grep | cut`。
- `.env.*` 全部 gitignore（`.gitignore:7`），`configs/volc.env.example` 是唯一入库的模板，且**必须包含 `VOICE_GATEWAY_PROVIDER=volc-duplex` 与 `VOICE_GATEWAY_CLIENT_AUDIO_FORMAT=pcm-s16le`**——事故 2 就是因为模板缺这两行，照着它重建配置必然静音。已加测试 `TestVolcEnvExampleCarriesTheGatewayWiring` 钉住。
