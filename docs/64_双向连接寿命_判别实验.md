# 上游 duplex 连接寿命：判别实验

**日期**：2026-09-11
**对应**：meta `77_` **P0-9**
**状态**：**实验已备好，未跑。** 本文只写「跑什么、看什么、怎么读」。

## 1. 要回答什么

一场练习会话里，上游（火山）duplex 会话被重开 = **上下文丢了**。重开本身是恢复逻辑，没错；
错的是**没有任何东西把历史补回来**，于是用户看到的下一轮 AI「不认得上一轮说过的话」。

**已知**（来自归档日志 `/tmp/fluentwork-backend.log.pre-aec`，重启前的二进制）：

| | |
|---|---|
| 重开**不是**本次重启引入的 | 旧日志里就有 **3 次**，与 `4b5968b`（2026-09-03）的日期一致 |
| 自变量是**轮间静默时长** | 旧二进制：55.7s / 60s / 80s；当前二进制：33.7s |
| 探针**从不触发** | `keepaliveIdleThreshold = 60s`，而实测死因发生在 33.7s —— 探针的门槛在死因之后 |

**不知道的**（本实验要分的）：

> 掐断连接的是**火山**自己的空闲超时，还是**本机流量穿过的代理**（`utun7` 持 `198.18.0.1`，fake-IP 特征）。

**为什么这个区分决定修法**：厂商级保活配置（`input_mod`、静音事件）**救不了被中间盒掐掉的连接**；
只有真有字节在流才行。两者都成立时，**唯一对两种机制都有效的修法是「轮间持续发静音」**。

## 2. 为什么不需要精确控制间隔

**因为日志里有时间戳。** 间隔不需要跑准 —— 跑完用检查器把**实际**间隔算出来即可。
所以实验是「跑几次不同量级的间隔 + 用工具读日志」，而不是「写一个能精确控制时序的驱动」。

检查器已经把这件事固化了（`session_id` 在本仓日志里**指两个不同的东西**，这是最容易读错的地方）：

```bash
./scripts/check-duplex-lifetime.py --gaps /tmp/fluentwork-backend.log
```

exit 0 = 每个会话窗口只开了一次；exit 1 = 发现重开。`--gaps` 追加那一列「轮间静默」。

## 3. 跑什么

**跑之前**：确认日志是这一次的（陈旧文件会让结论无效，见 `ios docs/62` §0 第 5 项），必要时归档旧的。

```bash
mv /tmp/fluentwork-backend.log /tmp/fluentwork-backend.log.$(date +%H%M)
# 重启栈，输出接到手册期望的路径
./scripts/dev-up.sh --local-mysql --skip-migrations --host 192.168.2.111 > /tmp/fluentwork-backend.log 2>&1
```

| # | 间隔 | 目的 |
|---|---|---|
| **A** | ~15s | 低于已知死因。**预期：不重开** —— 若不重开，就确认了「空闲时长是自变量」；若重开，说明有别的东西在杀连接，先查那个 |
| **B** | ~35s | 复现已知死因（当前二进制在这一带死过）。**预期：重开** |
| **C** | ~35s，**间隔期间持续出声/发音频** | **判别实验的本体**。字节在流的情况下若**不再重开** → 杀连接的是「空闲」，且**修法（轮间发静音）成立**；若**仍然重开** → 指向中间盒或另有机制 |

**C 怎么做到「持续发音频」**：真机上两轮之间保持说话或哼声即可 —— 客户端在语音窗口内会持续上行，
网关也就持续写上游。**注意这会让厂商的 VAD 认为用户在说话**，可能触发一轮新对话 ——
那本身也是信息（说明「发音频」和「保持静音」在协议上是两件事）。

**可选的 D（更干净的判别）**：让火山域的流量**绕过代理**再跑一次 B。
- B 重开、D 不重开 → **中间盒**。生产（无代理）不受影响，本地开发环境要单独说明。
- B、D 都重开 → **厂商侧**，`input_mod: "keep_alive"` 是正当候选。

## 4. 怎么读

```bash
./scripts/check-duplex-lifetime.py --gaps /tmp/fluentwork-backend.log
```

输出里只要看两处：

- **`duplex 开了 N 次`** —— N > 1 就是上下文丢了，这一场之后的所有轮次都算废
- **`轮间静默`那一列** —— 与它上面那行有没有 `← 这次之后重开`

**读的时候别踩这个坑**：`session_id` 在 `voice.duplex.*` 里是**厂商侧**会话 id，
在 `turn result captured` 和重开那行里是**我们的 app** 会话 id。
两者都是 uuid 形状、都叫 `session_id`，当成一回事会得出完全相反的结论
（比如把「provider 换了」读成「用户换了会话」）。检查器是按这个区分分组的。

## 5. 结论怎么写回台账

按 `77_` 的老规矩：**贴原始输出，不贴转述**。特别是**不通过那次的** —— 它是唯一能回放的东西。

三行足够：

1. A/B/C 各自的**实际**轮间静默（检查器的数字）+ 有没有重开
2. 若跑了 D：D 的结果
3. 一句话结论：死因是空闲（→ 修法：轮间发静音）/ 是中间盒（→ 本地环境单独说明，生产待观察）/ 另有机制（→ 重开一票）

> **`docs/53` §5 那条「未核实」现在可以更新了**：它问的是 `input_mod: keep_alive`
> 「是不是 mute/unmute 事件的前置条件」。目前**没有任何证据支持它是前置条件** ——
> 而**发了静音事件之后连接照样死**，这本身就是一条证据。
> 至于它是不是一条**有效的备选修法**，取决于本实验 A/B/C 的结论，不取决于它是不是前置条件。
