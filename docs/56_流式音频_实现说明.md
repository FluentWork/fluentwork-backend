# 流式音频：让 AI 更早开口

**日期**：2026-09-11
**状态**：实现与测试已齐。门禁见 §6。**未真机验证**，见 §7。
**对应**：meta `77_` **P1-2 音频半边**

## 1. 问题：文本先流式了，但 AI 并没有更早开口

`docs/55` 让 `ai.text.delta` 变成了真增量——字幕好看了。但**音频同样是攒完整轮才发的**：

```go
// turnToOutbound，改动前
if pcm := resampleToPlaybackRate(turn.AudioPCM); len(pcm) > 0 {
    for offset := 0; offset < len(pcm); offset += audioFrameBytes { ... }
}
```

整轮音频一次性重采样、切帧，注释还写着 "The assistant's voice, **last** so it follows ai.turn.end"。

**后果**：用户要等到整轮（ASR + LLM + **全部 TTS**）生成完毕，才听到**第一个音节**。

**对一个"说"的应用，这才是主导延迟。** 文本流式让屏幕上的字早出现，音频流式才让 AI 真的早开口。

## 2. 为什么不能直接把重采样逐块调用

现有实现是**无状态**的线性插值，输出位置由**绝对下标**算出（3:2）：

```go
pos := float64(i) * float64(inSamples) / float64(outSamples)
```

输出样本 `i` 插值于输入 `floor(1.5i)` 与 `floor(1.5i)+1` 之间。**而供应商的分块边界几乎从不落在这个边界上。**

逐块独立重采样 = 每个接缝处把插值相位**重置一次** —— 漂移，加上每个接缝一声爆音。

## 3. 关键推导：流式可以做到逐字节等价，而且**不需要 flush**

流式能不能等价，取决于一件事：**输出样本 `i` 是否依赖总长度。**

上游那行钳位是唯一的嫌疑：

```go
hi := lo + 1
if hi >= inCount { hi = inCount - 1 }   // ← 若会触发，输出就依赖总长度
```

**它从不触发。** 对 `inCount = 3k / 3k+1 / 3k+2` 三种余数分别验算，`hi` 恒 `<= inCount-1`：

| inCount | outCount | 最大 i | floor(1.5i)+1 |
|---|---|---|---|
| 3k | 2k | 2k-1 | 3k-1 = inCount-1 |
| 3k+1 | 2k | 2k-1 | 3k-1 < inCount |
| 3k+2 | 2k+1 | 2k | 3k+1 = inCount-1 |

（`TestResamplerOutputDoesNotDependOnTotalLength` 把这个验算钉住了，见 §5。）

**于是**：输出样本 `i` 只依赖输入 `floor(1.5i)` 和 `floor(1.5i)+1`，而这两个下标对**所有** `i < outCount` 都落在流内。

**所以两个源样本到齐就能出，流结束时正好出满 `outCount` 个 —— 没有东西需要 flush。**

这不是一个"差不多"的近似：**分块输出与整段输出逐字节相同**，`TestPCMResamplerMatchesTheBatchReference` 直接对着**旧实现的原文**比对。

## 4. 实现

### `pcmResampler`（`internal/voicegateway/pcm_resampler.go`）

保留未消费的输入 + 绝对基址 + 下一个输出下标：

```go
type pcmResampler struct {
    pending  []byte // 未消费的输入，s16le
    base     int64  // pending[0] 的绝对样本下标
    outIndex int64  // 下一个要产出的输出样本下标
}
```

`Write` 吐出**这一次能完成的所有输出**，并丢弃后续样本不再需要的输入。

浮点算式刻意与旧实现同形（`outIndex*3/2` 精确可表示，小数部分恒为 0 或 0.5），所以是**逐位复现**而不是近似。

### 批量入口改为委托

```go
func resampleToPlaybackRate(pcm []byte) []byte {
    var r pcmResampler
    return r.Write(pcm)
}
```

**一个实现，两条路径，不会漂移。** 旧实现作为参照留在测试里（`batchResampleReference`）——它必须是**第二份**代码，否则"流式没改一个字节"这句话无从谈起。

### 逐轮重建

`audioResampler` 在每轮开始时重建（`resetTurnStreamingState`）。这是让输出与**今天的批量结果逐字节相同**的原因：旧路径本来就是每轮独立转换的。

### 尾帧必须冲一次

重采样输出不对齐 `audioFrameBytes`，所以不满一帧的尾巴由 `audioPending` 跨块携带 —— 否则每个供应商分块边界都会产生一个短帧，客户端整轮收到参差的帧。**而轮末必须把这个尾巴冲出去**：

```go
if s.streamedAudio {
    for _, frame := range s.frameAudio(nil, true) { ... }   // flush
}
```

不冲的后果有两层：**最后几毫秒被永久剪掉**，而且它留在缓冲里，会被**串到下一轮音频的开头**。

### 一个刻意的顺序变化

音频此前排在 `ai.turn.end` **之后**（"last so it follows ai.turn.end"）。流式之后，绝大部分音频**先于** `ai.turn.end` 到达。

**这是本次改动的目的本身**，且安全：客户端收帧即播（`audioEngine.play(frame:)`），`ai.turn.end` 只负责给转录项定稿，两者在客户端互不依赖。原注释已改写，避免下一个人把它当成约束。

## 5. 红验证抓出的重点：**"流式 == 整段"这条测试是抓不住天真实现的**

`pcmResampler` 的第一版写完后，按惯例做红验证：把 `Write` 改成**逐块独立重采样**（每个分块重置相位）—— 这正是要防的天真做法。

结果：

| 测试 | 天真实现下 |
|---|---|
| `TestPCMResamplerMatchesTheBatchReference` | **依然通过** |
| `TestPCMResamplerCarriesATrailingOddByte` | **依然通过** |
| `TestPCMResamplerIsInvariantToChunking` | **红** |

原因：**单次 `Write` 本来就和整段等价** —— 那条测试永远只喂一块，天真实现在这个输入下与正确实现无法区分。

**只有"换不同的分块方式、输出必须不变"这一条能抓住它。** 这正是分块必须被真正测试的原因：等价性测试看着更严格，实际对"边界"这个唯一的失效维度是盲的。

> 这与 `docs/54` 那次是**同一类**发现——那条 503 的测试断言了症状，两条路径产出同一个症状，所以它分辨不出守卫在不在。**红验证的价值不在于"测试会红"，而在于它会指出你测错了什么。**

## 7. 未做 / 未验

- **未真机验证。** 要验的是：首响延迟的实际改善（AI 是否明显更早开口）、以及整轮音频与改动前**听感一致**（无爆音、无剪尾、无重复）。
- **`server_ts_ms` 仍未消费**（P1-5）——所以这次**拿不到首响 p50/p95 的量化改善**，只能靠听感。这是 P1-5 从"可观测性"升级为"验收前提"的地方。
- **客户端播放队列的深度未评估。** 音频现在来得更早也更均匀，而不是轮末一次性爆发。`LiveAudioEngine` 的调度缓冲（`.unbounded`，见 F13/F18）在这种情况下是否仍然合适，没有测过。
- **不同供应商分块大小的分布未知。** 测试用的是刻意错落的尺寸；真实分块可能更大或更规整，那会影响首响改善的幅度（不影响正确性）。
