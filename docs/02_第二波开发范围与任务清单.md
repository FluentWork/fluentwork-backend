## 二、第二波的目标

第二波聚焦把第一波的骨架做实，并长出"入库"与"内容生成"两面：

1. review 异步管线从 stub 升级为真实评价 + 炼化生成
2. `GET /sessions/:id/review` 扩展为全量返回模型
3. `corpus` 模块与 `phrase_blocks` 表承接炼化入库
4. `content` 模块与 `daily_reads` 表支撑每日一读
5. `B7` 命中检测链路（网关旁路 + 单体执行）

> **第二波的 backend 目标不是继续铺新链路，而是让 session / review / corpus / content 四个面站稳。**

优先阅读顺序：

### 1. 第五章核心链路时序

1. §5.2 会话结束后的异步管线：评价 + 炼化合并一次旗舰模型调用、JSON Schema 校验、幂等键、重试 1 次、评价任务 P90 ≤ 15s
2. §5.1 实时对话链路中的 `B7` 命中检测旁路（800ms 超时，失败跳过）
3. §5.4 每日一读批处理：凌晨 02:00、`uk_user_date` 防重、同步兜底生成、预置内容兜底

### 2. 第三章数据库设计

1. `phrase_blocks` 表结构与索引纪律（JSON 列纪律、锚点字段明文参与检索）
2. `daily_reads` 表与唯一键
3. `ai_cost_logs` 成本埋点纪律：每次 AI 调用同步落一条，不允许后补

### 3. 第四章接口契约

当前第二波最相关的是：

1. `GET /sessions/:id/review`（扩展为全量模型）
2. `GET /corpus/blocks`、`PUT /corpus/blocks/:id`、`DELETE /corpus/blocks/:id`
3. `POST /corpus/blocks/:id/favorite`、`POST /corpus/blocks/batch-accept`
4. `GET /daily-reads/today`、`POST /daily-reads/:id/follow-read`

### 4. 第九章测试与发布策略

1. 调度状态迁移与级联类单测覆盖率 ≥ 90% 的纪律
2. WSS 协议帧用 schema 契约测试防静默变更（`badge` 帧纳入）

### 当前应该优先改的区域

1. `session` review worker：从 stub 升级为真实生成

### 当前不应该抢先展开的区域

1. `drill` 闪测模块
2. 话题卡批处理
3. `material` 素材模块
4. `billing` 真正实现
5. APNs 推送与限流开关
6. 与第二波无关的大规模目录重构

---

## 七、必须遵守的禁区

继承第一波禁区：

1. 不模糊 `app-server` 和 `voice-gateway` 边界
2. 不把第二波目标扩张成完整业务单体
3. 不让 review 异步任务阻塞主链路
4. 不把非核心链路失败升级成主链路失败

第二波补充：

1. 命中检测的实际执行在 `app-server`，网关只旁路触发——检测逻辑不得下沉到网关
2. 每日一读 / 命中检测故障不得影响"说 -> 转录落库"主链路（熔断原则）
3. `anchor_user_said` 按 3.2 要点 4 口径明文落库参与检索，不得自行加密
4. Prompt 口径以 `meta` 的 33 号文档为准，不在代码仓私下定案
5. 每次 AI 调用必须同步落 `ai_cost_logs`

## 八、提交与评审口径

沿用第一波口径：

1. 每个 PR 尽量只对应一个 backend issue 或一个 PR 级任务
2. 契约变化、schema 变化、状态变化应同步补测试或补文档
3. 若 iOS 依赖某接口，优先保证契约清晰，不用临时魔法值凑通
4. 若发现 PRD / 技术方案口径冲突，应先回写 `meta`，不要在本仓私下定案
