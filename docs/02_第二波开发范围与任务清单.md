## 二、第二波的目标

第二波聚焦把第一波的骨架做实，并长出"入库"与"内容生成"两面：

1. review 异步管线从 stub 升级为真实评价 + 炼化生成
2. `GET /sessions/:id/review` 扩展为全量返回模型
3. `corpus` 模块与 `phrase_blocks` 表承接炼化入库
4. `content` 模块与 `daily_reads` 表支撑每日一读
5. `B7` 命中检测链路（网关旁路 + 单体执行）

> **第二波的 backend 目标不是继续铺新链路，而是让 session / review / corpus / content 四个面站稳。**

## 七、必须遵守的禁区

继承第一波禁区：

1. 不模糊 `app-server` 和 `voice-gateway` 边界
2. 不把第二波目标扩张成完整业务单体
3. 不让 review 异步任务阻塞主链路
4. 不把非核心链路失败升级成主链路失败

第二波补充：

1. 命中检测的实际执行在 `app-server`，网关只旁路触发——检测逻辑不得下沉到网关
2. 每日一读 / 命中检测故障不得影响"说 -> 转录落库"主链路（熔断原则）
3. `anchor_user_said` 按 3.2 要点 4 口径明文落库参与检索，不得自行加密
4. Prompt 口径以 `meta` 的 33 号文档为准，不在代码仓私下定案
5. 每次 AI 调用必须同步落 `ai_cost_logs`

## 八、第二波仍需特别盯住的功能薄弱点

1. `B8` / `B9` 最大的功能漏洞不是“还没接 LLM”，而是失败语义容易做坏：Schema 校验失败、重试耗尽、部分字段缺失时，必须仍让转录可回看、状态可解释，不能把回顾页打成空壳。
2. `B10` 如果只把 `phrase_blocks` 表和 CRUD 接出来，但不把 `batch-accept` 幂等、软删除语义、游客归并后的数据迁移口径定死，后续语料库、命中检测、闪测调度都会吃脏数据。
3. `B11` 的薄弱点不在建表，而在生成防重与失败兜底：若唯一键、防重复生成、预置内容兜底三者缺一，每日一读会直接放大成本抖动和空页面问题。
4. `B12` 最容易出事故的是旁路污染主链路：超时控制、重复触发、重复注入、重复下发徽章都要明确去重口径，否则“轻量反馈”会变成主会话噪音。
5. `B13` 若没有先立 `VoiceProvider` 防腐层和降级切换验证，第二波会在功能上看似接通、结构上却把供应商细节扩散进网关主流程，后续回退成本很高。
