# 核心链路质量评估流程（Flow Eval）

**文档版本**: V1.0
**创建日期**: 2026-09-18
**分支**: `eval/moat-core-flow`
**目的**: 把护城河的核心链路串成一条可运行的流，用 mock 输入跑出真实输出，按既定标准打分，量化质量。

---

## 一、为什么需要它

`86_` 审计出的最大缺口是 **M1：判定标准不可执行**——而"标准"不只是闪测判定的 rubric，更是**整条链路缺少一套"什么算好输出"的定义与度量**。没有这套东西：

- 改一版 prompt 无法判断是变好还是变坏（只能靠感觉）；
- 换模型、调参数、加功能都在盲飞；
- 对外说的"质量"无法证伪。

B15 那套离线评估只做 **schema 回归**（喂现成的 review/refine JSON，检查格式与锚点是否在转录里），它回答的是"输出格式对不对"。本文档的流程回答的是**"输出好不好"**。

---

## 二、流的设计

### 2.1 输入

一条 mock 会话（形状与网关上报一致）：

```json
{
  "id": "s001", "scene": "standup", "profile": "filler_heavy",
  "utterances": [{"seq":1,"speaker":"ai","text":"..."},{"seq":2,"speaker":"user","text":"..."}],
  "rescue_events": [{"seq":1,"level":3,"path":"incomplete","ladder":"...","user_opened":true,"anchor":"..."}],
  "expectations": { "min_blocks":1, "max_blocks":5, "topics":["deploy","migration"],
                    "judge_cases":[{"answer":"...","expect":"pass"},{"answer":"...","expect":"fail"}] }
}
```

100 条样本覆盖两个正交维度：**场景**（standup / review / 1on1 / interview / casual）× **口语缺陷**（干净 / filler 多 / 未完成句 / 沉默后被救援 / 母语直译），各取组合。

### 2.2 流经的环节（全部走生产代码）

```
mock 会话
  │
  ├─① 回顾 + 炼化   reviewgen.OrchestratorAdapter（生产 prompt，含救援事件）
  │     └─ 期望输出：三层评价 + 3–5 个三元组；锚点必须来自转录
  │
  ├─② 入库         corpus.Service.BatchAccept（与 iOS 一键入库同一路径）
  │     └─ 期望输出：块落库、状态灯为灰、标签合法
  │
  ├─③ 闪测判定     drill.LLMJudge（生产判定 prompt）
  │     └─ 期望输出：对"等价改写"判 pass、"离题答案"判 fail（金标来自样本自带 judge_cases）
  │
  ├─④ 命中检测     session.HitDetector（确定性打分，阈值 0.65）
  │     └─ 期望输出：同一表达判命中、无关表达判不命中（宁可漏报不可错报）
  │
  └─⑤ 话题卡       topic.Generator（H1 阈值 + H2 落地校验）
        └─ 期望输出：有 block_ids、有 source_note、不泛话题
```

### 2.3 输出（每次运行产出）

```
eval-out/<run-id>/
  samples/<id>.json    每条样本的：输入 → 各环节实际输出 → 逐项判分
  report.json          聚合指标（含每条未达标样本的失败原因）
  report.md            人读版：指标表 + 失败样本清单 + 抽检清单
  review-sheet.md      人工抽检用（默认 10%，含争议项优先）
```

## 三、评价方式（三层）

| 层 | 谁判 | 判什么 | 成本 |
|---|---|---|---|
| **L1 规则** | 代码 | 结构、锚点、枚举、去重、落地（可机检的硬约束） | 免费、确定性 |
| **L2 LLM 裁判** | 模型 + rubric | 质量（忠实度/地道度/可迁移性/评价真实性/话题贴切度） | 每次 1 调用 |
| **L3 人工抽检** | 人 | L2 的争议项与随机样本；校准 L2 是否可信 | 10% 样本 |

**L2 的 rubric（1–5 分）**：

| 维度 | 5 分 | 3 分 | 1 分 |
|---|---|---|---|
| 忠实度 | 完全保留原意 | 大意对但有偏移 | 改变原意 |
| 地道度 | 母语者会这么说 | 语法对但不自然 | 生硬/直译 |
| 可迁移性 | 换场景也能用 | 只能用于本句 | 脱离语境不可用 |
| 评价真实性（review） | 指出的是真问题 | 有 1 条凑数 | 编造问题 |
| 话题贴切度（topic） | 明确来自该用户语料 | 沾边 | 放之四海皆可 |

**L3 的存在理由**：LLM 裁判本身会错。抽检的作用是**校准裁判**——若人工与裁判的一致率 <80%，先修 rubric，而不是相信分数。

---

## 四、评价标准（门槛）

| 指标 | 门槛 | 依据 |
|---|---|---|
| 结构合法率（schema + 锚点在转录内） | **100%** | 锚点是"真实卡壳点"的唯一判据（PRD §5.2.1） |
| 炼化块数在 1–5 | ≥95% | 太少=没炼出东西，太多=灌水 |
| 归一化后块重复率 | ≤5% | 重复块稀释资产（M5） |
| 闪测判定准确率 | **≥95%** | M1 的上线门槛；判定是唯一真值来源 |
| 命中检测：误报率 | **≤5%** | PRD §5.2.3 明确"宁可漏报不可错报" |
| 命中检测：漏报率 | ≤30% | 允许保守，但不能形同虚设 |
| 炼化质量：忠实度 <4 的比例 | ≤5% | 改写不能改变原意 |
| 炼化质量：三档均分 | ≥4.0 | 地道度/可迁移性 |
| 评价真实性均分 | ≥3.8 | 不编造问题 |
| 话题卡落地率（有块清单 + 来源） | 100% | H2 硬约束 |
| 话题泛化率（LLM 判"放之四海皆可"） | ≤5% | H2 禁止泛话题 |

**总门禁**：结构合法率 =100% 且 判定准确率 ≥95% 且 各质量均分达标 → 通过；否则**阻塞发布**，并在报告中列出失败样本。

---

## 五、怎么读报告

1. **先看总门禁**：不通过就不必细读分数；
2. **再看规则层失败**：这是硬 bug（例如锚点不在转录里 → 炼化的输入或校验有问题）；
3. **再看质量分布**：均分达标但长尾很差的，说明 prompt 在特定场景（常见于 `interview` 与 `casual`）失效；
4. **最后看抽检**：人工确认裁判可信度。

## 六、运行有效性（血泪教训）

第一次改进话题阶段后重跑，报告给出**全指标 0.000**——因为火山账号欠费，`refine` 阶段对每条样本都返回 `403 AccountOverdueError`。零分报告读起来像"产品质量灾难"，实际是"这次运行根本没跑起来"。

因此 harness 现在区分两件事：

- **运行无效**：失败样本占比 > 20% → 报告标注 `valid: false` + 原因 + 前三条原始错误，**不做门禁判定**，退出码非零；
- **运行有效但质量不达标**：正常门禁流程。

> 结论写进了工具本身：**没有跑起来的运行，不能产出质量结论。**

## 七、首轮实测发现与修复（Flow Eval 的第一份产出）

首轮 100 条（有效运行，499 次调用）：

| 类别 | 结果 |
|---|---|
| 结构层 | schema 100%、锚点在转录内 100%、标签合法 100%、无重复块 100%、救援锚点被采用 100% |
| 炼化质量 | 忠实度 4.63 / 地道度 4.63 / 可迁移性 4.60（1–5），低忠实度 2% |
| 评价真实性 | 3.84 |
| 命中检测 | 误报率 **0%**、自表达命中 100%、同义改写召回 57%（刻意保守，仅记录） |
| 判定 | 准确率 0.792 ❌、生产预算超时率 0.969 ❌ |
| 话题卡 | 带块清单/来源 100%；泛话题率待重测（旧版测量不具代表性） |

### 7.1 F1：判定超时被当成"答错"（已修）

- 生产判定预算 `1.5s`，实测 **16/16 次超时**；真实耗时 **1.56–4.8s，中位 1.96s**；
- `LLMJudge` 超时返回 `{Pass:false, Reason:"judge_timeout"}` 且 err 为 nil → 服务层按失败处理 → **streak 清零、状态回退、next_due +1h**。答对被判错。

修法两条：
1. **超时 ≠ 失败**：`JudgeResult.Judged` / `JudgeResponse.Judged` + `Retryable`；未判定的尝试**不动调度**、仍入账（`drill_records.judged = 0`，migration 0023）并计入当日新块释放；申诉对未判定记录直接说明"无可回滚"。
2. **预算改为实测驱动**：`JudgeTimeout` 1.5s → **6s**（覆盖实测最大值并留余量），可用 `DRILL_JUDGE_TIMEOUT` 覆盖；新增 `drill_unjudged_total` 指标作为预算健康信号。

### 7.2 F2：判定过严（已修）

200 个金标案例中 40 个判错，**全部是 `expect=pass got=fail`**，理由清一色"omits the time adverbial / key details"——说了要点但没逐项说全被判失败，与 PRD §7.5"语义等价而非逐字一致"冲突。

修法：`JudgePrompt` 写死 rubric——**保留核心命题即 pass**，即使更短、省略可选细节、换用不同但地道的说法；只有核心含义缺失/改变或无法理解才 fail。新增 `omitted_details` 字段回流"要点对但漏细节"的比例（它同时是"块是否太长"的信号）。

**效果已验证**（账号恢复后重测，金标集未变）：

| 指标 | 修复前 | 修复后 | 门槛 |
|---|---|---|---|
| 判定准确率 | 0.792 ❌ | **0.974** ✅ | ≥0.95 |
| 生产预算超时率 | 0.969 ❌ | **0.005** ✅ | ≤0.10 |

### 7.4 F3：话题卡泛话题率 55.6%（真实缺陷，未修）

给裁判看了用户的 85 块语料后（此前不给语料，它只能一律判泛），9 张卡中 5 张判为泛话题，三种形态：

1. **同类型卡片跨天重复**：三次生成都产出 "Daily Standup Progress Update"，且同日两张仅差一个词——生成器看不到往期卡片；
2. **面试题脱离语料**："Rate-limiter content is generic"——用户语料里是自我介绍类表达，卡片却出系统设计题；
3. **standup 模板化**："Mostly generic standup template"。

**根因**：H2 的服务端校验只到**标签层**（seed_tags 能命中用户的块即可），而卡片**正文**是否真的由这些块派生，没有校验。生成器 prompt 要求"贴用户工作"，但可验证的只有标签。

**建议**：① prompt 要求每张卡引用至少一句用户原话；② 服务端增加正文级校验（卡片的实质词须与所附块有交集，否则丢弃——与 H2"禁止泛话题"同一条纪律）；③ 传入往期卡片，避免跨天重复。

### 7.5 F4：六个端点只用了其中一个（成本核对时发现）

对账时发现 `drill.judge` 的记账行 `model` 列写的是 **pro**，而 DRILL_JUDGE 端点背后是 turbo。查代码：`orchestrator.NewArkClient` 把客户端绑定在 `cfg.ArkReviewRefineEP` 上，**所有操作共用这一个端点**。控制台里配的 `DRILL_JUDGE` / `TOPIC_CARD` / `HIT_MATCH` / `DAILY_READ` / `TEXT_DEGRADE` 五个端点从未被调用。

- 影响：按任务分模型的意图（快任务用 turbo）实际未生效；判定跑在较慢的 pro 上（实测中位 1.96s 就是 pro 的延迟）；
- 账本的 `model` 列**记的是事实**（确实调了 pro）——这正是记账该有的样子：配置与行为不一致时，账本会说话；
- 这也是 F1 的一条现成解法：把判定指到 turbo 端点即可，无需改 prompt。

### 7.6 记账核对（ai_cost_logs）

用 3 条样本 + 一个**演示费率**文件（`input=1.0 / output=2.0` CNY/百万，为便于手算）对真库核对：

| task_type | 行数 | tokens_in | tokens_out | 微元（账本） | 手算应得 |
|---|---|---|---|---|---|
| drill.judge | 12 | 4874 | 645 | 6164 | 6164 ✓ |
| eval.moat.rubric | 3 | 2812 | 188 | 3188 | 3188 ✓ |
| reviewgen.generate | 3 | 2950 | 1181 | 5312 | 5312 ✓ |

- **行数 = 调用数**：判定 12 行 = 2 个案例 × 2 个预算轮 × 3 条样本 ✓；
- **微元 = tokens_in×1 + tokens_out×2**（每百万），逐行与手算一致（如 404+2×54 = 512）✓；
- **两次判定轮 token 完全相同**（404/54 出现两次），证明两轮只差预算、不差输入 ✓；
- **不配费率时** cost = 0 且模型计入 `UnpricedModels`（前几轮即如此）——缺费率不会被编造的数字掩盖。

顺带修了定价文件的一个易用性缺口：支持 `_` 开头的注释键（该文件由运维手改，JSON 没地方写注释），其余仍然严格解析。

### 7.7 F3 / M5 / F4 的修复与复测（同日）

| 项 | 修法 | 复测 |
|---|---|---|
| **F4 端点路由** | `orchestrator` 按 operation 路由到各自端点（judge→turbo、topic→topic 端点…），未配置路由回落 review；启动日志打印路由表 | 判定与话题改走 turbo，成本与延迟下降 |
| **F4 附带：记账重复** | review 生成此前会写**两行**（orchestrator 一行 + session 自建一行），且 session 那行与 B18 逐句评估共用 `review.eval` 无法区分。现由 orchestrator 统一记一行并带用户归属（`CompletionRequest.UserID`） | 一次调用一行、可归因 |
| **F3 话题落地** | H2 从**标签层**升级到**正文层**：卡片必须逐字引用用户语料中 ≥4 个连续词，否则服务端丢弃；prompt 明写该规则；跨天重复（prompt 传入往期标题 + 服务端按归一化标题去重） | 9 张卡全部引用语料；跨天重复被丢弃（一轮实测 9→6） |
| **M5 跨会话去重** | 入库按归一化表达去重：已有同句 → 不新建，返回既有块 + `merged_count` | 跨会话重复率 0.150 被量化，新建侧不再累积 |

**话题质量指标的测量敏感性（重要）**：同一批卡片在四种测量设计下得到 0.556 / 0.444 / 0.000 / 0.000（grounded 3.44→3.11→5.00）。前两个数测的是**裁判看不到的语料**（只给抽样），第三个测的是**服务端已保证的事实**（只给卡片自称的块），现在的设计才问对了问题：**给全量语料 + 明确要求"判断话题本身，引文不构成证据"**。当前 9 张卡逐张人工核对与裁判一致（都引用了真实块、主题与用户场景匹配），但**指标本身仍不稳健**——这正是 §三 L3 人工抽检存在的理由。

## 八、把它当门禁用（改 prompt / 换模型前的例行步骤）

```bash
./scripts/eval-gate.sh                    # 全量跑，与基线对比，退化即非零退出
./scripts/eval-gate.sh --reuse-run <上次全量目录>   # 只重跑话题阶段（约 15 次调用）
./scripts/eval-gate.sh --write-baseline   # 有意变更后重录基线
```

**纪律**：任何 prompt、模型、调度参数的改动，合并前先跑一次；基线只在**有解释的有意变更**后重录。

**基线的容忍度**（`eval/moat/baseline.json`）：比率类 0.02，1–5 均分类 0.2。这些数字本身会抖——模型每次重放同一 prompt 都有差异——门禁若在噪声上触发，人就会开始忽略它，那比没有门禁更糟。

**哪些指标进不了门禁**（只记录、不判定，理由写在同一份 JSON 里）：

| 指标 | 为何不设门禁 |
|---|---|
| `hit_paraphrase_recall` | 检测器**刻意**用召回换精确（PRD §5.2.3），下降不是退化 |
| `topic_generic_rate` / `topic_grounded_mean` | 裁判口径在四种测量设计间给出 0.556/0.444/0.000/0.333（§7.7）；**不稳定的数字不能当门禁**。结构类话题指标（产出数、带块清单、带来源）是确定性的，仍然门禁 |
