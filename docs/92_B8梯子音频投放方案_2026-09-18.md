# B8 梯子音频投放方案（P1-3）

**日期**：2026-09-18
**状态**：**§5.1 / §5.2 后端半边已实施**（见 §9）；§5.3 待 iOS
**对应**：meta `77_` **P1-3**（PRD §5.4.3 约束 2、§5.5 第 4 行）· `78_` §2.2 的 `audio_url`

---

## 1. 一句话方案

**梯子的音频不新增投递通道，走 iOS 已经在用的那条**：网关把合成后的 PCM 按
`ai.tts.start` → 二进制帧 → `ai.tts.end` 推给客户端，`ai.rescue.ladder` 帧继续只带文本。
`audio_url` 保持为空，不再需要。

理由：iOS 的 `TTSFrameDispatcher` 已经把这条路实现完了——包括分片、序号门控、
打断。新增一条音频通道意味着客户端再写一遍这些，而梯子音频**没有**非走新通道不可的理由。

---

## 2. 关键实测：合成是通的，之前不通是配置错了

原本判断（`77_` P2-4、`54_`）是"prod SKU 403，凭据不到"。实测下来**不是**：账号有
`seed-tts-2.0` 授权，报错是因为**说话人与资源代际不匹配**。

| 资源 ID | 说话人 | 结果 |
|---|---|---|
| `seed-tts-2.0` | `zh_female_vv_jupiter_bigtts`（**代码里的默认**） | `55000000` resource ID is mismatched with speaker |
| `seed-tts-2.0` | `zh_female_cancan_mars_bigtts` | 同上 |
| `seed-tts-2.0` | `zh_female_vv_uranus_bigtts` | **`code:0`，返回音频** |
| `volc.service_type.10029` / `volc.tts.default` | 任意 | `45000030` requested resource not granted |

`mismatched` 与 `not granted` 是两个不同的错：**资源在手，说话人不属于这个资源**。
`seed-tts-2.0` 只认 2.0 代际（`*_uranus_bigtts`）的说话人，代码配置的是 1.0 代的
`jupiter`。换成 `zh_female_vv_uranus_bigtts` 后，用**现有的 dev 凭据**立刻出声：

```
text="先说结论，再说原因"    pcm=70464 B  dur=2.20s  首音 477ms  共 644ms
text="I think the main risk is the migration window."
                            pcm=96330 B  dur=3.01s  首音 292ms  共 559ms
```

量级上完全够用：**一级梯子 3 秒的预算里，合成只花 0.6 秒**。

### 顺带发现：duplex 兜底 TTS 是坏的

`VolcDuplexFallbackProvider`（`volc_duplex_fallback.go`）向 vendor 发
`response.create`，服务器回 `unknown event name:response.create`；换 `chat.tts`
也是 `unknown event name`。也就是说这条兜底路径在当前协议版本上**从来不可能成功**
——只是没有调用方，所以没人发现。它还有第二个缺口：`ensureConnLocked` 开的会话
从不声明 `input_audio_mute.commit`，而 vendor 文档明确说没有上行音频的会话会被判定
为掉线。方案里一并处理（§6）。

---

## 3. 为什么是这条路

约束来自客户端代码，不是偏好：

| 约束 | 出处 | 含义 |
|---|---|---|
| 二进制音频帧只有在 `ai.tts.start` 之后才播 | `TTSDecoder.swift` `TTSFrameDispatcher.handle(audio:)`：`.idle` 直接返回 false | 裸推二进制帧会被客户端**丢掉** |
| 播放缓冲固定 16 kHz 单声道 PCM16 | `AppDependencies.swift` `RawPCM16FrameDecoder` / `LiveAudioEngine` | 只要 PCM16 就能播；`VolcengineOpusFrameDecoder` 是**故意留的空实现** |
| 帧是 100ms 一片 | `provider_volc_duplex.go` `audioFrameBytes = 3200` | 2.2 秒的梯子 ≈ 22 帧 |
| 帧头是 4 字节大端序号 | `encodeAudioFrame` | 复用现成编码即可 |
| 打断后按序号水位丢帧 | `AudioFrameDropGate.swift` | **梯子帧的序号必须排在被打断的那一轮之后** |

最后一条是这套方案唯一有点技术含量的地方，也是选"复用现有通道"而不是"新开一条"的
第二个理由：序号水位、打断、丢帧这些语义，现有通道已经有了，新开一条要全部重造。

---

## 4. 不做什么

| 方案 | 为什么否 |
|---|---|
| **对象存储 + `audio_url`**（`78_` §2.2 原设想） | 仓库里没有对象存储；app-server 也不对 iOS 暴露（要新增公开端点、鉴权、TTL、清理）。为一个 2 秒的短句引入一套存储，是拿一整天换一句"音量小一点" |
| **`ai.rescue.ladder` 内联 base64** | 2.2 秒 PCM 约 70 KB，base64 后 94 KB，塞进控制帧。能跑，但把"控制面"和"媒体面"混在一起——而媒体面本来就有现成通道 |
| **直接改用 Opus** | 体积小一半，但 `VolcengineOpusFrameDecoder` 在 iOS 侧是空实现，等于要客户端补一个解码器。**收益是省带宽，成本是跨越一个仓库的改动加一次真机联调**，不值得放在第一步 |
| **网关自己合成** | 又回到"网关持有 provider 凭据、模型开销不进账本"的旧形状——这正是 `4f113e6` 刚拆掉的那条路。合成必须留在 app-server |

## 5. 改动清单

### 5.1 app-server

| # | 改动 | 备注 |
|---|---|---|
| A1 | `defaultVolcTTSSpeaker` 改为 2.0 代际说话人（`zh_female_vv_uranus_bigtts`），或把说话人与 `ResourceID` 一起变成成对校验 | 目前这个常量是**保证 403 的**写法。若配置里给了 1.0 说话人 + `seed-tts-2.0`，应在启动时就报错，而不是等第一次合成了才知道 |
| A2 | 默认 `Format` 与 `SampleRate` 改为 `pcm` / `16000` | 客户端就播这个格式，省掉一次重采样 |
| A3 | `/internal/v1/tts/synthesize` 返回 PCM 分片（已有 `audio_base64` 字段，语义不变） | 该端点目前**无任何调用方**（`54_` §2），本方案是它的第一个消费者 |
| A4 | 记账：合成前记 `chars`（P1-5 的 `UsageRecorder` 已就绪） | 梯子用的是用户自己的额度，账本要看得见 |
| A5 | duplex 兜底路径：删掉，或修好（正确的事件名 + `CommitInputMute`） | 现在它是坏的（§2）。它存在的前提是"主路径失败时还能出声"，一个从来不能成功的兜底比没有兜底更危险——它会让降级看起来像已覆盖 |

### 5.2 voice-gateway

| # | 改动 | 备注 |
|---|---|---|
| B1 | `RescueSynthesizer` 接口改形状：不再返回 URL，返回**音频字节 + 格式** | 现签名 `Synthesize(ctx, text, turnID) (audioURL, durationMS, err)` 是为 `audio_url` 设计的；接口从没有实现，改它不欠债 |
| B2 | 新增实现：调 `/internal/v1/tts/synthesize`，base64 解码得 PCM | 参照 `HTTPRescueGenerator` 的形状（同样的 base URL、内部 token、超时纪律） |
| B3 | 切帧：按 `audioFrameBytes`(3200) 切片，序号接在**本会话已有的音频序号**之后 | `SequencedVoiceProviderSession.NextAudioSequence()` 已有，沿用它——这是让 §3 最后一条约束自动成立的关键 |
| B4 | 发送序：`ai.tts.start`(带 turn_id、voice、16000、pcm) → N 个二进制帧 → `ai.tts.end`(status ok) | 与 provider 的音频走同一个写路径 |
| B5 | 用户开口即打断：发 `ai.tts.end`(status interrupted) 并停止后续帧 | 梯子的目的就是让他开口，开口了就该停 |
| B6 | 超时与降级：合成超过预算（建议 1.5s，与生成预算合计仍在一级间隔内）→ 只发文本梯子 | 现有降级语义不变：`audio_url` 本就允许为空 |
| B7 | `RescueVoiceSpeed` / `RescueVoiceVolume`：落成合成参数或删掉 | 现在是没有消费者的常量。PCM 合成本身不带音量；音量应由客户端播梯子时降，这需要对 iOS 提要求（§5.3） |

### 5.3 iOS（需要对方 owner）

| # | 要求 | 依据 |
|---|---|---|
| C1 | 处理 `ai.rescue.ladder`：把 `text` 显示在对话气泡里（淡色背景） | `78_` §2.2，目前**一行都没实现**（全仓 grep `rescue` 为零） |
| C2 | 接受梯子音频走 `ai.tts.*`：它已经支持，无需新代码——但要确认"梯子的 turn_id 不与对话轮次混同" | `TTSFrameDispatcher` 按 turn_id 记账 |
| C3 | 梯子语音音量低于对话（如 0.85）：由客户端在播放时施加 | `RescueVoiceVolume` 的原始意图 |
| C4 | 用户开始说话时停止梯子播放 | 与 B5 配对 |

## 6. 降级与失败

| 失败点 | 行为 |
|---|---|
| 合成失败 / 超时 / 供应商报错 | 发纯文本梯子（`audio_url` 空），**照发不误**。现有行为，不变 |
| 无人调用 TTS（`VOLC_SPEECH_API_KEY` 为空） | app-server 返回 503，网关降级为文本梯子。现有行为 |
| TTS 授权再次失效（如 prod SKU） | 同上——梯子功能**不依赖音频**，音频是增强 |
| 会话被打断后又有新的梯子 | 序号续接保证新帧序号大于水位，不会被丢帧门丢掉 |

**一条设计纪律**：音频是增强，文本是主体。任何一级梯子在合成失败时都必须照常发出，
且**不得**因为等音频而推迟文本——文本已经在手里了。

## 7. 验证

| 层级 | 怎么验 |
|---|---|
| 单元（app-server） | 说话人与资源代际不匹配时给出可读错误；`Format=pcm` 时返回偶数长度的 s16le 字节 |
| 单元（网关） | 帧序与序号：一级梯子产出 start + N 帧 + end；打断时 end(status=interrupted) 且后续帧停止；合成失败时只发文本 |
| 契约（跨包） | 起 app-server 真 handler + 假 TTS provider，网关客户端走真 HTTP——沿用 `hit_writeback_test.go` / `rescue_client_test.go` 的做法（手写响应体是 B8 那次 bug 的成因） |
| 真机（**必须**） | ①沉默 3 秒后**听到**梯子（不是看到）；②用户开口即停；③文本气泡同时出现；④TTS 关掉时文本照常出现且不报错 |

真机这一条是 `77_` P1-3 验收标准 1、2 的唯一判据——单元测试只能证明帧发对了，
证明不了"耳朵里听到的是梯子而不是 AI 在继续说"。

---

## 8. 现状判定与阻塞

**不是"等授权"，是"改配置 + 写投递"**：合成通路实测可用（§2），投递方案如 §5。

真正需要决定的是 **A5**（duplex 兜底删还是修）和 **B7/C3**（音量在哪一侧施加）。
两项都可以先按"删掉兜底 + 客户端施加音量"实施，因为它们都不影响主路径。

需要协调的是 **iOS**：`ai.rescue.ladder` 至今没有任何客户端处理代码，而 PRD 约束 2
（"说出来，不弹卡片、不切页面"）是客户端行为。**这一条是当前最大的不确定性**，
建议在动工前先与 iOS owner 确认 §5.3 的四条。

### 9.2 落地清单

- **app-server**：默认 speaker 改 2.0 代际、`format=pcm`/`sample_rate=16000`、`ErrSpeakerResourceMismatch` 前置校验（把 vendor 的 `55000000` 变成一句说清修法的错误）、`tts.VoiceRescueLadder`（0.9 速）+ `rescue_ladder` 别名
- **gateway**：`RescueSynthesizer` 返回音频字节；`HTTPRescueSynthesizer` 走 `/internal/v1/tts/synthesize`；`RescueAudioOutbound` 切帧并复用 provider 的音频序号空间；`sendRescueAudio` 匀速发送 + 可中断；`WireRescue` 接上合成器
- **常量**：`RescueVoiceSpeed` 落在 app-server 的音色条目（合成参数），`RescueVoiceVolume` 留给客户端播放时施加 —— 见代码注释里的分工说明

### 9.3 实测数据（合成，非真机）

配置路径（目录查表、无显式 speaker）下，12 词英文 rung：

```
speaker=zh_female_vv_uranus_bigtts speed=0.90
chunks=10  pcm=120630 B  dur=3.77s  首音 565ms  全部 951ms
```

`DefaultRescueSynthTimeout = 1s` 即据此定：整级（文本生成 ~2s + 合成 ~1s）要落在
一级的 3s 预算内，超出只丢声音、不丢文本。
