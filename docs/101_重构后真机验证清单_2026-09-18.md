## 1. 【M3，最高风险】AI 还出声吗

**改了什么**：AI 的音频帧现在由与梯子共用的 `audioFramer` 切出来（以前是 provider 自己切的）。线上格式与序号规则都没变——但这是主路径。

| | |
|---|---|
| **怎么做** | 正常说一句话，松手，等 AI 回答 |
| **预期** | **听到** AI 说话，内容与以前一致；说完正常进入评价等待 |
| **日志** | `ai.tts.end` 与 `ai.turn.end` 都到；`outcome=ok` |
| **失败的样子** | ① 完全没声音 → 切帧或序号出了问题；② 声音断续/变速 → 采样率被搞错了 |
| **特别要查** | `grep "ai.tts.start" /tmp/fw.log` —— 每一轮**恰好一条**，且落在该轮**第一条**二进制音频帧之前。**没有它 = 静音**：iOS 按轮次给二进制帧认领归属，无归属的帧一律丢弃（`TTSPlaybackCoordinator.onAudioFrame`，契约见 `docs/98_` §五）。被打断的那一轮**不发** start —— 没有音频要引出，而 barge-in 之后到达的 start 会把客户端已标记作废的轮次重新激活 |

## 2. 【M1】断线重连后音频还在

**改了什么**：音频序号从 provider 字段变成会话持有的 `SeqAllocator`。原始真机 bug 就是"重开后转写还在、声音没了"。

| | |
|---|---|
| **怎么做** | ① 正常聊 2–3 轮；② 让上游断一次——切走 Wi-Fi 3–5 秒再回来，或等一次空闲（volc-duplex 约 2 分钟空闲会掉线）；③ 继续说话 |
| **预期** | 重连后**仍然听得到** AI 说话，转写正常 |
| **日志** | `provider reopened after audio forward failure; retrying chunk` + `reopen budget refilled for the new turn` |
| **失败的样子** | 转写在、**没有声音**——正是这个 bug 的原症状。这时 M1 的修复没生效或序号仍被重置 |
| **怎么核对序号** | **后端日志不打帧序号**，所以只能从两头看：① 网关侧看有没有 `provider reopened … retrying chunk`（发生了重开）且其后仍有 `ai.tts.end`；② iOS 侧 `tts_first_audio` 事件带 `sequence` 字段，可用来确认重连后没有回落到小数字 |

## 3. 【M2/M4】梯子：文本、音频、打断

> **前置**：梯子的音频走 `ai.tts.*` 流（`docs/93_` §3）。那条绑在「只记录、不出声」的
> `MockTTSDecoder` 上的路已经拆掉了——生产 DI 现在解的是真解码器，所以**这一条连音频一起验**：
> 每级都应该真的被听到。听不到就是缺陷，不是"还没接线"。

| | |
|---|---|
| **怎么做** | AI 说完后**沉默**：3 秒（第 1 级）、6 秒（第 2 级）、9 秒（第 3 级） |
| **预期** | 每级都收到 `ai.rescue.ladder`；`level` 依次 1→2→3；文本 1/3 是英文、**2 是中文** |
| **日志** | `B8 rescue ladder emitted` 每级一行，带 `level` / `text_length` / `spoken` |
| **要确认的** | `spoken=true`（合成成功）。`spoken=false` 说明只有文本，去看有没有 `rescue TTS synthesis failed` |
| **打断** | 第 1 级正在"说"时立刻开口 → 后端应发 `ai.tts.end` 且 `completion_status=interrupted`；再沉默 3 秒应**重新从 level 1 开始**，不是接着 level 2 |
| **边界** | ① 三级用完后继续沉默 → **不再有任何帧**（等 20 秒确认）<br>② AI 那轮以 `timeout`/`error` 结束 → **不发梯子** |

## 4. 【M4】badge 与锚点落在正确的 turn 上

**改了什么**：turn 的名字由 `Turn` 统一解析（以前 badge 与救援锚点各算各的）。

| | |
|---|---|
| **怎么做** | 说出语料库里某个块的表达 |
| **预期** | `feedback.badge emitted`，其 `turn_id` 与 `ai.turn.end` 的 `turn_id` **一致**；语料库页该块「用上过」+1 |
| **怎么做（锚点）** | 说完后到回顾页看：锚点应是**你确实说过的那半句**，不是模板 |
| **新日志要留意** | `turn_transition_rejected` —— **干净的一轮应当是零条**（救援开、关两种配置都一样）。出现即说明客户端发了顺序意外的帧，看一眼 `event` 与 `state` 字段。**偶尔一条是信息，不是错误**；连续每轮都出现就是客户端的行为变了 |

## 5. 【M5】不该出现的 error 帧

**改了什么**：控制帧失败策略收敛成一张表，只有 `client.turn.abort` 静默。

| | |
|---|---|
| **怎么做** | 按住说话不松手约 60 秒（触发 abort），然后正常继续 |
| **预期** | 收到 `client.turn.abort` 出站；**没有** `error` 帧；会话**仍然活着**，可以再开口 |
| **为什么这条重要** | abort 的 error 帧会映射到 iOS `.failed` 并杀掉会话——这正是这个帧要避免的事 |
| **另外** | 打断（interrupt）时若 provider 转发失败，**应该**收到 `provider_interrupt_failed`。正常情况下不该看到 |
