# 109 — 开发启动脚本监管（实现说明）

> **任务**：修掉「`voice-gateway` 经常起不来」与「徽章语料还要单独跑一遍」
> **基线**：`4ccbf5a`
> **真源**：`fluentwork-meta/agents/shared/defect-fix-discipline.md`
> **范围**：`scripts/` 与本文。**没有改动任何 `.go` 文件。**

---

## 接缝

- **接缝**：层接缝（启动脚本 ↔ 被启动的进程树）。本次**新增**一个共享实现点
  `scripts/lib/dev-service.sh`，并把三份各写一遍的「起一个服务」收进去。
- **状态所有权**：
  - 「哪些服务是我起的、它们的 pid/端口/日志在哪」由 `DEV_SERVICES` **独占**。
    此前 `dev-up.sh` 与 `dev-local-start.sh` 各持 `SERVER_PID` / `GATEWAY_PID` 两个变量。
  - 「日志目录在哪」由 `DEV_LOG_DIR` **独占**。
  - 「端口上那个进程是不是本仓的服务」由 `dev_is_our_service` **独占**。
    回收端口这件事只有一个实现点（`dev_reclaim_ours`），启动前的预检与收尾的
    `dev-down.sh` 都走它 —— 否则两处对「谁的进程」的判断会各自漂移。
- **不变量**（四条，都必须永远成立）：
  1. **`$!` 必须是服务本体**，不是 `go run` 的包装进程。
  2. **停止必须收掉整个进程组**，不是只杀直接子进程。
  3. **端口被外来进程占着时，一个都不许动**（安全边界）。
  4. **「起没起来」这个问题，只能由本轮自己起的那个进程回答** ——
     不能让端口上的任何一个应答者替它回答。
- **证明**：`scripts/check-dev-service.sh`（33 条断言），已接进 `scripts/dev-check.sh`，
  所以**每次门禁都跑**。

## 根因

不是「脚本写得糙」。是**同一个问题在三个脚本里各写了一遍，于是同一个坑也有三份**；
而其中一份的判据在问一个「没有唯一所有者」的问题。

### 一、`go run ... &` 的 `$!` 是包装进程 —— Ctrl-C 之后服务本体泄漏

旧脚本的启动方式是 `go run ./cmd/x &` 然后记 `SERVER_PID=$!`。
`$!` 是 **`go run` 包装进程**，不是服务本体。实测：

```
=== 旧脚本的启动方式：go run ... & ，记下 $! ===
wrapper($!) = 22721
child        = 22736
端口 8199 占用者 = 22736

=== 模拟 Ctrl-C：kill 掉包装进程 ===
/tmp/fw-repro.sh: line 28: 22721 Terminated: 15   go run ./cmd/voice-gateway > /tmp/fw-repro-gw.log 2>&1
wrapper alive? NO
child   alive? YES
端口 8199 占用者 = 22736   ← 残留仍占着端口
```

**杀掉的 22721 是包装进程；真正在监听 8199 的 22736 活着。** 于是 Ctrl-C 之后，
一个上一轮的网关继续占着端口 —— 而这就是「下一次启动，`voice-gateway` 起不来」的来源。

旧脚本的 `cleanup`（`HEAD:202-208`）正是这样：

```bash
if [[ -n "${GATEWAY_PID}" ]] && kill -0 "$GATEWAY_PID" >/dev/null 2>&1; then
  kill "$GATEWAY_PID" >/dev/null 2>&1 || true
  wait "$GATEWAY_PID" >/dev/null 2>&1 || true
fi
```

**它只 kill 包装进程，本体必然泄漏。** 实测（旧脚本跑完被我 SIGTERM 之后）：

```
$ ps -o command= -p 22779 22786
22779 已退出                # go run 包装进程被 trap 杀了
22786 泄漏中: /Users/tango/Library/Caches/go-build/a0/a00d…-d/app-server
```

附带一个症状：泄漏的本体**继承了脚本的 stdout**，所以 `bash /tmp/fw-old-dev-up.sh 2>&1 | tail -25`
这条管道在 3 分 58 秒里**没有返回** —— `tail` 等不到 EOF。这就是「Ctrl-C 之后终端不回来」。

### 二、残留占着端口时，旧脚本报的是**「已就绪」**，不是「起不来」

这一条比第一条更坏，也是本次最有价值的发现。把上面那个残留留在 `:8199` 上，
然后跑 `HEAD` 版的 `dev-up.sh`（`PORT=8198 GATEWAY_PORT=8199`），逐字输出：

```
Starting voice-gateway on ws://127.0.0.1:8199/v1/voice
Healthy. Smoke-testing guest auth...
{"user_id":"47c8af39-0926-4bd3-8186-a06bb18035e4","is_guest":true,"status":"active", …}
📡 WSS URL for iOS: ws://127.0.0.1:8199/v1/voice
   Set LOCAL_HOST=127.0.0.1 in Xcode scheme for physical device testing.

app-server (pid 22779) and voice-gateway (pid 22788) are running. Ctrl-C to stop.
{"level":"INFO","msg":"voice-gateway listening","addr":"0.0.0.0:8199", …}
{"level":"ERROR","msg":"voice-gateway exited","err":"listen tcp 0.0.0.0:8199: bind: address already in use"}
exit status 1
```

**脚本先说了「Healthy」、说了「are running」、说了「Ctrl-C to stop」，然后网关才死。**

机制在 `wait_for_url`（`HEAD:115-132`）：

```bash
for i in $(seq 1 60); do
  if ! kill -0 "$pid" >/dev/null 2>&1; then      # ← 问的是「我的进程」
    echo "${name} exited before becoming healthy" >&2
    return 1
  fi
  if curl -sf "$url" >/dev/null 2>&1; then       # ← 问的是「这个端口」
    return 0
  fi
  sleep 0.5
done
```

**两半判据问的是两个不同的主体。** `kill -0` 问「我起的那个进程还在吗」，
`curl` 问「这个端口上有东西应答吗」。当残留还在应答时：

- `kill -0 $GATEWAY_PID` 为真 —— 因为 `go run` **还在编译**，包装进程活着；
- `curl -sf :8199/healthz` 为真 —— 因为**残留**在应答。

两者同时为真，于是循环判定「我的网关起来了」。而本轮真正的网关随后才 bind 失败退出。

**这是一个不变量有两个归属地的形状**（与 `108_` 的 `costLogs` 同形）：
「已就绪」这件事，被 `curl` 那一半交给了端口上的任何人。
`curl` 无法区分「我起的进程绑上了端口」与「端口上本来就有别人」——
而这两种情况**要求完全相反的动作**（后者要回收，前者要放行）。

### 三、端口冲突 / 编译 / 就绪，三段被压进同一个 30s 窗口

同一个 `wait_for_url`：`seq 1 60` × `sleep 0.5` = **固定 30 秒**，且它同时承担三件事：

| 实际情况 | 旧脚本的说法 |
|---|---|
| 端口被别人占着 | 30s 后「did not become healthy」，或进程退出后的「exited before becoming healthy」 |
| 冷编译还没完（`go run` 首次编译可超过 30s） | 同上 —— **和上一条一模一样** |
| 起来了但 `/healthz` 慢 | 同上 |

**三种不同的病因给出同一句话**，而它们要的动作完全不同。用户拿到「voice-gateway exited
before becoming healthy」，第一反应是去查网关，而真正的原因在端口上、或者根本还没编译完。

### 四、徽章语料（`badge-in`）只有 `dev-up.sh` 播

网关只为「能在语料里找到的短语」发 `feedback.badge`，而语料由 app-server 提供
（`cmd/voice-gateway/main.go` 里 `NewHTTPCorpusSource(cfg.AppServerInternalURL, …)`）。
`dev-echo` 用的是本地语料，没有这个依赖 —— 所以「开发时打不出徽章」只在真链路上出现。

播种这一步以前**只在 `dev-up.sh` 里有**。而文档里推荐的入口是
`dev-stack.zsh` → `dev-local-start.sh` —— 走这条路的人永远打不出徽章，
得自己再想起来跑一遍 `corpus-seed`。这就是「badge-in 还需要单独运行脚本」。

### 五、推荐的入口不开 review worker

`cmd/app-server/main.go:274-280`：

```go
runWorker := strings.TrimSpace(os.Getenv("APP_RUN_REVIEW_WORKER"))
if runWorker == "" {
	if cfg.MySQLDSN == "" {
		runWorker = "1"
	} else {
		runWorker = "0"
	}
}
```

**只有 `MYSQL_DSN` 为空（内存存储）时才默认开。** 而 `dev-local-start.sh` 是
**恒定的 MySQL 栈**（它自己刚起了 MySQL 与 Redis），`MYSQL_DSN` 一定非空。

同时 `grep -rn "cmd/worker" scripts/` 的结果是：**没有任何脚本启动 `cmd/worker`**
（只有两处注释，和 `docs/01_本地启动.md:234` 叫用户手敲 `go run ./cmd/worker`）。

所以：**`dev-up.sh --local-mysql` 与 `dev-local-start.sh` 这两条路上，
会话结束后 review 永远不会完成，且没有任何报错。**
`dev-up.sh` 早先补过这一行，`dev-local-start.sh` 没有 —— 于是**被推荐的那条路
恰恰是静默不产 review 的那条**。

## 方案

**把三份「起一个服务」收成一个实现点**，而不是把三份的差异调平。
调平只解决今天这三份；收成一个点让第四份不可能出现。

| 文件 | 动作 |
|---|---|
| `scripts/lib/dev-service.sh` | **新增**（约 470 行）。唯一的构建/启动/停止/监管实现。bash 3.2 语法（macOS 自带 `/bin/bash` 是 3.2.57，三个调用方的 shebang 都是 `#!/usr/bin/env bash`，所以不用 `declare -A` / `mapfile` / `${var,,}`） |
| `scripts/dev-up.sh` | 重写为七段：① 端口预检 ② 全部构建 ③ 启动 ④ 等就绪 ⑤ 游客鉴权冒烟 ⑥ 播语料 ⑦ 汇总 + 监管。新增 `--no-seed` / `--no-kill-stale` / `--gateway-port` |
| `scripts/dev-local-start.sh` | 同样重构；补 `export APP_RUN_REVIEW_WORKER=1`；补第 ⑥ 段（播语料） |
| `scripts/dev-local.sh` | 删掉写死的 `HOST=192.168.2.104`，改成 `detect_lan_ip()`（默认路由网卡，再退 en0/en1/en2）；探测不到就报错，不猜 |
| `scripts/dev-down.sh` | 收尾时按 `dev_is_our_service` 回收本仓残留；并列出**它不停**的东西 |
| `scripts/dev-status.sh` | **新增**。一屏看全貌：依赖 / 服务 / 日志关键行 / 语料提醒。任一服务没在跑则 exit 1 |
| `scripts/check-dev-service.sh` | **新增**。33 条断言 |
| `scripts/dev-check.sh` | 在 `go build` 与缺陷纪律之间插入新断言 |

### 关键实现选择

**1. 先构建成二进制，再直接运行二进制**（不是 `go run`）。
`dev_build` 把产物放到 `bin/<name>`，`dev_start_service` 直接 exec 它。
于是 `$!` 就是服务本体，第 1 条不变量自动成立。
构建与运行**分开计时**，于是「还在编译」再也不会被报成「服务起不来」。

**2. 用独立进程组启动，收尾时收整组。**

```bash
set -m
"$@" >>"$log" 2>&1 &
local pid=$!
set +m
disown "$pid" 2>/dev/null || true
```

`set -m` 让后台作业拿到自己的 PGID（== 它的 PID），于是 `kill -TERM -$pid`
一次收掉本体与它派生的子进程。`set +m` 立刻恢复，避免影响调用方的作业控制；
`disown` 只是把它从 bash 的作业表里摘掉，免得停止时 bash 再打一行「Terminated」通知 ——
进程本身照旧由我们显式回收。

**3. 三段分开报告**（这是第 3 条根因的修法）：

| 阶段 | 失败时的说法 |
|---|---|
| 构建 | 「构建失败（Ns）—— 这不是「服务起不来」，是编译不过」+ 编译错误 |
| 绑定端口 | 「端口 N 始终没有被绑定」 |
| `/healthz` | 「端口已绑定，但 http://…/healthz 不应答」 |

**4. 「是不是我们的进程」这个判据要认全两种落点。**
见下面「顺带修掉」的第一条 —— 这条是**验证阶段实测暴露的我自己代码里的缺陷**。

## 顺带修掉的三个形状（验证阶段暴露的）

这三条都是**我自己这次写的新代码里的缺陷**，靠端到端验证才暴露 ——
所以按 `AGENTS.md` §7 的纪律，每一条都补了断言，避免再长回去。

### 1. `dev_is_our_service` 的判据只在一半情况下取真值

原本只认 `~/Library/Caches/go-build/<xx>/<hash>-d/<name>`。实测发现
**`go run` 的产物有两种落点，同一台机器上同时存在**：

```
$ ps -o command= -p 22736 22786
22736 /var/folders/x2/kff15jq9773986hg_7v7h9hr0000gn/T/go-build33506635/b001/exe/voice-gateway
22786 /Users/tango/Library/Caches/go-build/a0/a00d5306498306037e542eb326cf16f364f7e15fed08d350968cc09075e4ebdf-d/app-server
```

缓存命中时直接 exec 缓存里的可执行文件；现编现链接时落在 `$TMPDIR/go-buildNNNN/b001/exe/`。

**只认前者，等于「回收老残留」在一半情况下静默失效** —— 而失效的样子正是
「端口被占着，脚本却说不属于本仓，于是不动它」，也就是这次要修的病本身。
判据里的这条缺口会伪装成「实现是对的，只是这条路上不生效」。

### 2. 收尾会谎报「已停止」

端口预检失败就 `exit 1` 时，EXIT trap 照样打：

```
① 端口预检
🛑 正在停止服务...
✅ 已停止。
退出码=1
```

**那一刻一个服务都没起过。** 这三个字会让人以为上一轮的服务被收了，
于是不再去看端口 —— 而端口上恰恰还站着东西。修法是把收尾收进库
（`dev_cleanup`），并在注册表为空时什么都不说。

### 3. `dev-status.sh` 的两处：读错日志目录 + 拿不存在的 CLI 当判据

`DEV_LOG_DIR=/tmp/fw-val/logs ./scripts/dev-status.sh` 报「`.dev-logs/` 下没有日志」，
而日志就在 `/tmp/fw-val/logs` 里 —— 写死的路径盖过了唯一所有者。
症状是「日志不见了」，比服务起不来更难查。

另一处更隐蔽：依赖检查原本用 `mysqladmin ping` / `redis-cli ping`。
实测本机：

```
$ ls -l /opt/homebrew/bin/mysqladmin
ls: /opt/homebrew/bin/mysqladmin: No such file or directory
$ brew list --formula | grep -iE 'mysql|redis'
（无输出）
```

**两个 CLI 都不存在**，所以那两行判据对「装没装、跑没跑」永远只能给出 ❌ ——
**一个从不取真值的判据**，而且它给出的还是一个确定的、看起来很有信息量的答案。
修法：改用 `lsof` 看端口有没有人听（本文件其它部分本来就依赖它），
并把「未安装」「装了没起」「检测不可用」分成三句 —— 因为它们要的动作各不相同，
合成一句 ❌ 会把人送去执行一条注定失败的 `brew services start mysql`。
