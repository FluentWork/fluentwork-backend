# 音频首响的服务端标记：为什么不加帧

**日期**：2026-09-11
**状态**：实现与测试已齐。
**对应**：meta `77_` **P1-21**

## 1. 为什么

`server_ts_ms` **只挂在 `ai.text.delta` 上**（P1-5 加的）。于是：

| | 总延迟 | 能拆成上行/服务端/下行吗 |
|---|---|---|
| **文本**首帧 | 可测 | **能** —— 有服务端时间戳 |
| **音频**首帧 | 可测 | **不能** —— 没有服务端时间戳可减 |

而 `docs/51` §7 说清楚了：**首响的总数本来就不需要 offset**（两个端点都在客户端钟上），
offset 买到的**只是那个拆分**。所以缺口很具体：**用户感知的那一路拆不开。**

## 2. 先撞上的约束：最自然的载体用不了

第一反应是把时间戳挂到 `ai.tts.start` 上 —— 它本来就是"二进制音频之前的控制帧"，形状完全对。

**但 `provider_volc_duplex.go` 明写了不发它，而且理由是硬的：**

> Sent as plain binary frames with **no** ai.tts.start on purpose.
> `TTSFrameDispatcher` only claims binary frames once it has seen an `ai.tts.start`,
> and the decoder bound into it (`MockTTSDecoder`) records without driving AVAudioEngine
> — its own doc says so. With no `ai.tts.start` the middleware falls back to
> `audioEngine.play(frame:)`, which is the path that actually makes sound today.

**发 `ai.tts.start` 会把音频从"真的出声"的那条路挪到"只记录不出声"的那条。**
这正是 B17「built, not turned on」的同一种地雷 —— 而且这一次踩下去用户是**听不到声音**。

## 3. 三个选项，选了最便宜的那个

| 选项 | 代价 |
|---|---|
| 新增一个控制帧带时间戳 | 跨服务协议变更（infra schema + 后端 + iOS 三方），且 iOS 不消费就变成**新的死路** |
| 把时间戳塞进二进制音频帧头 | 每帧都要多带 8 字节，而这个戳**一轮只需要一个**；且动的是"out of band"的二进制布局 |
| **服务端自己记一笔** | **线上零改动** |

选第三个。**网关本来就同时知道这一轮的两端**：

- `turnStarted`（`user.speech.end` 到达时置上）
- 第一帧音频发出的那一刻（`AssistantAudio` 的首次调用）

相减就是**网关自己那一段**。客户端的总数减去它，**剩下的就是网络的** —— 正是这个记录要换来的那个拆分。

## 4. 标记带什么

```
voice.duplex.first_audio  session_id=… turn_id=turn-1 server_ts_ms=… server_ms=…
```

- **`server_ms`** —— 网关自己那一段（本轮开始 → 第一帧音频发出）。不用 join 也能直接读。
- **`server_ts_ms`** —— **绝对**时间戳，让 join 不依赖两台机器的时钟一致：客户端用 ping 推出的
  offset 把它换算到自己的钟上，**和它处理 `ai.text.delta` 的方式完全一样**。

两个都给：前者给"一眼看"，后者给"跨日志对齐"。

## 5. 测试

`internal/voicegateway/provider_first_audio_mark_test.go`，三条：

| 测试 | 守什么 |
|---|---|
| `…MarksTheFirstAudioFrameOfATurn` | 第一帧音频**恰好**打一条；`server_ms` 反映真实间隔（120ms 前开始的轮 → ≥100）；带 `turn_id`（**没有它就 join 不上**） |
| `…MarksFirstAudioOncePerTurn` | 5 个音频块**只打一条** |
| `…DoesNotMarkOnAnEmptyAudioChunk` | 空块不配被当成"第一帧音频" |

第二条不是洁癖：音频是一**簇**到达的，每块打一条会把"用户什么时候开始听见"变成一个**速率**。

## 6. 影响面

| 维度 | 影响 |
|---|---|
| **协议 / schema** | **零改动**。不加帧、不动二进制布局、不动冻结的 v1 |
| **线上字节** | **一个都没变**。只多一条服务端日志 |
| **iOS** | **零改动**。join 发生在日志侧（`session_id` / `turn_id` 本来就是两边都有的字段） |
| **可观测性** | 多一条 `voice.duplex.first_audio`；音频首响从"只有一个总数"变成**可与客户端总数相减得到网络段** |

## 7. 未做

- **没有把音频首响做成客户端可读的 wire 字段**。§2 的约束排除了最自然的载体，而另外两条路的代价
  （跨服务协议变更 / 每帧 8 字节）换来的只是"少一次日志 join"。**如果将来真需要客户端实时拿到它**，
  正确的做法是先在 iOS 侧有消费者，再加帧 —— 否则就是又一个"有生产、没消费"。
- **没有给 `D=0` 之外的东西加标记**。`voice.duplex.first_audio` 只回答"服务端花了多久才让用户听见"。
- **没有测 `turnStarted` 为零的情形**（`markFirstAudio` 会直接返回）。那种情况是"没有在途的轮"，
  此时谈首响没有意义 —— 静默返回是对的，但**没有测试钉住它**。
