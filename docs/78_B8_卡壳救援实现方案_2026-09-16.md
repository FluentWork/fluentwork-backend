### ⚠️ 与 V1.0 的两处语义修正

1. **沉默窗口的锚点从 `user.speech.start` 改为 `ai.tts.end`。** V1.0 §5.2 的流程图把开窗点画在用户开始说话，这会**排除 PRD §1.1 认定的首要卡壳场景**（"听不懂问题" → 用户完全不开口，永远不发 `user.speech.start`）。新语义：窗口由 AI 说完话开启（发言权交给用户），`user.speech.start` 只重置梯子层级、不移动窗口。§5.2 与 §5.3 的文字已同步。
2. **TTS 合成改为可缺省。** 原设计假定网关能直接调用 TTS Router；实际 `internal/content/tts` 自身处于 "built, not turned on"（见 docs/54）、住在 app-server 进程中、且内部端点返回 base64 分片而非可播放 URL。因此 `RescueSynthesizer` 是一个**可以传 nil** 的接口：无合成器时下发**纯文本梯子**（`audio_url` 为空），而不是伪造一个 iOS 必然取不到的 URL。

实施细节与推理路径见 `docs/devnotes/2026-09-16-b8-rescue-handler-integration.md`。

## 一、需求背景

### 1.1 PRD V1.6 描述

> **B8 卡壳救援**（PRD §8.2，V1.6 新增）
> 
> - **触发**: 用户沉默 ≥3 秒
> - **三层梯子**（递进救援）:
>   1. **句首骨架**: "I think the main risk is..." (英文)
>   2. **中文提示**: "先说结论，再说原因" (中文)
>   3. **完整示例**: "I think we should use a blue-green deployment..." (英文完整句)
> - **交互约束**:
>   - 不打断对话流（插入 TTS，不终止回合）
>   - 不计入失败（不影响评价指标）
>   - 每层间隔 3 秒，用户开口则重置
> - **埋点**: `first_stuck_rescue_triggered` (首次卡壳时间)

### 1.2 产品意义

PRD V1.6 评审会议（2026-09-11）明确：

> "B8 是全产品最重要的先行指标（首次开口率）的兜底机制。目标用户'听说薄弱'，沉默 ≥3s 意味着：(1) 听不懂问题；(2) 不知道怎么说；(3) 陷入焦虑。三层梯子对应三种认知负荷递减策略，最终目标是让用户**说出第一句话**，而不是完美表达。"

北极星指标受首次开口率直接驱动，B8 缺失等同于放弃 30-40% 的新用户激活。


## 三、实现细节

### 3.1 沉默检测 (SilenceDetector)

**已实现** (`internal/voicegateway/silence_detector.go`)。核心状态：

```go
type SilenceDetector struct {
    thresholds  RescueThresholds // 默认 3s/6s/9s，可配；零值补默认后单调钳制
    windowStart time.Time        // 发言权交给用户的时刻；零值 = 无窗口
    userSpeaking bool            // 用户正在说话 → 抑制救援
    rescueLevel int              // 本窗口内已触发的最高层级
}

func (d *SilenceDetector) OnAISpeechEnd(now time.Time)                    // 开窗
func (d *SilenceDetector) OnUserSpeechStart(now time.Time)                // 重置梯子层级，不动窗口
func (d *SilenceDetector) OnUserSpeechEnd(now time.Time, complete bool)   // true=关窗, false=继续爬梯
func (d *SilenceDetector) CheckSilence(now time.Time) (shouldRescue bool, level int)
func (d *SilenceDetector) Reset()
```

**`CheckSilence` 返回的是「最低的未触发档」而不是最高档**：迟到的轮询仍按 1→2→3 走完梯子，而不是直接跳到完整示例。生产 500ms 的 tick 远快于 3s 档距，所以永远不会出现一次 tick 补两档。

**集成点**: 在 `handler.go` / `handler_rescue.go` 中
- `sessionRuntime` 新增：检测器（**每会话克隆**，见下）、编排器、`rescueTick`、时钟、`rescueWG`、在途标志、停止 channel、上下文互斥锁、`ConversationContext`、当前 turn_id
- `loop` 启动轮询协程（每 `defaultRescueTick` = 500ms 一次 `CheckSilence`），`close` 里先停轮询再 `Wait`
- `sendOutbound` → `noteProviderOutbound()`：累积 AI 文本、记录 turn_id、按 `ai.tts.end` / `ai.turn.end` 开窗
- `handleControl`：`user.speech.start` → `noteUserSpeechStart()`；`user.speech.end` → `noteUserSpeechEnd()`（用 `IncompleteDetector` 判定后决定是否关窗）；`client.turn.abort` → `noteTurnAbort()`
- `session.start` → `noteScenario()` 记录场景

**三条必须记住的边界**（都有测试钉住）：
1. **检测器按会话克隆**：`SetRescueComponents` 传进来的实例只当阈值模板。共用一个检测器会让 A 会话开的窗口被 B 会话的 ticker 花掉，梯子送到错误的用户手上。
2. **在途检查必须早于 `CheckSilence`**：后者返回即消费该档，先后颠倒会在每次「生成与 tick 重叠」时永久丢一档。
3. **`ai.turn.end` outcome 为 `timeout` / `error` 时不开窗**：该回合没有问出任何问题，用户没有可卡壳的对象。B15 的 30s turn timeout 正是这条路径，且它到达时梯子早已用尽 —— 不挡的话，一个已超时的回合会在 33s 起被重新唠叨。

**为什么窗口不锚在 `user.speech.start`**（V1.1 修正，原 V1.0 方案如此）：见文首 §〇 说明与 `docs/devnotes/2026-09-16-b8-rescue-handler-integration.md` 第三节。

### 3.2 救援生成器 (RescueGenerator)

**已实现** (见 `internal/conversation/rescue_generator.go`):

```go
type RescueLevel int

const (
    RescueSkeleton RescueLevel = 1  // 句首骨架
    RescueHint     RescueLevel = 2  // 中文提示
    RescueComplete RescueLevel = 3  // 完整示例
)

type RescueGenerator struct {
    llmClient LLMClient
}

func (g *RescueGenerator) GenerateRescue(
    ctx context.Context,
    level RescueLevel,
    conv ConversationContext,
) (string, error)
```

**Prompt 策略**:

1. **Level 1 (Skeleton)**: 
   - 提取 AI 最后一句的主谓宾，生成"I think..." / "The key point is..." 句首
   - 最多 8 词，不完整句
   
2. **Level 2 (Hint)**:
   - 中文元认知提示，如"先说结论" / "举个例子" / "用因果关系"
   - 最多 12 字

3. **Level 3 (Complete)**:
   - 完整英文回答示例（参考场景上下文）
   - 15-25 词，完整句

### 3.3 不完整检测 (IncompleteDetector)

**已实现** (见 `internal/conversation/incomplete_detector.go`):

```go
type IncompleteDetector struct{}

func (d *IncompleteDetector) IsIncomplete(text string) bool {
    // 规则 1: 句尾 marker (and, but, because, so, ...)
    // 规则 2: 连接词开头 (because, although, ...)
    // 规则 3: 少于 3 词且无明显动词
}
```

**用途**: 
- 用户说话后，判断是否"真正开口"（完整表达）
- 不完整表达 → 继续等待，不重置救援计时器
- 完整表达 → 重置计时器，停止救援

**测试覆盖** (已通过 11 个测试用例):
- ✅ "I think" → incomplete
- ✅ "Because of that" → incomplete  
- ✅ "okay" → complete (单词视为完整简短回应)
- ✅ "I agree with your point" → complete

### 4.2 SilenceDetector 接口 (已实现)

```go
// 阈值可配（零值补默认 + 单调钳制），生产用 3s/6s/9s
type RescueThresholds struct {
    Level1 time.Duration // 默认 3s
    Level2 time.Duration // 默认 6s
    Level3 time.Duration // 默认 9s
}

func NewSilenceDetector() *SilenceDetector
func NewSilenceDetectorWithThresholds(t RescueThresholds) *SilenceDetector

// 开窗：AI 说完话，发言权交给用户，计时从此刻开始。
// 这是**唯一**的开窗入口 —— 锚在 user.speech.start 会漏掉"完全不开口"的用户。
func (d *SilenceDetector) OnAISpeechEnd(now time.Time)

// 用户开始说话：重置梯子层级（重新开口配得上一条新梯子），
// 但**不移动窗口**（半句话不能白赚 3 秒，见 §5.3 case 1）。
func (d *SilenceDetector) OnUserSpeechStart(now time.Time)

// 用户结束说话：complete=true 关窗（球在 AI 这边），false 保留窗口继续爬梯。
func (d *SilenceDetector) OnUserSpeechEnd(now time.Time, complete bool)

// 返回(是否触发, 层级)；升序返回最低未触发档，不跳档。
func (d *SilenceDetector) CheckSilence(now time.Time) (bool, int)

func (d *SilenceDetector) Reset()
func (d *SilenceDetector) GetState(now time.Time) (windowStart time.Time, level int, elapsed time.Duration)
func (d *SilenceDetector) Thresholds() RescueThresholds // 供 handler 每会话克隆
```

### 4.3 RescueSynthesizer 接口（音频出口，可传 nil）

```go
// 未实现。传 nil 时下发纯文本梯子（audio_url 为空）。
// 实现时必须使用 RescueVoiceSpeed = 0.9 / RescueVoiceVolume = 0.85。
type RescueSynthesizer interface {
```

**降级链**（两级，都不阻断下发）：
1. LLM 生成失败 → 用固定文本库（§8.1），梯子照发
2. 合成失败 / 未配置 → `audio_url` 留空，文本照发

理由：文本才是让特性生效的那部分，音频是其上的增强。用户沉默时递上一个错误提示，比递上一句提示更糟。

## 五、数据流

### 5.1 正常流程（用户流畅回答）

```
1. AI 说完 → ai.tts.end / ai.turn.end
   → SilenceDetector.OnAISpeechEnd(now)   开窗

2. iOS → WSS: user.speech.start
   → OnUserSpeechStart(now)   重置梯子层级，窗口不动；用户说话中抑制救援

3. iOS → WSS: user.speech.end (text="I agree with that")
   → IncompleteDetector.IsIncomplete() → false
   → OnUserSpeechEnd(now, complete=true)  关窗
   → 正常处理回合

4. AI 说完下一轮 → 重新开窗
```

### 5.2 救援流程（用户沉默 ≥3s）

```
1. AI 说完 → ai.tts.end
   → SilenceDetector.OnAISpeechEnd(now)   开窗（用户不需要先开口）

2. [沉默 3s]
   → 轮询协程（每 500ms）CheckSilence → (true, 1)
   → RescueOrchestrator.GenerateAndSynthesize(level=1, context)
       ├─ RescueGenerator 生成文本（LLM 失败 → 固定文本库）
       └─ RescueSynthesizer 合成（未配置/失败 → audio_url 留空）
   → WSS → iOS: ai.rescue.ladder (level=1, text="I think...")
   → iOS 播放救援语音 + 显示文本

3. [用户仍沉默 3s, 总计 6s] → 触发 Level 2 → ai.rescue.ladder (level=2)

4. [再次 3s, 总计 9s] → 触发 Level 3 → ai.rescue.ladder (level=3)

5. [仍沉默] → 不再触发（三级已用尽），等 B15 Turn Timeout 自然收口
```

> **注意**：流程起点是「AI 说完」而不是「用户开口」—— 这是 V1.1 的关键修正。

### 5.3 边界情况

> 以下时间轴以「AI 说完」为 t=0 —— 窗口由 `ai.tts.end` / `ai.turn.end` 开启（V1.1 修正）。

#### Case 1: 用户说了不完整句

```
0. AI 说完 → 开窗 (t=0)
1. user.speech.start (t=2.4s)
   → 重置梯子层级，**窗口不动**（半句话不能白赚 3 秒）
2. user.speech.end (text="I think") (t=2.5s)
   → IncompleteDetector.IsIncomplete() → true
   → OnUserSpeechEnd(complete=false) → **保留窗口**，继续爬梯
3. [又沉默 0.5s, 距开窗总计 3s]
   → 触发 Level 1 救援
```

> 关键：触发位置由「开窗时刻」决定，而不是「用户放弃的时刻」。用户越早放弃，救援来得越快 ——
> 这正是「I think 之后接不上」这一场景想要的。

#### Case 2: 用户打断救援 TTS

```
1. 救援 Level 1 正在播放
2. iOS → WSS: interrupt
   → 停止当前 TTS 播放
   → **保持救援状态**（用户可能还是卡住了）；检测器不受影响
3. user.speech.start
   → 重置梯子层级（用户重新开口配得上一条新梯子），窗口仍在原锚点
```

#### Case 3: 救援后用户仍沉默

```
1. Level 1 → Level 2 → Level 3 全部触发（0s / 3s / 6s / 9s）
2. 用户仍沉默
   → **不再触发救援**（三级已用尽，已给足支持）
   → 等待 B15 Turn Timeout (30s) 自然终止
3. Turn Timeout 产生的 ai.turn.end (outcome=timeout)
   → **不开新窗口**（该回合没有问出任何问题，用户没有可卡壳的对象）
```

> 第 3 步是 V1.1 新增的护栏。缺了它，一个已经超时的回合会在 30s 被重新唠叨 ——
> 而唠叨正是这个特性要消灭的东西。

### 7.2 集成测试

**已实现** (`internal/voicegateway/handler_rescue_test.go`, 12 tests)。

**关键手法：假时钟**。三条档位设为 50/100/150ms、tick 5ms，时钟由测试推进而非 `sleep`。两个好处：
- 「9 秒梯子」是一个断言而不是一次等待 → 不在负载机器上变成 flaky
- 负向用例（"不该收到梯子"）**在时钟冻结下成为构造上的必然** → 不与时序赛跑

**场景**（均已覆盖）:

1. **沉默救援全链路**：AI 说完 → 推进时钟 → 依次收到 level 1/2/3；此后不再打扰
2. **开窗信号双路径**：仅 `ai.tts.end` 开窗 / 仅 `ai.turn.end` 开窗（mock、dev-echo 只有后者）
3. **用户答完整** → 不救援；**用户说话中** → 不救援
4. **半句话继续计时**（§5.3 case 1）：AI 说完 → 推进 1/5 档距 → `user.speech.end("I think")` → 再推 4/5 → 触发 level 1
5. **`client.turn.abort`** → 解除抑制，梯子保留
6. **失败回合不开窗**：outcome=timeout / error → 全程无梯子；partial → 开窗
7. **未接线** → 全程无梯子（特性关闭时逐字节等价于 B8 之前）
8. **检测器每会话独立**，模板实例不被污染
9. **生成器确实拿到** `ScenarioContext` 与 AI 末句

> 原方案里的「打断不影响状态」场景未单独成文：`interrupt` 分支不改动检测器状态，
> 其效果已由「`user.speech.start` 重置梯子」与「`user.speech.end` 关窗」两条覆盖。

## 八、风险与缓解

### 8.1 LLM 生成失败

**风险**: Ark API 超时或返回空内容

**缓解**:
1. **降级策略**: 预设固定文本库
   - Level 1: `["I think...", "The key point is...", "In my view..."]`
   - Level 2: `["先说结论", "举个例子", "分几点说"]`
   - Level 3: `["I think we should consider the trade-offs carefully."]`

2. **超时控制**: `context.WithTimeout(ctx, 3*time.Second)`

3. **重试逻辑**: 失败后直接降级，不重试（避免延迟累加）

### 8.2 TTS 合成延迟

**风险**: 沉默 3s 触发救援，但 TTS 合成需 800ms，用户等待 3.8s 才听到救援

**当前状态**: 音频出口尚未实现，网关下发的是**纯文本梯子**，因此这条风险暂时不适用。

**音频出口落地后需要做的事**:
1. **预热策略**: 首次开窗时预生成 Level 1 骨架并缓存
2. **检测提前**: 沉默 2.5s 时开始生成，3s 时播放（提前 0.5s）
3. **监控告警**: TTS P95 延迟 > 1s 时触发告警

**已就位的部分**: LLM 生成的 deadline 被强制在 3s（`DefaultRescueLevel1After`）以内 —— 一条落在下一档之后才到的救援，已经输掉了它被生成时的那场比赛。

### 8.3 用户反感救援

**风险**: 部分高级用户觉得"被打断"或"太啰嗦"

**缓解**:
1. **设置开关**: 后续版本添加"救援提示"开关（默认开启）
2. **语速柔和**: `speed=0.9, volume=0.85` 避免生硬
3. **产品文案**: UI 显示"💡 提示"而非"救援"，降低负面感知

### 8.4 iOS 状态机冲突

**风险**: 救援 TTS 与正常 AI 回复的 TTS 队列冲突

**缓解**:
1. **协议明确**: `ai.rescue.ladder` 不触发状态转移
2. **播放优先级**: 救援 TTS 插队但可被打断
3. **联调验证**: Phase 5 重点测试状态机稳定性

## 十、总结

### 10.1 核心价值

B8 卡壳救援是 **PRD V1.6 最重要的新增功能**，直接影响北极星指标（首次开口率）。通过三层递进梯子，降低用户认知负荷，最大化"说出第一句话"的概率。

### 10.2 技术亮点

1. **非侵入式设计**: 救援不打断对话流，不影响状态机
2. **降级保障**: LLM 失败时使用预设文本库，保证可用性
3. **精细化检测**: `IncompleteDetector` 识别不完整句，避免误重置
4. **可观测性**: 埋点覆盖触发/有效率/延迟，支持迭代决策
