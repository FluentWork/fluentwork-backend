# 结构性问题怎么"先写会红的测试"——以及怎么迁到别的项目

**日期**：2026-09-18
**回答两件事**：
1. `AGENTS.md` §6「先有失败测试」这条纪律，**结构性/架构性问题怎么套用**
2. 这套纪律怎么**迁移到其他项目**
**配套**：`99_`（接缝驱动纪律）、`.golangci.yml`（R6 的机器执行部分）

---

## 一、结构性问题的"失败测试"是什么

§6 的原文只管"有人报告了一个问题"。结构问题没人报告——**它没有报告人，只有发现者**。
但纪律本身**照样适用**，只是"测试"的主语变了：

| | 报告型缺陷 | 结构性问题 |
|---|---|---|
| 触发 | 有人报告 | 有人**发现**（审核、审计、读代码时） |
| 断言对象 | **行为**（这个输入 → 这个输出） | **形状**（这条边不存在 / 只有一处 / 单调） |
| 测试住在哪 | 通常与被测代码同包 | 常常在**包外**（`_test` 包）或**配置里**（linter） |
| 什么时候红 | 行为回归时 | **有人加第二条路径时** |
| 没人看会怎样 | 功能坏掉，用户能感知 | 静默积累（`94_` 的九条） |

**一句话：结构问题 = 主语换成"形状"的同一套红/绿纪律。**

### 1.1 最硬的现成例子（就在本仓）

`scripts/check-defect-discipline.sh` 检查的是"实现说明里有没有『测试』小节"——
**那也是一条结构断言**（文档结构的断言），它靠 grep 而不是 `t.Fatal`：

```bash
if grep -qE '^##+ .*(测试|门禁|验证)' "$file"; then continue; fi
echo "✘ $file" >&2 ; failed=1
```

**断言形状不一定要写在 Go 里。** 这一条是整个回答的关键：
bash / python / linter 配置 / SQL，都是合法的落点。

## 二、五类结构问题 ↔ 五类断言

| # | 结构问题 | 断言形式 | 本仓的落点 | 现状 |
|---|---|---|---|---|
| 1 | **依赖方向被破坏** | 导入规则 | `.golangci.yml` 的 `depguard` | ✅ 今天加的 |
| 2 | **同一件事两份实现** | 反射扫描 / 一致性测试 | Go test 扫包内实现指定方法集的类型 | 待做 |
| 3 | **表示不收敛**（同一概念多种表示） | 反射扫描 / linter | 同上（本仓要先做 L7） | 待做（有前置） |
| 4 | **常量的语义/推导关系** | 断言推导式 | `TestFrameBytesDerivesFromSampleRate` | ✅ 已做（M3）：实际落在 `TestAudioSizesAreDerivedFromTheSampleRate`，`internal/voicegateway/utterance_test.go` |
| 5 | **状态机允许非法迁移** | 表驱动合法迁移集 | 见 `97_` §2.1 | ✅ 已做（M4）：`Turn.rejected` 计数 + `TestTurn_IllegalEventsAreCountedNotAbsorbed`（形状是"计数"而不是 `97_` 的手写白名单） |

### 2.1 第 1 类（今天已落地，可当模板）

```yaml
# .golangci.yml
linters:
  enable: [depguard]
  settings:
    depguard:
      rules:
        main:
          files: ["**/internal/voicegateway/**"]
          deny:
            - pkg: ".../internal/content/tts"
              desc: "语音链路不进程内调 TTS；走 HTTP 到 app-server"
```

**它当场就抓到了一个真实的边界模糊**：一个测试为了驱动真 handler 而
`import content/tts`。修法不是放宽规则，是**把测试挪到包外**
（`tts_test` 包）——这样"被测的 import 图"和"生产的 import 图"就一致了。

> **教训**：结构断言常常会逼出一个更诚实的测试位置。

### 2.2 第 2/3 类的写法（Go，反射扫描）

```go
// 一个语义只允许一个实现点：扫描包里所有实现了给接口的类型。
func TestOnlyOneTypeImplementsFrameWriter(t *testing.T) {
    var want = reflect.TypeOf((*FrameWriter)(nil)).Elem()
    var found []string
    for _, name := range []string{"voiceproto", "voicegateway"} {
        pkg := load(t, "internal/"+name)
        for _, typ := range typesIn(pkg) {
            if types.Implements(typ, want) {
                found = append(found, typ.String())
            }
        }
    }
    if len(found) != 1 {
        t.Fatalf("帧写入有 %d 处实现：%v —— 一份语义一个实现点（R2）", len(found), found)
    }
}
```

**注意**：这类断言依赖包结构（必须能枚举出"所有实现"）。
本仓的 `voicepoc` 包名与角色不符、生产传输层混在里面，会让这个扫描扫不准——
所以它有个**前置**：先做 `96_` 的 M6（拆 `voicepoc`），否则断言会漏。
**（2026-09-20 追加）前置已清除**：M6 在 `34395f0` 落地，生产传输层现在在
`internal/voiceduplex`，`voicepoc` 只剩 WER / 注入窗口等工具，`depguard` 的
`no-poc-in-production` 规则钉住了这个方向。也就是说第 2/3 类断言的阻塞点已经没有了，
只差写扫描本身。

**这就是"结构断言"的一个重要性质：它会暴露连带的债。** 这本身是好事。

### 2.3 第 4 类：推导关系（最便宜，收益直接）

```go
func TestFrameBytesDerivesFromSampleRate(t *testing.T) {
    f := AudioFormat{SampleRate: 16000, Channels: 1, BitsPerSample: 16}
    if got := f.FrameBytes(100); got != 3200 {
        t.Fatalf("FrameBytes(100ms) = %d, want 3200", got)
    }
    // 换采样率，帧长必须跟着变——常量复制做不到这一点
    f.SampleRate = 24000
    if got := f.FrameBytes(100); got != 4800 {
        t.Fatalf("24k FrameBytes(100ms) = %d, want 4800", got)
    }
}
```

现状的两处 `3200` 与两处 `640` 都是**复制**。这条测试在重构后才有意义——
但**它现在就能写**（断言"存在一个推导函数"），会立刻红，然后推动重构。

### 2.4 第 5 类：状态机

```go
func TestTurnStateMachine_RejectsIllegalTransitions(t *testing.T) {
    for _, tc := range []struct{ from, to State }{
        {StateIdle, StateSpeaking},      // 没开始听就说话
        {StateClosed, StateSpeaking},    // 已经结束的 turn 又出一帧
    } {
        if err := NewTurn(...).transition(tc.to); err == nil {
            t.Fatalf("%s → %s 被接受了；它必须是非法迁移", tc.from, tc.to)
        }
    }
}
```

## 三、这个仓库已经做过的三次（证明这条路成立）

| 做法 | 断言的形状 | 落点 |
|---|---|---|
| `sync-shared-schemas.sh` + `TestSchemaV1BytesAreFrozen` | 内嵌镜像 == 真源；字节不许变 | 配置/协议接缝 |
| `check-duplex-lifetime.py` | 日志上的不变量：一个 app 会话窗口里 duplex 只开一次 | **日志接缝**（没有改一行代码） |
| `check-defect-discipline.sh` | 文档结构：实现说明必须带凭据 | 流程接缝 |

**三种介质、三种形态、同一个方法**：把一个不变量写下来，然后用机器检查它。
所以 R6（依赖方向要能跑）不是新东西——**它只是这个已知有效的方法，第一次被用在代码结构本身上。**

## 四、行业里叫什么、用什么

我们自己做出来的这套，在业界有名字：**架构适应度函数（architecture fitness functions）**
——把架构特征写成可自动执行的检查，与功能测试一起常驻 CI。
（Ford & Parsons《Building Evolutionary Architectures》提出；InfoQ 有专文。）

> **重要纠正：它是 CI 的一部分，不是月度仪式。**
> 我在 `99_` §六建议的"每月挑一条接缝审计"是**人工复核**（找该建什么新断言），
> 断言本身**每次提交都要跑**——就在 `dev-check.sh` 里，和 `go test` 并列。
> 两者的关系：每月**产出**新断言，每天**执行**已有断言。混为一谈就白做了。

| 我们需要的 | 业界工具 | 备注 |
|---|---|---|
| 导入方向 | `depguard`（golangci-lint）、`go-arch-lint`、`import-boss` | ✅ 本仓已用 depguard |
| 包边界/分层规则 | `ArchUnit`（Java）、`import-linter`（Python）、`arch-unit`（TS） | 按语言选 |
| 跨服务契约 | `Pact`（消费者驱动契约） | 我们规模用不上，真 handler 驱动测试是它的轻量版 |
| 代码形状/反模式 | `semgrep`、`ast-grep` | 可写自定义规则，语言无关 |
| 不变量（随机化） | 属性测试：`gopter`/`rapid`（Go）、`Hypothesis`（Python）、`fast-check`（TS） | 适合状态机 |
| 日志/运行时形状 | 自写脚本（如 `check-duplex-lifetime.py`） | 没有通用工具，**自写最划算** |

**选择原则**（避免过度工程）：
**能用 linter 配置解决的，别写测试；能用测试解决的，别引工具；能自写 30 行脚本的，别引框架。**
本仓的 `depguard` 十行 YAML 就顶掉了一类问题。

## 五、怎么迁到别的项目

### 5.1 三层拆分（关键：只有第一层该被复制）

| 层 | 内容 | 可移植性 |
|---|---|---|
| **L1 原则** | 七条规则本身、接缝清单、红/绿纪律的"主语换成形状" | ✅ 逐字复制 |
| **L2 机制** | PR 模板那四行、CI 挂载点、"先证明它会红" | ⚠️ 按项目调整 |
| **L3 项目特有** | 本仓的接缝清单、案底（`94_` 九条）、devnotes 规则 | ❌ 不迁移，各项目自己长 |

**最常见的迁移错误**：把 L3 一起搬过去，写成一份"最佳实践长文"——
新项目读到一半就开始跳过，因为里面全是别人的坑。
**搬 L1 + 装 L2，让 L3 在使用中长出来。**

### 5.2 新项目落地的最短路径（一个下午）

| 步 | 动作 | 产出 |
|---|---|---|
| 0 | 把 L1 那页贴进项目的 agent 说明（`CLAUDE.md` / `AGENTS.md`） | 规则就位 |
| 1 | **列接缝清单**：进程间 / 包间 / goroutine 间 / 表示间 / 层间，各写一行 | 一页纸，通常 5–15 条 |
| 2 | 每条接缝挑**一条**断言，写下来，**确认它会红**（故意破坏一次） | 见下 |
| 3 | 接进已有的那条命令（`make check` / `npm test` / `./scripts/dev-check.sh`） | 每次提交都跑 |
| 4 | 起一份 `devnotes`，第一条写"为什么有这个文件" | 后续每条坑进这里 |

第 2 步的"确认它会红"**不是仪式**——本仓今天就踩过一次：
一个测试在"从不工作"的实现上也会通过，等于没有测试。**先证明它会红，再相信它。**

### 5.3 不同技术栈的落点

| 栈 | 导入方向 | 形状扫描 | 契约 |
|---|---|---|---|
| Go | `depguard` / `go-arch-lint` | Go test + `go/packages` 反射扫描 | 真 handler + `httptest` |
| TypeScript | `eslint-plugin-boundaries` / `dependency-cruiser` | `ast-grep` 规则 | `msw` / 真 server |
| Python | `import-linter` | `ast` 模块扫描（简单） | `TestClient`(FastAPI) / `pytest-httpserver` |
| Swift/iOS | 无成熟工具 → 模块边界靠 SPM target | 测试里断言协议实现数 | 协议 mock 由**生产方**提供 |
| 跨语言 | — | `semgrep` 自定义规则 | 消费者驱动契约（Pact） |

**iOS 那行值得单说**：没有成熟的架构 linter，但 **SPM 的 target 边界本身就是约束**——
把"不许互相 import"变成 target 依赖图，编译器帮你执行。这是移动端最划算的做法。

### 5.4 迁移时最容易失败的三件事

| 失败形态 | 为什么 | 对策 |
|---|---|---|
| 写成长文，没人读 | L3 内容太多 | 只搬 L1 一页，其余在使用中长 |
| 断言太多太严，天天红 | 违反"长期红的检查等于没有检查"（本仓 `AGENTS.md` §6 自己写过这句） | 每条断言先确认它能红，再确认它**平时是绿的** |
| 只有断言没有节奏 | 断言拦已知的，不发现新的 | 每月一条接缝的人工审计（`99_` §六） |

## 六、一句话回答

> **结构性问题的"失败测试"，就是把"形状"当成被测对象的那条同样的红/绿纪律。**
> 它可以写进 Go 测试、linter 配置、脚本或 SQL——**介质不重要，可执行才重要**。
>
> 迁到别的项目：**搬原则（一页），装机制（一个下午），让项目特有的那层在使用中长出来。**
